`obs.cert_path`/`obs.key_path` を設定すると、`SIGHUP` をきっかけにした証明書の
リロードが有効になります。
運用者が同じパスへ新しい PEM ペアを置いてプロセスへシグナルを送ると、それ以降に
新しく確立される（コールドスタートする）接続はすべて新しい証明書を使います。
ハンドシェイクを既に終えた接続は、リロードの影響を受けません。

## 仕組み

- `obs.cert_path`/`obs.key_path`（両方設定時）は、`wired_server_run_opt` の中で
  `SIGHUP` ハンドラをインストールします。
  シグナルを受け取ると、同じ PEM ペアを読み直して再デコードし、
  `id->chain`/`chain_count`/`cert_seed` をその場で更新します。
  `id` が const でないのはこのためです。
  呼び出し側は `id`（とその裏にある領域）を、実行中ずっと変更可能な状態で
  保持する必要があります。
- このページのサーバーは `id` 自身を持っているので、`on_step` フックから毎ティック
  `id->chain[0]` を読み、leaf 証明書（チェーンの末端にあるサーバー自身の証明書）の
  SHA-256 が変わったタイミングでログに出せます。
  起動時に一度、リロード直後にもう一度です。
- 差し替え用の PEM ペアは、起動直後の早い段階で一度だけ `live-cert.pem`/
  `live-key.pem`（`obs.cert_path`/`obs.key_path` が指すのと同じパス）に
  書き込みます。
  このファイルはサーバー自身が初期内容を書き込み、あとから差し替える対象なので
  gitignore されています。
  元データは `main.c` 内の `CERT_A`/`CERT_B` です。
  この書き込みは、運用者のデプロイ操作を模したものです。
  サーバーは `SIGHUP` が実際に届くまで、起動時に読み込んだ証明書をそのまま使い
  続けるので、このタイミングで書き込んでも最初のハンドシェイクには影響しません。
- `probe tls --fp` は、クライアント側からも同じ leaf 証明書のフィンガープリント
  （証明書のハッシュ値）を表示します。
  2 回目のハンドシェイクが新しい証明書を見ていることを、サーバーのログとは
  独立に確認できます。
