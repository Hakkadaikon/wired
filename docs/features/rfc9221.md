## §5.2 確認応答の扱い

- [x] 9221-020 (§5.2) 実装は、DATAGRAM フレームを ack-eliciting として扱わなければならない。
  - test: `tests/transport/ackgen_test.c` —
    `test_ackgen_datagram_only_packet_delayed`
- [~] 9221-021 (§5.2) 実装は、損失を検出しても DATAGRAM フレームを再送してはならない。
  - evidence: DATAGRAM を含むパケットは送信済みパケットの記録(送信中バイト数と PTO のため)にだけ入り、送信セッションには入らないので、再送されることはない。
- [~] 9221-022 (§5.2) サーバーは、DATAGRAM フレームだけを含むパケットに対する ACK フレームを、max_ack_delay の範囲内で遅らせられるようにするべきである。
  - evidence: 実際に動いている `ackpolicy` は DATAGRAM を含むどの ack-eliciting パケットに対しても ACK を最大 max_ack_delay まで遅らせる。DATAGRAM だけのパケットのテスト(`test_ackgen_datagram_only_packet_delayed`)が動かしているのは、どこからも呼ばれていない `ackgen_should_ack` である。
- [x] 9221-028 (§5.2) DATAGRAM フレームだけを含むパケットが失われた疑いがあるとき、サーバーは、ほかの ack-eliciting パケットと同じようにプローブパケットを送らなければならない(RFC 9002 §6.2.4)。
  - test: `tests/app/srvrun_rec_test.c` — `test_srvrun_pto_pings_datagram_only` (DATAGRAM だけのパケットで 1-RTT の PTO を設定する。プローブは PING)

## 対象外

クライアントだけの要件、アプリケーションプロトコルの要件、任意の機能の要件で、このサーバー SDK が実装しないものです。カバレッジの分母から除いています。

- (§3) サーバーの max_datagram_frame_size を 0-RTT の状態とともに保存し、新しい値が保存した値より小さくないことを検証すること。クライアントの動作。
- (§3) max_datagram_frame_size トランスポートパラメーターがない場合にアプリケーションプロトコルがどう反応するかを定めること。アプリケーションプロトコルの関心事。
- (§3) 記憶した max_datagram_frame_size のもとで 0-RTT で DATAGRAM フレームを送ること。クライアントの動作。サーバーは 0-RTT パケットを送らない。
- (§3) DATAGRAM フレームを一方向だけでネゴシエートまたは使用すること。アプリケーションプロトコルの選択(MAY)。
- (§5.1) Datagram Data の中でデータグラムのフローを多重化する識別子を定めること。アプリケーションプロトコルの責任。
- (§5.2) データグラムが失われたことや確認応答されたことをアプリケーションに通知すること。任意(MAY)の機能で、サーバーの経路には載せていない。
- (§5.4) 輻輳で遅れたデータグラムの送信期限と、輻輳による破棄をアプリケーションに通知すること。任意の機能で、載せていない。
- (§6) 0-RTT での DATAGRAM フレームの許容できる使い方のプロファイル(RFC 9001 §5.6)を定めること。アプリケーションプロトコルの関心事。
- (§6) 損失への反応から DATAGRAM の使用が検出できること。参考情報。
