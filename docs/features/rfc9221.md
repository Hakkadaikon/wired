# RFC 9221 — An Unreliable Datagram Extension to QUIC

EARS requirement ledger extracted from the spec text
(`tasks/specs/rfc9221.txt`, not in git). Each requirement carries the test
that demonstrates it; an unchecked box with no test line is an open gap.
Status as of 2026-10.

Legend:

- `[x]` — demonstrated by the referenced test
- `[~]` — exercised indirectly (evidence line explains how; no dedicated test)
- `[ ]` — not demonstrated by any test yet

**Coverage: 18/26 tested, 4 indirect, 4 untested.**

## §3 Transport Parameter

- [x] 9221-001 (§3) Where datagram receive support is enabled, the server
  shall advertise it with the max_datagram_frame_size transport parameter
  (0x20), a variable-length integer giving the maximum DATAGRAM frame size
  it is willing to receive.
  - test: `tests/tls/server_tp_test.c` —
    `test_server_tp_datagram_frame_size`
- [x] 9221-002 (§3) The server shall treat an absent or zero
  max_datagram_frame_size as the peer not supporting DATAGRAM frames.
  - test: `tests/app/datagram_test.c` — `test_datagram_allowed`
  - test: `tests/tls/server_tp_test.c` —
    `test_server_tp_datagram_frame_size`
- [x] 9221-003 (§3) The server shall not send DATAGRAM frames until it has
  received a max_datagram_frame_size transport parameter with a non-zero
  value.
  - test: `tests/app/dg_send_test.c` — `test_dg_send_unsupported`
  - test: `tests/app/srvrun_test.c` —
    `test_srvrun_datagram_rejected_when_peer_unadvertised`
- [x] 9221-004 (§3) The server shall not send a DATAGRAM frame larger than
  the max_datagram_frame_size value received from its peer.
  - test: `tests/app/dg_send_test.c` — `test_dg_send_over_max`
  - test: `tests/app/srvrun_test.c` —
    `test_srvrun_datagram_rejected_over_peer_limit`
- [x] 9221-005 (§3) If a DATAGRAM frame is received without the server
  having advertised support, then the server shall terminate the connection
  with an error of type PROTOCOL_VIOLATION.
  - test: `tests/app/dgcheck_test.c` — `test_dgcheck`
  - test: `tests/app/srvloop_test.c` —
    `test_srvloop_datagram_without_advertising_rejected`
- [x] 9221-006 (§3) If a received DATAGRAM frame is larger than the value
  the server sent in its max_datagram_frame_size transport parameter, then
  the server shall terminate the connection with an error of type
  PROTOCOL_VIOLATION.
  - test: `tests/app/dgcheck_test.c` — `test_dgcheck`
  - test: `tests/app/srvloop_test.c` —
    `test_srvloop_datagram_exceeding_advertised_limit_rejected`
  - test: `tests/app/srvrun_test.c` —
    `test_srvrun_oversized_datagram_latches_violation_on_step`
- [x] 9221-007 (§3) The server should support advertising the recommended
  max_datagram_frame_size value of 65535 to accept any DATAGRAM frame that
  fits in a QUIC packet.
  - test: `tests/tls/server_tp_test.c` —
    `test_server_tp_datagram_frame_size`
- [~] 9221-008 (§3) When accepting 0-RTT data, the server shall send a
  max_datagram_frame_size greater than or equal to the value it sent on the
  connection where it sent the NewSessionTicket message.
  - evidence: the advertised value comes from the server identity
    (`max_datagram_frame_size` in `srvboot.c`), fixed for the process, so it
    cannot shrink between connections of one process; the accept-safe
    predicate `datagram_0rtt_accept_ok`
    (`test_0rtt_accept_meets_or_exceeds_issued`) has no caller and the
    ticket does not record the issued value.

## §4 Datagram Frame Types

- [x] 9221-010 (§4) The implementation shall parse the DATAGRAM frame types
  0x30 and 0x31, taking the least significant bit of the Type field as the
  LEN bit that indicates whether a Length field is present.
  - test: `tests/app/datagram_test.c` — `test_datagram_with_len`
  - test: `tests/app/datagram_test.c` — `test_datagram_no_len`
- [x] 9221-011 (§4) When the LEN bit is 0, the implementation shall take
  the Datagram Data field as extending to the end of the packet.
  - test: `tests/app/datagram_test.c` — `test_datagram_no_len`
  - test: `tests/app/dg_recv_test.c` — `test_dg_recv_no_length`
- [x] 9221-012 (§4) When the LEN bit is 1, the implementation shall take
  the Length field as a variable-length integer giving the length of the
  Datagram Data field in bytes.
  - test: `tests/app/datagram_test.c` — `test_datagram_with_len`
  - test: `tests/app/dg_recv_test.c` — `test_dg_recv_with_length`
- [x] 9221-013 (§4) The implementation shall accept empty (zero-length)
  datagrams.
  - test: `tests/app/datagram_test.c` — `test_datagram_truncated`
  - test: `tests/app/dgcheck_test.c` — `test_dgcheck`
- [x] 9221-014 (§4) If a DATAGRAM frame's data is truncated relative to its
  declared Length, then the implementation shall reject the frame as
  malformed.
  - test: `tests/app/datagram_test.c` — `test_datagram_truncated`
  - test: `tests/app/dg_recv_test.c` — `test_dg_recv_truncated`

## §5.1 Multiplexing Datagrams

- [ ] 9221-019 (§5.1) The server should present an API to assign relative
  priorities to DATAGRAM frames with respect to each other and to QUIC
  streams.
  - gap: the `dgpriority` module has no caller and no public API exposes
    DATAGRAM priority.

## §5.2 Acknowledgement Handling

- [x] 9221-020 (§5.2) The implementation shall treat DATAGRAM frames as
  ack-eliciting.
  - test: `tests/transport/ackgen_test.c` —
    `test_ackgen_datagram_only_packet_delayed`
- [~] 9221-021 (§5.2) The implementation shall not retransmit DATAGRAM
  frames upon loss detection.
  - evidence: `srvrun_send_datagram_now` keeps no sent-packet or
    retransmission state for a DATAGRAM, so nothing can resend it; the
    dedicated tests drive the unwired `dgcc`/`dg_loss` helpers.
- [~] 9221-022 (§5.2) The server should support delaying ACK frames, within
  the limits of max_ack_delay, for packets that only contain DATAGRAM
  frames.
  - evidence: the live `ackpolicy` delays the ACK up to max_ack_delay for
    any ack-eliciting packet, DATAGRAM included; the DATAGRAM-only test
    (`test_ackgen_datagram_only_packet_delayed`) drives the unwired
    `ackgen_should_ack`.
- [ ] 9221-028 (§5.2) When the server suspects a packet containing only
  DATAGRAM frames was lost, the server shall send probe packets as for any
  ack-eliciting packet (RFC 9002 §6.2.4).
  - gap: DATAGRAM-only packets are not tracked for loss or PTO
    (`srvrun_send_datagram_now`), so no probe is ever sent for them.

## §5.3 Flow Control

- [~] 9221-024 (§5.3) The implementation shall not subject DATAGRAM frames
  to flow control, and they shall not contribute to any per-flow or
  connection-wide data limit.
  - evidence: `srvrun_send_datagram_now` never reads or charges stream or
    connection credit; the dedicated `test_dgcc` drives unwired constant
    predicates.
- [x] 9221-025 (§5.3) When the server cannot process or store a received
  DATAGRAM frame, the server may drop it.
  - test: `tests/app/srvloop_test.c` —
    `test_srvloop_datagram_queue_overflow_drops_newest`

## §5.4 Congestion Control

- [ ] 9221-026 (§5.4) The implementation shall subject DATAGRAM frames to
  the connection's congestion controller, counting their bytes in flight.
  - gap: `srvrun_send_datagram_now` sends without a cwnd check and adds
    nothing to bytes in flight; `dgcc.c` is unwired.
- [ ] 9221-027 (§5.4) When the congestion controller does not allow a send,
  the server shall either delay sending the DATAGRAM frame until allowed or
  drop it without sending.
  - gap: the DATAGRAM send path bypasses the cwnd/pacing gate entirely
    (see 9221-026).

## Out of scope

Client-only, application-protocol, and optional-feature requirements this
server SDK does not implement, excluded from the coverage denominator:

- (§3) Storing the server's max_datagram_frame_size with 0-RTT state and
  validating that the new value is not smaller than the stored one —
  client behavior.
- (§3) Defining how an application protocol reacts to the absence of the
  max_datagram_frame_size transport parameter — application-protocol
  concern.
- (§3) Sending DATAGRAM frames in 0-RTT under a remembered
  max_datagram_frame_size — client behavior; the server sends no 0-RTT
  packets.
- (§3) Negotiating or using DATAGRAM frames in one direction only —
  application-protocol choice (MAY).
- (§5.1) Defining identifiers that multiplex flows of datagrams inside
  Datagram Data — application-protocol responsibility.
- (§5.2) Notifying the application that a datagram was lost or
  acknowledged — optional (MAY) features not shipped on the server path.
- (§5.4) A sending expiration time for congestion-delayed datagrams, and
  notifying the application of a congestion drop — optional features not
  shipped.
- (§6) Defining a profile for acceptable use of DATAGRAM frames in 0-RTT
  (RFC 9001 §5.6) — application-protocol concern.
- (§6) Detectability of DATAGRAM use through its loss response —
  informational.
