各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。
2026-10 時点の状況です。

凡例:

- `[x]`: 挙げたテストで確認済み

## §2 表記法と定義

- [x] 9002-001 (§2) 実装は ACK、PADDING、CONNECTION_CLOSE 以外のすべてのフレームを ACK 誘発(ack-eliciting)フレームとして分類しなければならない。

## 対象外

クライアント専用、または運用者レベルの要件で、このサーバー SDK が実装しないもの。カバレッジの分母から除外しています。

- (§5.2) 接続中のほかの時点で min_rtt を確立し直すことと、それを頻繁に更新しすぎることに対する SHOULD NOT。任意(MAY)のヒューリスティックで、実装していない。
- (§5.3) 確認前に、補正後に min_rtt を下回った RTT サンプルを無視することと、Initial パケットの確認応答の遅延を無視すること。任意(MAY)の緩和で、実装していない。
- (§5.3) 鍵がないために確認応答の処理を先送りしたとき、ローカルの遅延を RTT サンプルから差し引くこと。クライアントの 0-RTT の確認応答の場面であり、サーバーは確認応答をすぐに処理する。
- (§6.2.1) サーバーがアドレスを検証するまで、Initial パケットの確認応答で PTO のバックオフをリセットしないこと。クライアントの振る舞い。
- (§6.2.2) 以前の接続の平滑化 RTT や PATH_CHALLENGE/PATH_RESPONSE の遅延を初期 RTT として再利用すること。任意(MAY)のヒューリスティックで、実装していない。
- (§6.2.2.1) サーバーのアドレス検証中のクライアントの PTO の義務(送信中のものがなくても PTO を設定する、PTO で Handshake パケットかパディングした Initial を送る)。クライアントの振る舞い。
- (§6.2.3) ハンドシェイクの完了を早めるために、PTO の満了より前に確認応答されていない CRYPTO データを送ること。任意(MAY)の高速化。
- (§6.2.4) より早い確認応答を引き出すためにパケット番号を飛ばすことや、プローブする代わりに送信中のパケットを損失とみなすこと。実装したプローブの方式に代わる任意の手段。
- (§6.3) Retry パケットを受信したときに輻輳制御と損失回復の状態をリセットすること。クライアントの振る舞い。
- (§6.4) 0-RTT が拒否されたときに、送信中の 0-RTT パケットの回復の状態を破棄すること。クライアントの振る舞い(サーバーは 0-RTT パケットを送らない)。
- (§7) 代替の輻輳制御が RFC 8085 §3.1 に適合すること。アルゴリズム選択の指針であり、SDK の既定の CUBIC と選択可能な NewReno/BBR モードはこの仕様の範囲外。
- (§7.2) 最大データグラムサイズが変わったときに初期輻輳ウィンドウを計算し直すこと。SDK は 1200 バイトに固定した最大データグラムサイズを使う。
- (§7.4) ピアが鍵を持つ前に届いた Handshake、0-RTT、1-RTT パケットの損失を無視すること。任意(MAY)の緩和で、実装していない。
- (§7.6.2) パケット番号スペースをまたいでパケットを永続的な輻輳の判定に含めること。サーバーは Application Data の損失だけを追跡しており、これは §7.6.2 が認める(MAY)単一スペースでの代替手段である。
- (§7.8) 十分に使っていなかったあとのウィンドウ更新の代替の仕組み(RFC 7661)。任意(MAY)で、実装していない。
- (§8.2) トラフィック分析に対抗するために、確認応答をほかのフレームとまとめたりパディングしたりすること。アプリケーションまたは運用者向けの緩和策の指針。
- (§8.3) ECN の報告が抑制されていることを検出するために、ときどきパケットに ECN-CE を付けること。任意の検出手段で、実装していない。
