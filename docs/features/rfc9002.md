# RFC 9002 — QUIC Loss Detection and Congestion Control

EARS requirement ledger extracted from the spec text
(`tasks/specs/rfc9002.txt`, not in git). Each requirement carries the test
that demonstrates it; an unchecked box with no test line is an open gap.
Status as of 2026-10.

Legend:

- `[x]` — demonstrated by the referenced test
- `[~]` — exercised indirectly (evidence line explains how; no dedicated test)
- `[ ]` — not demonstrated by any test yet

**Coverage: 42/75 tested, 24 indirect, 9 untested.**

## §2 Conventions and Definitions

- [x] 9002-001 (§2) The implementation shall classify all frames other than
  ACK, PADDING, and CONNECTION_CLOSE as ack-eliciting.
  - test: `tests/transport/dispatch_test.c` — `test_dispatch_ack_eliciting`
- [~] 9002-002 (§2) The server shall treat a sent packet as in flight when it
  is ack-eliciting or contains a PADDING frame and it has not been
  acknowledged, declared lost, or discarded along with old keys.
  - evidence: the server's in-flight set is the `wired_sendsess` log of sent
    STREAM slices, cleared on ACK or loss (`test_sendsess_ack_consumes`,
    `test_sendsess_threshold_declares_lost`); the general predicate
    `pkt_in_flight` has no caller and PADDING-only packets are never
    tracked.

## §5.1 Generating RTT Samples

- [x] 9002-004 (§5.1) When an ACK newly acknowledges the largest acknowledged
  packet and at least one newly acknowledged packet is ack-eliciting, the
  server shall generate the RTT sample latest_rtt as the time elapsed since
  the largest acknowledged packet was sent.
  - test: `tests/app/srvrun_test.c` —
    `test_srvrun_rtt_sample_uses_newest_hit_only`
- [~] 9002-005 (§5.1) The server shall generate an RTT sample using only the
  largest acknowledged packet in the received ACK frame.
  - evidence: one ACK range covering three slices samples only the newest
    (`test_srvrun_rtt_sample_uses_newest_hit_only`); no multi-range test.
  - gap: `srvrun_cc_range` samples once per ACK range per send session, so
    a multi-range ACK yields several samples.
- [ ] 9002-006 (§5.1) When an ACK frame does not newly acknowledge the
  largest acknowledged packet, the server shall not use it to update RTT
  estimates.
  - gap: the server samples from any newly acked slice in a range; nothing
    checks that the frame's largest acknowledged is newly acknowledged
    (`rtt_sample_valid` has no caller).
- [~] 9002-007 (§5.1) If an ACK frame does not newly acknowledge at least one
  ack-eliciting packet, then the server shall not generate an RTT sample.
  - evidence: `srvrun_cc_range` samples only when the range newly acks
    bytes of a tracked STREAM slice, which is always ack-eliciting; no test
    feeds an ACK of only non-eliciting packets.

## §5.2 Estimating min_rtt

- [x] 9002-008 (§5.2) When the first RTT sample is taken, the server shall
  set min_rtt to latest_rtt.
  - test: `tests/transport/rtt_test.c` — `test_rtt_first_sample`
- [~] 9002-009 (§5.2) On all samples after the first, the server shall set
  min_rtt to the lesser of min_rtt and latest_rtt.
  - evidence: `next_sample` in `src/transport/recovery/detect/recovery/rtt.c`

- [~] 9002-010 (§5.2) The server shall compute min_rtt from locally observed

    server feeds `ack_delay = 0` (`srvrun_rtt_note`); no dedicated
    assertion.
- [x] 9002-011 (§5.2) When persistent congestion is established, the server
  shall set min_rtt to the newest RTT sample.
  - test: `tests/transport/rtt_test.c` —

## §5.3 Estimating smoothed_rtt and rttvar

- [~] 9002-012 (§5.3) Before any RTT sample is available, the server shall
  initialize smoothed_rtt to kInitialRtt and rttvar to kInitialRtt / 2.
  - evidence: `rtt_init` seeds both (`srvrun_retry.c` calls it);
    `test_srvrun_pto_budget_exhausted_tears_down_connection` drives probes
    at the derived 1024 ms cadence but never asserts a probe is withheld
    before it, so the seed value is not pinned.
- [x] 9002-013 (§5.3) On the first RTT sample after initialization, the
  server shall set smoothed_rtt to latest_rtt and rttvar to latest_rtt / 2.
  - test: `tests/transport/rtt_test.c` — `test_rtt_first_sample`
- [x] 9002-014 (§5.3) On subsequent RTT samples, the server shall update
  smoothed_rtt as 7/8 * smoothed_rtt + 1/8 * adjusted_rtt and rttvar as
  3/4 * rttvar + 1/4 * |smoothed_rtt - adjusted_rtt|.
  - test: `tests/app/srvrun_test.c` — `test_srvrun_rtt_ewma`
  - test: `tests/transport/rtt_test.c` — `test_rtt_constant_stays`
  - test: `tests/transport/rtt_test.c` — `test_rtt_within_bounds`
  - test: `tests/transport/rtt_test.c` —
    `test_rtt_sample_ignores_max_ack_delay_before_confirm`
- [~] 9002-015 (§5.3) While the handshake is not confirmed, the server shall
  ignore the peer's max_ack_delay when adjusting RTT samples.
  - evidence: `rtt_sample` uses the delay unclamped before confirmation
    (`test_rtt_sample_ignores_max_ack_delay_before_confirm`).
  - gap: `srvrun_rtt_note` passes `ack_delay = 0`, so the server never
    applies the peer's ACK Delay at all.
- [~] 9002-016 (§5.3) After the handshake is confirmed, the server shall use
  the lesser of the acknowledgment delay and the peer's max_ack_delay when
  adjusting an RTT sample.
  - evidence: `rtt_sample` clamps after confirmation
    (`test_rtt_sample_clamps_ack_delay_after_confirm`,
    `test_rtt_sample_uses_ack_delay_after_confirm_when_smaller`).
  - gap: same as 9002-015 (the server feeds `ack_delay = 0`).
- [~] 9002-017 (§5.3) If subtracting the acknowledgment delay would make the
  RTT sample smaller than min_rtt, then the server shall not subtract it.
  - evidence: `adjust` in `rtt.c` keeps latest_rtt below the min_rtt +
    ack_delay boundary; the only boundary test drives the unwired
    `rtt_adjusted` helper, and the server feeds `ack_delay = 0`.

## §6.1.2 Time Threshold

- [~] 9002-021 (§6.1.2) When a later packet in the same packet number space
  has been acknowledged, the server shall declare an earlier packet lost if
  it was sent more than max(kTimeThreshold * max(smoothed_rtt, latest_rtt),
  kGranularity) in the past, with kTimeThreshold = 9/8.
  - evidence: a slice past 9/8 * srtt is declared lost on its own
    (`test_sendsess_time_threshold_declares_lost_alone`); `loss_by_time`
    takes the larger RTT (`test_loss_by_time_uses_max`).
  - gap: `sendsess_lost_by_time` passes srtt as both RTTs, so latest_rtt is
    never considered.
- [ ] 9002-022 (§6.1.2) The server shall set the time threshold to at least
  the local timer granularity (kGranularity).
  - gap: `loss_by_time` on the server path has no kGranularity floor (the
    floor exists only in the unwired `lossdrive_loss_delay`).
- [ ] 9002-023 (§6.1.2) When packets sent prior to the largest acknowledged
  packet cannot yet be declared lost, the server shall set a timer for the
  remaining time.
  - gap: the server has no loss-detection timer; the time threshold is
    re-evaluated only when an ACK step runs (`srvrun_feed_acks`).

## §6.2 Probe Timeout

- [~] 9002-024 (§6.2) When the PTO timer expires, the server shall not mark
  prior unacknowledged packets as lost.
  - evidence: a PTO fire never reaches `cc_on_loss`; it requeues the two
    oldest slices for resend (`test_sendsess_pto_probes_two_oldest`), which
    does take them out of the in-flight log
    (`test_srvrun_pto_requeue_frees_inflight_bytes_before_resend`).
- [~] 9002-025 (§6.2) The server shall compute the PTO per packet number
  space.
  - evidence: the boot flight (Initial/Handshake) has its own deadline and
    count (`test_srvrun_boot_pto_resends_after_deadline`) apart from the
    1-RTT send-session PTO (`test_srvrun_pto_not_due_within_rtt_window`);
    Initial and Handshake share one boot timer.

## §6.2.1 Computing PTO

- [x] 9002-026 (§6.2.1) When an ack-eliciting packet is transmitted, the
  server shall schedule the PTO as smoothed_rtt + max(4 * rttvar,
  kGranularity) + max_ack_delay.

  - test: `tests/app/srvrun_test.c` —
    `test_srvrun_pto_not_due_within_rtt_window`
- [ ] 9002-027 (§6.2.1) When the PTO is armed for the Initial or Handshake
  packet number space, the server shall set max_ack_delay to 0 in the PTO
  computation.
  - gap: the boot PTO (`srvrun_boot_pto_due`) uses `srvrun_pto_deadline_ms`,
    which adds `SRVRUN_MAX_ACK_DELAY_US`; the `hspto` module that excludes
    it has no caller.
- [x] 9002-028 (§6.2.1) The server shall set the PTO period to at least
  kGranularity.
  - test: `tests/transport/pto_test.c` — `test_pto_granularity_floor`
- [~] 9002-029 (§6.2.1) When ack-eliciting packets are in flight in multiple
  packet number spaces, the server shall set the timer to the earlier value
  of the Initial and Handshake spaces.
  - evidence: the server keeps one boot timer for its whole Initial +
    Handshake flight, stamped at the flight's send
    (`test_srvrun_boot_pto_resends_after_deadline`); no per-space deadline
    comparison exists or is tested.
- [ ] 9002-030 (§6.2.1) While the handshake is not confirmed, the server
  shall not set a PTO timer for the Application Data packet number space.
  - gap: `srvrun_pto_slot` has no confirmation gate (a 0-RTT-triggered
    response could arm it); the `hspto` module that gates it has no caller.
- [~] 9002-031 (§6.2.1) When an ack-eliciting packet is sent or acknowledged,
  the server shall restart its PTO timer.
  - evidence: the 1-RTT PTO deadline is measured from the oldest in-flight
    slice (`srvrun_sess_pto_due`), so an ACK that clears it moves the
    deadline (`test_srvrun_pto_not_due_within_rtt_window`).
  - gap: a new send does not restart the timer (A.8 measures from the last
    ack-eliciting send); `pto_should_reset` has no caller.
- [x] 9002-032 (§6.2.1) When the PTO timer expires, the server shall double
  the PTO period (backoff 2^pto_count).
  - test: `tests/transport/pto_test.c` — `test_pto_backoff`
  - test: `tests/transport/pto_test.c` — `test_pto_backoff_scales`
- [x] 9002-033 (§6.2.1) When an acknowledgment is received, the server shall
  reset the PTO backoff factor.
  - test: `tests/app/sendsess_test.c` — `test_sendsess_pto_resets_on_ack`
- [ ] 9002-034 (§6.2.1) While a timer is set for time-threshold loss
  detection, the server shall not set the PTO timer.
  - gap: the server has no time-threshold loss timer (see 9002-023), so the
    precedence rule is not implemented; `losstimer` has no caller.

## §7.6 Persistent Congestion

- [x] 9002-062 (§7.6.1) The server shall compute the persistent congestion
  duration as (smoothed_rtt + max(4 * rttvar, kGranularity) + max_ack_delay)
  * kPersistentCongestionThreshold, with a threshold of 3.
  - test: `tests/transport/persistent_test.c` — `test_persistent_threshold`
  - test: `tests/app/srvrun_test.c` —
    `test_srvrun_persistent_congestion_threshold` (just below, at and just
    above 3*PTO)
- [x] 9002-063 (§7.6.2) The server shall establish persistent congestion only
  when two ack-eliciting packets are declared lost, no packets sent between

## Out of scope

Client-only or operator-level requirements this server SDK does not
implement, excluded from the coverage denominator:

- (§5.2) Reestablishing min_rtt at other times in the connection, and the
  SHOULD NOT on refreshing it too often — optional (MAY) heuristic, not
  implemented.
- (§5.3) Ignoring RTT samples that fall below min_rtt after adjustment
  before confirmation, and ignoring the acknowledgment delay for Initial
  packets — optional (MAY) leniencies, not implemented.
- (§5.3) Subtracting local delays from RTT samples when acknowledgment
  processing is postponed for missing keys — client 0-RTT acknowledgment
  scenario; the server processes acknowledgments immediately.
- (§6.2.1) Not resetting the PTO backoff on acknowledgments in Initial
  packets until the server has validated the address — client behavior.
- (§6.2.2) Reusing a previous connection's smoothed RTT or a
  PATH_CHALLENGE/PATH_RESPONSE delay as the initial RTT — optional (MAY)
  heuristics, not implemented.
- (§6.2.2.1) Client PTO obligations during server address validation
  (arming the PTO with nothing in flight, sending a Handshake packet or a
  padded Initial on PTO) — client behavior.
- (§6.2.3) Sending unacknowledged CRYPTO data ahead of the PTO expiry to
  speed up handshake completion — optional (MAY) acceleration.
- (§6.2.4) Skipping a packet number to elicit a faster acknowledgment, or
  marking in-flight packets lost instead of probing — optional alternatives
  to the implemented probe strategy.
- (§6.3) Resetting congestion control and loss recovery state on receiving a
  Retry packet — client behavior.
- (§6.4) Discarding recovery state for in-flight 0-RTT packets when 0-RTT is
  rejected — client behavior (the server does not send 0-RTT packets).
- (§7) Conformance of an alternative congestion controller to RFC 8085
  §3.1 — algorithm-selection guideline; the SDK's CUBIC default and
  selectable NewReno/BBR modes are beyond this spec.
- (§7.2) Recalculating the initial congestion window when the maximum
  datagram size changes — the SDK uses a fixed 1200-byte maximum datagram.
- (§7.4) Ignoring the loss of Handshake, 0-RTT, and 1-RTT packets that
  arrived before the peer had keys — optional (MAY) leniency, not
  implemented.
- (§7.6.2) Considering packets across packet number spaces for persistent
  congestion — the server tracks Application Data losses only, the
  single-space fallback §7.6.2 permits (MAY).
- (§7.8) Alternative window-update mechanisms after underutilization
  (RFC 7661) — optional (MAY), not implemented.
- (§8.2) Bundling acknowledgments with other frames or padding to resist
  traffic analysis — application/operator mitigation guidance.
- (§8.3) Marking occasional packets with ECN-CE to detect suppression of
  ECN reports — optional detection strategy, not implemented.
