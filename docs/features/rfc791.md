# RFC 791 — Internet Protocol (IPv4)

EARS requirement ledger extracted from the spec text
(`tasks/specs/rfc791.txt`, not in git). Each requirement carries the test
that demonstrates it; an unchecked box with no test line is an open gap.
Status as of 2026-10.

Scope: this ledger covers only the IPv4 header build/parse and checksum
requirements exercised by wired's own AF_XDP path
(`src/transport/io/socket/net/ipv4.c`,
`src/transport/io/xdp/xdpframe/xdpframe.c`). wired is a server SDK, an endpoint,
not a gateway: routing, fragmentation-by-gateways, and options are out of
scope and listed below rather than silently dropped. The header is built by
wired itself only on the AF_XDP path; the interop runs used kernel UDP
sockets, which build their own IPv4 headers, so this framing is
unit-tested but not interop-proven.

Legend:

- `[x]` — demonstrated by the referenced test
- `[~]` — exercised indirectly (evidence line explains how; no dedicated test)
- `[ ]` — not demonstrated by any test yet

**Coverage: 14/16 tested, 2 indirect, 0 untested.**

## §3.1 Internet Header Format

- [x] 791-001 (§3.1) The implementation shall set the Version field to 4.
  - test: `tests/transport/net_test.c` — `test_ipv4_checksum`
- [x] 791-002 (§3.1) The implementation shall set the Internet Header
  Length field to the header length in 32-bit words, with a minimum
  correct value of 5.
  - test: `tests/transport/net_test.c` — `test_ipv4_ihl_min5`
- [x] 791-003 (§3.1) The implementation shall set Total Length to the
  length of the datagram in octets, including the internet header and
  data.
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_tx_roundtrip`
    (the built frame passes `xdpframe_parse`, which requires Total Length
    to equal IHL*4 + UDP Length and to fit the frame)
- [x] 791-005 (§3.1) The implementation shall set the Protocol field to the
  next-level protocol carried in the data portion of the datagram.
  - test: `tests/transport/net_test.c` — `test_ipv4_checksum`
- [x] 791-006 (§3.1) The implementation shall compute the Header Checksum
  as the 16-bit one's complement of the one's complement sum of all 16-bit
  words in the header, with the checksum field itself treated as zero
  during the computation.
  - test: `tests/transport/net_test.c` — `test_ipv4_checksum`
  - test: `tests/transport/net_test.c` — `test_net_datagram_over_link`
- [x] 791-007 (§3.1) The implementation shall recompute and verify the
  Header Checksum at each point that the internet header is processed.
  - test: `tests/transport/srvxdp_test.c` —
    `test_srvxdp_rx_drops_bad_headers` (the AF_XDP receive path,
    `wired_srvxdp_rx_burst` -> `xdpframe_parse`, verifies the checksum over
    the whole IHL*4 header, options included)
  - test: `tests/transport/xdpframe_test.c` —
    `test_xdpframe_rx_rejects_bad_ip_checksum`
  - test: `tests/transport/net_test.c` — `test_ipv4_checksum`,
    `test_net_datagram_over_link` (memlink path, `ipv4_check`)
- [x] 791-011 (§2.3, §3.1 Flags, Fragment Offset) When sending a complete
  datagram, the implementation shall set the reserved flag bit and the MF
  flag to zero and the Fragment Offset to zero.
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_tx_roundtrip`
  - gap: the parser only checks MF and the offset; no test asserts the
    reserved bit, which `ipv4_build` zeroes with the rest of the header.
- [x] 791-012 (§2.3, §3.2 Identification) The implementation shall set
  Identification to a value unique for the source, destination and
  protocol for the time the datagram could be alive in the internet.
  - test: `tests/transport/srvxdp_test.c` —
    `test_srvxdp_send_sets_df_unique_id` (two sends carry different
    Identifications, DF set); `tests/transport/net_test.c` —
    `test_ipv4_df_and_id`
  - evidence: `wired_srvxdp_send` stamps a per-socket counter; DF is always
    set (RFC 9000 §14), so every datagram is atomic and RFC 6864 §4.1 needs
    no cross-socket uniqueness.
- [x] 791-013 (§3.1 Time to Live) If a received datagram's Time to Live is
  zero, then the implementation shall discard it.
  - test: `tests/transport/srvxdp_test.c` — `test_srvxdp_rx_drops_ttl_zero`
  - test: `tests/transport/xdpframe_test.c` —
    `test_xdpframe_rx_rejects_ttl_zero` (TTL 1 still accepted)
- [x] 791-014 (§3.1 Total Length, §3.2 Fragmentation) The implementation
  shall accept datagrams of up to 576 octets that arrive whole.
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_rx_accepts_576`
  - decision: the "or in fragments to be reassembled" half of this
    sentence is a deliberate deviation, listed under Out of scope below.
- [~] 791-015 (§3.1 Total Length) The implementation should send datagrams
  larger than 576 octets only when it has assurance that the destination
  accepts them.
  - evidence: QUIC sends at least 1200-byte datagrams by design (RFC 9000
    §14 requires the path to carry them) and probes larger sizes with
    DPLPMTUD ([RFC 8899](rfc8899.md)); no IPv4-layer test.
- [x] 791-017 (§3.1, §3.2) If a received datagram's Version is not 4, its
  IHL is below 5, or its Total Length does not cover the header plus a UDP
  header or exceeds the received data, then the implementation shall
  reject it.
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_rx_rejects`
  - gap: the Version check (`xdpf_ver_ihl_ok`) has no rejection case.
- [x] 791-008 (§3.1) The implementation shall set the Source Address and
  Destination Address fields to the 32-bit source and destination internet
  addresses.
  - test: `tests/transport/net_test.c` — `test_ipv4_checksum`

## §3.2 Discussion

- [x] 791-009 (§3.2) The implementation shall be conservative in the
  datagrams it sends (well-formed) and liberal in the datagrams it accepts
  (not rejecting technical errors where the meaning is still clear).
  - test: `tests/transport/xdpframe_test.c` —
    `test_xdpframe_rx_accepts_ihl_with_consistent_options`
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_rx_rejects`
  - evidence: the send side (`ipv4_build`,
    `src/transport/io/socket/net/ipv4.c`) is conservative -- it always
    builds the fixed 20-byte IHL=5 header with no options, matching this
    section's "well-formed" half. The receive side
    (`src/transport/io/xdp/xdpframe/xdpframe.c`) previously rejected any
    IHL other than exactly 5, which was stricter than the spec: RFC 791
    3.1 only requires IHL >= 5 (the minimum correct value), not IHL == 5.
    Fixed `xdpf_ip_ok`/`xdpf_ip_len_ok`/`xdpf_udp` to accept IHL >= 5,
    computing the actual header length from the IHL field and locating
    UDP after any IP options rather than at a fixed 20-byte offset; a
    datagram whose IHL claims options but whose Total Length does not
    account for them is still rejected (an actual inconsistency, not a
    liberal-acceptance case). Per `rfc-and-verification-layers.md`, this
    was found and fixed by code review against the RFC text rather than
    by an interop failure, since a self-loopback test (both ends running
    this SDK's own IHL=5-only sender) cannot surface a peer that legally
    sends IHL > 5.
- [x] 791-010 (§1.4, §3.2) If the Header Checksum fails, then the
  implementation shall discard the datagram at once.
  - test: `tests/transport/srvxdp_test.c` —
    `test_srvxdp_rx_drops_bad_headers` (`wired_srvxdp_rx_burst` delivers
    nothing for a frame with one flipped checksum bit, even with the UDP
    checksum opt-out on)

## §3.3 Interfaces

- [~] 791-018 (§3.3) When sending, the implementation shall use a source
  address that is one of the legal addresses for this host.
  - evidence: replies take the received datagram's destination address as
    their source (`tests/transport/xdpframe_test.c` —
    `test_xdpframe_reflect` asserts the swap); there is no explicit check
    against the host's address list.

## Out of scope

Client-only or operator-level requirements this server SDK does not
implement, excluded from the coverage denominator, per this document's
scope note above:

- (§3.1) 791-004: setting the Time to Live field as an upper bound on the
  datagram's lifetime, decremented at each point of processing —
  `ipv4_build` (`src/transport/io/socket/net/ipv4.c`) sets a fixed TTL
  of 64 on send (the receive-side "TTL zero must be destroyed" rule is
  791-013); "decrement at each point of processing" describes
  router/gateway forwarding behavior, which does not apply to this
  endpoint (non-gateway) SDK, consistent with the routing/gateway scope
  exclusion below.
- (§1.4, §2.3, §3.1 Options) The Options mechanism (security, loose/strict
  source routing, record route, timestamp) and the Padding field — control
  functions for gateways and special routing scenarios; wired's AF_XDP path
  sends only the fixed 20-byte header with no options (acting on received
  options is 791-016).
- (§3.1 Total Length, §3.2 Fragmentation) 791-014's reassembly half,
  accepting a datagram that arrives in fragments — deliberate deviation on
  the AF_XDP path. wired sets DF on everything it sends (791-012), and
  RFC 9000 §14 requires QUIC endpoints to set DF on IPv4 and forbids a
  path whose datagram size is below 1200 bytes, so a QUIC datagram is never
  meant to be fragmented (RFC 8900 also recommends that protocols avoid
  IP fragmentation). The BPF filter (`xdpbpf_prog_build`, the
  `0xff3f` flags/offset test) hands every fragment to the kernel stack with
  XDP_PASS, and `xdpframe_parse` rejects MF or a non-zero offset
  (`test_xdpframe_rx_rejects`). The kernel reassembles the fragments but
  delivers them to the port-reservation UDP socket, which the AF_XDP server
  does not read, so they are dropped. The kernel UDP driver (no
  `--ifindex`) receives reassembled datagrams normally.
- (§3.1 Options, §3.2 Options) 791-016, parsing and acting on every option
  a received datagram carries — deliberate deviation on the AF_XDP path.
  The BPF filter reads the QUIC header at fixed IHL=5 offsets and hands
  any datagram with IHL != 5 to the kernel stack with XDP_PASS, where (as
  with fragments) the port-reservation socket absorbs it, so an
  option-bearing datagram never reaches the AF_XDP server. This is stricter
  than RFC 1122 §3.2.1.8, which asks a host to ignore options it does not
  understand and still process the datagram. `xdpframe_parse` itself
  accepts IHL > 5 and skips the options without interpreting them
  (`test_xdpframe_rx_accepts_ihl_with_consistent_options`). The kernel UDP
  driver gets the kernel's own option handling.
- (§1.4, §2.3, §3.2 Fragmentation) Fragmenting datagrams (the procedure a
  gateway uses to split a datagram) — wired never fragments what it sends;
  the destination-side reassembly rule is 791-014 and the sender-side
  flag/offset/Identification rules are 791-011/012.
- (§1.4, §2.3, §2.4) Routing and gateway forwarding of datagrams between
  networks, and the Gateway to Gateway Protocol — router/gateway behavior,
  not an endpoint concern.
- (§3.1 Type of Service) The Type of Service field's precedence, delay,
  throughput, and reliability indications — a hint to intermediate network
  selection that wired's endpoint role does not act on; the field is zeroed
  by `ipv4_build`, which also satisfies "at most two of these three
  indications should be set".
- (§3.3 Interfaces) The example SEND/RECV upper-level interface between IP
  and its user, including the error report on an unsuccessful SEND and the
  ICMP error for an unknown user — a descriptive API shape for
  illustration; ICMP (RFC 792) is not shipped.
- (§2.3 Addressing) Mapping internet addresses to local-net addresses and
  multi-homed hosts — OS/operator address configuration.
- (§3.2 Fragmentation) Breaking fragment data on 8-octet boundaries and
  forwarding 68-octet datagrams unfragmented — fragmenting/forwarding
  module behavior; wired never fragments or forwards.
- (Appendix A, Appendix B) Worked examples and data transmission bit order
  — illustrative and already reflected in the RFC 1071 ledger's checksum
  worked example.
- (Glossary, References) Definitional and bibliographic material —
  non-normative.
