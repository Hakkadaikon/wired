# RFC 6979: DSA と ECDSA の決定的な使用

仕様の本文(`tasks/specs/rfc6979.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。範囲は、SDK が実装している P-256 / SHA-256 の具体化(`src/crypto/asymmetric/ecc/p256sign/`。hlen == qlen == 256 ビット)です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。2026-10 時点の状況です。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 17/21、間接 4、未テスト 0。**

## §3.4 使用上の注意

- [~] 6979-017 (§2.4, §3.4) 候補の k から r = 0 が得られた場合、実装はその k を不適として扱い、ループを続けなければならない。
  - evidence: `test_rfc6979_retry_skips_rejected_candidates` は、適否のコールバックが拒否した候補で `p256sign_k_retry` がループすることを示します。`tests/crypto/p256sign_test.c` —
    `test_p256sign_s_zero_candidate_unsuitable` は、`ps_k_suitable`(`p256sign_sign` が渡すコールバック)を動かして s = 0 の候補を拒否させます。r = 0 の分岐(`ps_compute_r`)にはテストで到達できません。r = (kG).x mod n が 0 になるのは x = 0 か x = n のときだけで、そうした k を見つけるのは離散対数問題だからです。r を偽装する差し替え口(seam)を作っても、テストされるのは署名処理ではなくその差し替え口になります。そのため、これは推論に基づいて `[~]` のままにしています。

## §4 セキュリティに関する考慮事項

- [~] 6979-018 (§4) 実装は、サイドチャネルを通じて秘密鍵が漏れないよう、防御策を使うべきである。
  - evidence: 署名では `p256fixed_mul_g` で kG を計算します。そのテーブル参照と点の選択は、マスクした `p256fixed_cmov` を使います(秘密のウィンドウで分岐も添字づけもしません)。`tests/crypto/p256fixed_test.c` —
    `test_p256fixed_window_patterns`(すべてのウィンドウ位置での d == 0 のマスクつきスキップ)と `test_p256fixed_differential` は、これらのマスクした経路が `ec_mul` と同じ結果になるかを確かめるだけです。サイドチャネル耐性そのものは単体テストでは示せません。

## 対象外

このサーバー SDK が実装しない、クライアント専用または運用者レベルの要件です。カバレッジの分母から外しています。

- (§2.1–2.2, §2.4) 素の DSA の鍵パラメーター、鍵ペア、署名: SDK は DSA を実装していません。
- (§2.4) (r, s) の組の DER エンコーディング: ここでは参考の補足です。TLS 層の `ecdsasig` エンコーダーは別にテストしています。
- (§3.3) k の生成を HMAC_DRBG として述べた別の説明: §3.2 を参考として言い直したものです。
- (§3.5) 根拠: 参考情報です。
- (§2.3.2, §3.2 h) qlen != hlen の場合(長いハッシュの bits2int による切り詰め、複数ブロックの T の連結): 実装している唯一の具体化である P-256/SHA-256 では、決して到達しません。
- (§3.6) 変種の構成(追加のエントロピー入力 k'、別の秘密、別の HMAC ハッシュ): 意図して実装していません。公開されたベクターが当てはまるよう、SDK は基本のアルゴリズムに従います。
- (§4) 秘密鍵の生成・保管・破棄の指針: 運用者の関心事です。
- (A.1) K-163 の詳しい例: SDK が持たない二元体の曲線です。
- (A.2.1–A.2.4, A.2.6–A.2.17) DSA と P-256 以外の曲線のベクター: 実装していません(P-384 の署名は実装しておらず、P-384 は証明書チェーンの検証専用です)。
- (A.2.5) SHA-1/SHA-224/SHA-384/SHA-512 の行: SDK が署名に使うのは ecdsa_secp256r1_sha256 だけです。
- (A.3) サンプルコード: 参考情報です。
