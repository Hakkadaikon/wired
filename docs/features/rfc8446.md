# RFC 8446: トランスポート層セキュリティ(TLS)プロトコル バージョン 1.3

仕様の本文(`tasks/specs/rfc8446.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。
各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。
対象範囲は QUIC(RFC 9001)に組み込まれた TLS 1.3 のサーバー側です。レコード層は QUIC のパケット保護に置き換わるので、§5 と、QUIC が置き換えたほかの仕組みは「対象外」に挙げています。
2026-10 時点の状況です。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 112/139、間接 27、未テスト 0。**

## §4.1.1 暗号のネゴシエーション

- [x] 8446-003 (§2.1, §4.1.1) クライアントが提示した暗号スイートとサーバーがサポートするスイートに重なりがない場合、サーバーはハンドシェイクを中止しなければならない。
  - test: `tests/tls/sdrv_test.c` — `test_sdrv_suite_no_overlap_fails`
  - test: `tests/tls/cipher_test.c` — `test_cipher_select_none`
  - vuln: V-0328, V-0362, V-0363
- [~] 8446-004 (§4.1.1) クライアントの "key_share" 拡張に、サーバーがサポートするグループのシェアが含まれていない場合、サーバーはハンドシェイク鍵を導出してはならず、自身のフライトを送ってもならない。
  - evidence: key_share の走査は不在を報告し(`tests/tls/ext_keyshare_test.c` の `test_ext_key_share_scan_absent`)、フライトの構築はクライアントのシェアを必須とする。中止の経路そのものには専用のテストがない。
- [~] 8446-005 (§4.1.1) PSK を選択するとき、サーバーはクライアントの "psk_key_exchange_modes" 拡張から鍵交換モードを選ばなければならない(この SDK は psk_dhe_ke を必須とする)。
  - evidence: psk_key_exchange_modes のコーデックと psk_dhe_ke の検出はテスト済み(`tests/tls/pskmodes_test.c` の `test_pskmodes_roundtrip`)。PSK を受け入れる経路の中では、この確認をアサートしていない。
- [x] 8446-006 (§4.1.1) 最初の ClientHello に互換性のあるキーシェアが含まれない (EC)DHE グループを選択したとき、サーバーは HelloRetryRequest で応答しなければならない。
  - test: `tests/tls/sdrv_hrr_test.c` — `test_sdrv_hrr_no_x25519_triggers_hrr`
  - gap: HRR が指定するのは常に x25519 だけである。supported_groups に secp256r1 を挙げ(x25519 は挙げず)、P-256 のシェアを持たないクライアントは、secp256r1 で再試行させずに handshake_failure で中止される。
  - vuln: V-0333
- [~] 8446-106 (§4.1.1) クライアントの "supported_groups" のどのグループもサーバーのグループと重ならず、PSK も選択されていない場合、サーバーは "handshake_failure" または "insufficient_security" アラートでハンドシェイクを中止しなければならない。
  - evidence: `sdrv_ch_keyshare_reject`(`sdrv_p256.c`)は、使えるシェアがなく再試行もできないときに handshake_failure (0x0128) を記録する。グループがまったく重ならない ClientHello を流すテストはない。

## 対象外

クライアントだけの要件、運用者側の要件、QUIC が置き換えた要件のうち、このサーバー SDK が実装しないものです。カバレッジの分母から除いています。

- (§5, §5.1–§5.5) TLS のレコード層全体(フレーミング、TLSCiphertext の保護、レコードごとのノンス、レコードのパディング、鍵の使用上限)。QUIC はレコード層を QUIC のパケット保護に置き換える(RFC 9001 §4。AEAD の機密性の上限は代わりに RFC 9001 §6.6 に従って適用する)。
- (§4.1.3, Appendix D.1–D.2, D.5) TLS 1.2 以下のネゴシエーション、ServerHello.random のダウングレード検出用の値、SSL や旧バージョンの扱い。QUIC は TLS 1.3 以降を必須とする(RFC 9001 §4.2)。
- (§4.1.2, §4.1.4, §4.2.1, §4.2.8, §4.2.11) クライアント側での ClientHello の構築と、ServerHello / HelloRetryRequest / selected_identity のクライアント側での確認。クライアントの動作。
- (§4.2.2) ClientHello の間に来る保護されていない change_cipher_spec レコードの無視。レコード層に由来するもので、QUIC の CRYPTO ストリームでは起こりえない。
- (§4.2.3) RSASSA-PSS のソルト / OID / パラメーターの規則と、SHA-1 の旧来の証明書の規則。証明書の発行は運用者の設定であり、サーバーは ecdsa_secp256r1_sha256 でしか署名しない。
- (§4.2.4) certificate_authorities に基づく証明書の選択。サーバーは運用者が設定した 1 つのチェーンを返す。
- (§4.2.4, §4.2.5) CertificateRequest の certificate_authorities と "oid_filters"。任意("MAY")であり、サーバーはどちらも送らない。
- (§4.2.6, §4.6.2) post_handshake_auth とハンドシェイク後のクライアント認証。QUIC はハンドシェイク後の CertificateRequest を禁じており(RFC 9001 §4.4)、この拡張は無視する。
- (§4.2.8.1, §7.4.1) 有限体 Diffie-Hellman のグループと、その公開鍵の検証。FFDHE のグループは提示も選択もしない。
- (§4.2.10) 拒否した早期データを試行復号で読み飛ばすこと、0-RTT レコードに対する bad_record_mac の規則、早期データの再送の規則。QUIC は復号できない 0-RTT パケットを破棄し(RFC 9001 §4.6.2, §5)、再送はクライアントの動作である。
- (§4.4.2) クライアントのチェーンに含まれる余分な証明書や順序の入れ替わった証明書の受け入れ。チェーンはリーフから順に 1 段ずつ検証する。これは、クライアントの役割でサーバーのチェーンに使うのと同じ検証器である。
- (§4.4.2.1) OCSP の status_request と signed_certificate_timestamp の CertificateEntry 拡張。提供していない。
- (§4.4.2, §4.4.2.2) チェーンの順序、鍵用途のビット、クライアントが通知したアルゴリズムだけで署名されたチェーンの選択。返すチェーンは運用者の設定であり、RawPublicKey は提供していない。
- (§4.5) EndOfEarlyData。QUIC は使わず、受信は QUIC のプロトコル違反になる(RFC 9001 §8.3)。
- (§4.6.1) max_early_data_size の適用。QUIC はこれを 0xffffffff に固定し、0-RTT をフロー制御で制限する(RFC 9001 §4.6.1)。
- (§4.6.3, §7.2) TLS の KeyUpdate メッセージと "traffic upd" によるシークレットの更新。QUIC は TLS の KeyUpdate を禁じ、"quic ku" ラベルを使う独自の Key Phase の仕組みで鍵を更新する(RFC 9001 §6)。
- (§6) AlertLevel の扱い。QUIC は AlertLevel を運ばず、CRYPTO_ERROR による CONNECTION_CLOSE はすべて致命的である(RFC 9001 §4.8)。
- (§6.1) close_notify / user_canceled の終了アラート。QUIC のエンドポイントは終了アラートを使わない(RFC 9001 §4.8)。
- (§7.3) [sender]_write_key / [sender]_write_iv のレコード用トラフィック鍵。QUIC はパケット保護の鍵を独自の "quic key" / "quic iv" / "quic hp" ラベルで導出する(RFC 9001 §5.1)。
- (§7.5) 鍵素材のエクスポーター。QUIC はエクスポーターのインターフェースを必要とせず、提供もしていない。
- (§8) リプレイされても安全な早期データだけを送るというクライアント側の義務。クライアントの動作。確率的な(Bloom フィルターによる)リプレイ記録用ストア。提供していない。
- (§9.2) server_name を必須とし、ないときに missing_extension で応答すること。サーバーは SNI を必須としない。
- (§9.3) ミドルボックスのプロトコル不変量。ミドルボックスへの要件であり、サーバーのエンドポイントへの要件ではない。
- (Appendix A.1) クライアントの状態遷移。クライアントの動作(SDK のテスト用クライアントは、この台帳ではなく、それ自身のループバックテストで確かめている)。
- (Appendix C.2, C.5) 証明書の鍵長の下限と、認証なしでの運用。アプリケーションや運用者の方針。
- (Appendix D.4) ミドルボックス互換モード(互換用のセッション ID、ダミーの change_cipher_spec レコード)。QUIC はミドルボックス互換モードを禁じている(RFC 9001 §8.4)。
- (§2.2, Appendix E.1) 外部で用意した PSK と "ext binder" ラベル。SDK が提供するのは再開用の PSK("res binder")だけである。
