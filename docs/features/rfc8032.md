# RFC 8032: エドワーズ曲線デジタル署名アルゴリズム(EdDSA)

仕様の本文(`tasks/specs/rfc8032.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。2026-10 時点の状況です。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 18/20、間接 2、未テスト 0。**

## §8 セキュリティに関する考慮事項

- [~] 8032-019 (§8.1) 署名するとき、実装はどの秘密鍵の値に対しても同じ命令列とメモリアクセスを実行しなければならず、体の演算とスカラー倍算にデータに依存する分岐を持ってはならない。
  - evidence: `ed_ge_scalarmult`(`ed25519_field_ed.c`)は、`ed_fe_cmov` で選択する、256 ステップ固定の double-and-add-always ループです。サイドチャネルで情報が漏れないことは、単体テストでは示せません。
- [~] 8032-020 (§8.7) 実装は、バッファーに受け取ったメッセージ全体に対してだけ署名を検証しなければならず、逐次的な(init-update-finalize の)検証インターフェースを提供してはならない。
  - evidence: `ed25519_verify`(`ed25519.h`)はメッセージ全体を 1 組のポインターと長さで受け取ります。ストリーミングの API はありません。API の形の話で、単体テストで確かめられる振る舞いではありません。

## 対象外

このサーバー SDK が実装しない、クライアント専用または運用者レベルの要件です。カバレッジの分母から外しています。

- (§5.1, §7.2, §7.3) Ed25519ctx と Ed25519ph の変種(dom2 プレフィックス、コンテキスト、事前ハッシュ): 実装していません。TLS 1.3 と X.509 は純粋な Ed25519 だけを使います。
- (§5.2, §7.4, §7.5) Ed448 と Ed448ph: 実装していません。
- (§3) 汎用の EdDSA パラメーターの枠組み: 上で扱った §5.1 の具体化を通してだけ実現しています。
- (§4) PureEdDSA/HashEdDSA の命名: 説明のための記述です。
- (§6) Python による例示: 参考情報です。
- (§8.2-§8.6, §8.8, §8.9) セキュリティに関する考慮事項の指針(シードの乱数源、コンテキストの使い方、プリミティブの選択、事前ハッシュの混在、コファクターつき検証の選択、SHAKE256): 運用・設計の指針です。§8.4 の署名の可変性(malleability)の確認は 8032-013、§8.1 は 8032-019、§8.7 は 8032-020 で扱っています。
