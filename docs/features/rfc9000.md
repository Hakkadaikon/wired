仕様の本文(`tasks/specs/rfc9000.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

## 対象外

このサーバー SDK が実装しない、クライアントだけ、または運用者レベルの要件です。カバレッジの分母から除いています。

- (§2.3, §2.4, §5.3) ストリームと接続の API 操作の一覧。参考としての API の指針で、ワイヤー上の振る舞いではない。
- (§5.1) 長さ 0 の CID の接続を 1 つのアドレス/ポートに複数多重化することの禁止。デプロイ構成の指針。
- (§5.2.1) クライアントのパケット処理(長さ 0 の CID での照合、鍵待ちのパケットのバッファリング、ほかのバージョンのパケットの破棄)。クライアントの振る舞い。
- (§5.2.3) 単純なロードバランサーでの継続性に関する考慮事項。運用者のデプロイの問題。
- (§6.2) 将来のバージョンのネゴシエーションの堅牢性。将来の Standards Track の作業のために予約されている。
- (§9.6.1, §9.6.3) 優先アドレスのアドレスファミリーのクライアントによる選択と、同時に起きるクライアントの移行との相互作用。クライアントの振る舞い。
- (§9.7) IPv6 フローラベルの生成。トランスポート SDK の外にある、ソケットや OS 層の問題。
- (§10.1.1, §10.1.2) 生存確認とアイドルタイムアウトの延期の指針。アプリケーションの方針(keep-alive のヘルパーはあるが、RFC はワイヤー上の振る舞いを規範として定めていない)。
- (§14.2.1, §14.3.3) ICMP PTB メッセージの処理。SDK は意図して、ICMP の経路を持たないプローブ方式の DPLPMTUD だけを提供している。
- (§21.2–§21.14、上の §21.9 を除く) セキュリティに関する考慮事項のうち、デプロイでの緩和策(Slowloris の制限、リクエストフォージェリに対する入口フィルタリング、ステートレスリセットのオラクルに対するクラスターのルーティング、トラフィック解析に対するパディングの方針)。運用者やアプリケーションの問題。
- (§22) IANA のレジストリの方針。実装の振る舞いはない。
- (§7) 暗号ハンドシェイク自体に求められる性質。RFC 9001 と RFC 8446 の台帳で追跡している。
- (§7.2, §7.4.1, §8.1, §8.1.3, §9, §9.6.1, §17.2.1, §17.2.2, §17.2.2.1, §17.2.5, §18.2, §21.5.3) クライアントだけに向けた規則(サーバーのパケットを受けるまでの DCID の再利用、記憶した 0-RTT パラメーター、PTO のプローブ、トークンの使用、Unused ビットの無視、Retry を受け入れる際の細則、サーバー専用のパラメーター、優先アドレスの検証)。クライアントの振る舞い。
- (§6.2, §17.2.5.2, §17.2.5.3) Version Negotiation パケットや Retry パケットの受信(接続の試行の中止、Retry を 1 つだけ受け入れること、Initial の鍵の再導出)。クライアントの振る舞いで、SDK は QUIC クライアントを提供していない。
- (§5.1.1, §9, §9.5, §18.2) 移行を始めるエンドポイントや、自分のローカルアドレスを移すエンドポイントの規則。サーバーはどちらも行わない。
- (§5.1.2) Retire Prior To を更新するペースの調整。サーバーが送る Retire Prior To は常に 0 である。
- (§19.15, §19.16) 長さ 0 の接続 ID を使うエンドポイントの規則。サーバーは常に長さが 0 でない接続 ID を発行する。
- (§10.2.1) 鍵を破棄した closing 状態のエンドポイントの増幅の上限。サーバーは closing 状態の間も鍵を保持する。
- (§13.3, §19.3) 損失と ECN のフィードバックに対する輻輳制御の反応。RFC 9002 の台帳で追跡している。
- (§7.4.1, §19.21, §21.5, §21.12) 新しいトランスポートパラメーター、拡張フレーム、サーバー移行の拡張、将来の QUIC バージョンを定める人向けの規則。仕様策定の指針で、実装の振る舞いはない。
- (§7.5) ハンドシェイク後に破棄した CRYPTO フレームへの確認応答。サーバーがそれを破棄することはない。1-RTT の CRYPTO は接続を閉じ(`test_srvloop_onertt_crypto_latches`)、0-RTT の CRYPTO は PROTOCOL_VIOLATION になり、Handshake の鍵は確定時に破棄される。
- (§9.3.2) 検証に失敗し、最後に検証したアドレスもないときに通知なしで閉じること。サーバーではこの状況は起きない。ハンドシェイクのアドレスが最初に検証済みになるアドレス(srvrun_path_seed)なので、検証に失敗しても戻る先が必ずある(`test_srvrun_path_revert_to_last_validated`)。
- (§9) ハンドシェイクの確定前に移行を始めることと、disable_active_migration を送ったあとのパケットの扱い。サーバーは移行を始めず(上の移行の項目を参照)、disable_active_migration も送らない(それを書き込むエンコーダーはない)。
