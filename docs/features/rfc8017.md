# RFC 8017: PKCS #1: RSA 暗号仕様バージョン 2.2

仕様の本文(`tasks/specs/rfc8017.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。この台帳の範囲は、この SDK が実装するものに限ります。RSASSA-PKCS1-v1_5 の署名検証(§8.2/§9.2)と RSASSA-PSS/MGF1 の署名検証(§8.1/§9.1/付録 B.2.1)で、どちらも証明書チェーンまたは CertificateVerify の RSA 署名を検証するためだけに使います。暗号化スキーム(§7、RSAES-*)、鍵生成、RSA 署名の*生成*(RSASP1、§8.1.1/§8.2.1)は `src/crypto/` にはなく(grep で確認済み)、対象外にまとめています。2026-10 時点の状況です。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 18/23、間接 5、未テスト 0。**

## §3.1 RSA 公開鍵

- [x] 8017-001 (§3.1) 実装は RSA 公開鍵を、モジュラスと公開指数の組 (n, e) として表さなければならない。どちらも正の整数である。
  - test: `tests/crypto/rsa_pubkey_test.c` — `test_rsa_pubkey_extract`
- [x] 8017-002 (§3.1) RSA 公開指数 e は、3 から n - 1 までの整数でなければならない。
  - test: `tests/crypto/rsa_pubkey_test.c` — `test_rsa_pubkey_e_min`
  - test: `tests/crypto/rsa_pubkey_test.c` — `test_rsa_pubkey_e_max`
- [~] 8017-003 (§3.1) RSA モジュラス n は、相異なる奇素数の積でなければならない。
  - evidence: `x509_rsa_pubkey` は必要条件として偶数のモジュラスを拒否します(`tests/crypto/rsa_pubkey_test.c test_rsa_pubkey_even_n`)。因数が素数であることと相異なることは検証していません(公開鍵だけからは検証できません)。素因数分解の専用テストはなく、鍵の検証は実装のスキーム操作の範囲外であるという §6 の明示的な注記とも合っています。

## §4 データ変換プリミティブ(I2OSP / OS2IP)

- [x] 8017-004 (§4.1, §4.2) 実装は、非負整数と固定長のビッグエンディアンのオクテット文字列との間を、最上位のオクテットを先頭にして変換(I2OSP/OS2IP)しなければならない。
  - test: `tests/crypto/bignum_test.c` — `test_bn_be_roundtrip`
  - evidence: `bn_from_be`/`bn_to_be`(`src/crypto/asymmetric/bignum/bignum.h`)が OS2IP/I2OSP を実装しており、すべての RSA 検証テストで端から端まで動きます(署名とモジュラスは `bn_from_be` で読み、復元したメッセージは `bn_to_be` で書き出します)。

## §5.2.2 RSAVP1(RSA 検証プリミティブ)

- [x] 8017-005 (§5.2.2) 署名代表 s が 0 から n - 1 の間にない場合、実装はそれ以上計算せずに "signature representative out of range" として拒否しなければならない。

- [x] 8017-006 (§5.2.2) 実装は、メッセージ代表を m = s^e mod n として計算しなければならない。
  - test: `tests/crypto/rsa_verify_test.c` — `test_rsa_pkcs1_valid`
  - test: `tests/crypto/rsa_pss_test.c` — `test_rsa_pss_valid`

## §9.1 EMSA-PSS

- [~] 8017-010 (§9.1.2 step 3) emLen < hLen + sLen + 2 の場合、実装は "inconsistent" を出力しなければならない。
  - evidence: `pss_sizes_bad`(`src/crypto/asymmetric/rsa/pss.c`)がこの下限を実装していますが、PSS のテストはすべて 2048〜4096 ビットのモジュラスを使います。`test_rsa_pss_sizes`(以前のリンク先)は署名とハッシュを短くするだけなので、この分岐に届くテストはありません。
- [~] 8017-011 (§9.1.2 step 4) EM の最も右のオクテットが 0xbc でない場合、実装は "inconsistent" を出力しなければならない。
  - evidence: `src/crypto/asymmetric/rsa/pss.c` の `pss_prefix_bad` はほかのどの手順よりも前に `em.p[em.n - 1] != 0xbc` を検査します。有効な署名のすべてのテスト(正しい PSS の EM は常に 0xbc で終わる)と、ほかのフィールドを改変しても同じ検査を通る `test_rsa_pss_tampered_sig`/`test_rsa_pss_wrong_hash` で暗黙に動きます。末尾のバイトだけを反転させるテストはありません。
- [x] 8017-012 (§9.1.2 steps 5-9) 実装は、EM を maskedDB と H に分け、dbMask = MGF(H, emLen-hLen-1) を生成し、DB = maskedDB XOR dbMask でマスクを外し、DB の左端の 8emLen-emBits ビットをゼロにしなければならない。
  - test: `tests/crypto/rsa_pss_test.c` — `test_rsa_pss_valid`
  - test: `tests/crypto/mgf1_test.c` — `test_mgf1_kat`
- [~] 8017-013 (§9.1.2 step 6) maskedDB の最も左のオクテットの左端 8emLen-emBits ビットがすべてゼロではない場合、実装は "inconsistent" を出力しなければならない。
  - evidence: `pss_top_bits_clear`(`src/crypto/asymmetric/rsa/pss.c`)がこのマスクと比較をそのまま実装しています。破損した EM からしか到達できず、それを直接組み立てるテストはありません。EMSA-PSS のデコードのたびに間接的に通りますが、狙ったテストではありません。
- [~] 8017-014 (§9.1.2 step 10) DB の左端の emLen-hLen-sLen-2 オクテットがゼロでない場合、またはそれに続くオクテットが 0x01 でない場合、実装は "inconsistent" を出力しなければならない。
  - evidence: `pss_padding_ok` が PS/0x01 の検査を実装しています。改ざんした署名のテストは署名の 1 バイトを反転させ、それが(RSA のべき乗を通して)復元した EM を乱し、この検査か H'=H の検査で検出されますが、どちらの検査が働いたかは切り分けていません。
- [x] 8017-015 (§9.1.2 steps 11-14) 実装は、H' = Hash(0x00*8 || mHash || salt) を計算し直し、H' = H のとき、かつそのときに限り "consistent" を出力しなければならない。
  - test: `tests/crypto/rsa_pss_test.c` — `test_rsa_pss_valid`
  - test: `tests/crypto/rsa_pss_test.c` — `test_rsa_pss_wrong_hash`

## 対象外

暗号化スキーム、鍵生成、署名の*生成*です。いずれも `src/crypto/` に実装がなく(grep でないことを確認済み)、カバレッジの分母から除いています。

- (§3.2) RSA 秘密鍵の表現(両方の形式)と CRT 係数。`src/` に秘密鍵の型はなく、この SDK は公開鍵で署名を検証するだけです。
- (§5.1) RSAEP / RSADP(暗号化・復号のプリミティブ)。RSA の暗号化も復号も提供していません。
- (§5.2.1) RSASP1(署名プリミティブ)。RSA 署名の*生成*はありません。SDK 自身の証明書と CertificateVerify は ECDSA/Ed25519 を使い([セキュリティ](../security/README.md)を参照)、RSA はピアや CA が発行したものの検証だけに使います。
- (§6) スキームの概要にある暗号化スキーム全般の枠組みと、署名と暗号化を組み合わせるときの「スキームをまたいで鍵ペアを再利用しない」という推奨。暗号化スキームがないので当てはまりません。
- (§7, §7.1, §7.2) 暗号化スキーム: RSAES-OAEP と RSAES-PKCS1-v1_5(とそのエンコード方式 EME-OAEP/EME-PKCS1-v1_5)。提供していません。
- (§10) セキュリティに関する考慮事項。文書全体で論じた考慮事項への案内で、それ単独で対応できるものではありません。
- (付録 A.1.2, A.2.*) RSA 秘密鍵の ASN.1 構文と、RSAPublicKey(A.1.1。`x509_rsa_pubkey` で扱う)以外の PKCS #1 のアルゴリズム識別子。秘密鍵の ASN.1 解析は提供していません。
- (付録 B.1) MD2、MD5、SHA-1、SHA-224、SHA-512/224、SHA-512/256 のハッシュ関数の OID と DER 接頭辞。この SDK の DigestInfo の表(`rsa_di[]`)は、SDK のほかの部分が実装するハッシュ関数(FIPS 180-4)に合わせて SHA-256/384/512 だけをサポートします。古いハッシュやサポートしないハッシュは、追加のエンコードとして実装するのではなく、`di_prefix` が 0 を返すことで拒否します。
- (付録 A.2.3) RSASSA-PSS-params の AlgorithmIdentifier。RSASSA-PSS は SHA-256/MGF1/salt 32 に固定した TLS の CertificateVerify だけで使います。id-RSASSA-PSS の証明書署名の OID は許可リストで拒否します。
- (付録 B.1) 「NULL パラメーターのあるハッシュ AlgorithmIdentifier もないものも受け入れる」こと。PKCS#1 v1.5 の DigestInfo の外ではハッシュの AlgorithmIdentifier を解析せず、その DigestInfo では同じ付録の例外規定が NULL を求めています。
- (付録 A.1) rsaEncryption のパラメーターは NULL でなければならない(SHALL)。生成側のエンコード規則です。`x509_rsa_pubkey` は鍵の BIT STRING だけを読みます。
- (付録 B.2.2) MGF2(複数のハッシュを使うマスク生成関数)。TLS 1.3 の rsa_pss_rsae_sha256 に合わせて、MGF1-SHA-256 だけを提供しています。
