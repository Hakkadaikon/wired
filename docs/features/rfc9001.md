# RFC 9001: TLS による QUIC の保護

仕様の本文(`tasks/specs/rfc9001.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。
各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 72/78、間接 6、未テスト 0。**

## §4 TLS メッセージの運搬

- [x] 9001-001 (§4) サーバーは TLS ハンドシェイクデータを CRYPTO フレームで運ばなければならない。各フレームはオフセットと長さで識別される連続したブロックとする。
  - test: `tests/transport/crypto_stream_test.c` — `test_emit_splits`
  - test: `tests/transport/crecv_collect_test.c` — `test_crecv_single_offset0`
- [~] 9001-002 (§4) CRYPTO データを再送するとき、サーバーはそのデータを最初に送ったときと同じ鍵(暗号化レベル)を使わなければならない。
  - evidence: 送信履歴と再送の状態はパケット番号スペースごとに保持している(`tests/transport/pnspaces_sent_test.c` — `test_pnspaces_sent_ack_stays_in_space`)。そのため CRYPTO の再送は元のスペースで組み立て直される。レベルをまたぐ専用のテストはない。
- [x] 9001-003 (§4) 種類の異なるパケットを送る必要があるとき、サーバーはそれらを同じ UDP データグラムに結合するべきである。
  - test: `tests/app/srvloop_test.c` — `test_srvloop_confirm_and_200_coalesce`
- [x] 9001-004 (§4, Table 1) サーバーは各暗号化レベルを、対応するパケット種別とパケット番号スペースに対応づけなければならない(Initial、0-RTT/1-RTT → アプリケーションデータ、Handshake)。
  - test: `tests/transport/ptype_test.c` — `test_ptype_each`
  - test: `tests/transport/pnspace_test.c` — `test_pnspace_independent`
  - test: `tests/app/srvloop_test.c` —
    `test_srvloop_recv_zerortt_opens_with_early_keys`

## 対象外

クライアント専用、または運用者レベルの要件で、このサーバー SDK が実装しないもの。カバレッジの分母から除外しています。

- (§4.1.2) HANDSHAKE_DONE の受信、または 1-RTT の確認応答によるクライアント側のハンドシェイクの確認。クライアントの振る舞い。
- (§4.1.4) 非同期の TLS 処理が終わるまでの間も応答を続けること。TLS スタックはプロセス内で同期的に動くので、待ちの状態はない。
- (§4.2) "Clients MUST NOT offer TLS versions older than 1.3"。クライアントの振る舞い。
- (§4.3) ClientHello のサイズ管理(Retry を条件とした部分的な ClientHello のバッファリング、チケットサイズの最小化)。MAY レベルの運用上の指針。
- (§4.4) クライアントによるサーバーの身元の認証。クライアントの振る舞い。
- (§4.4) ハンドシェイク後の CertificateRequest メッセージをクライアントが拒否すること。クライアントの振る舞い。
- (§4.5) "Clients SHOULD NOT reuse tickets"。クライアントの振る舞い。
- (§4.6.1) max_early_data_size が 0xffffffff でない NewSessionTicket をクライアントが拒否すること。クライアントの振る舞い。
- (§4.6.2) 0-RTT が拒否されたときのクライアントのストリーム状態のリセットと、拒否後の 0-RTT の確認応答をエラーとして扱うこと。クライアントの振る舞い。
- (§4.9.1) Handshake パケットを初めて送信するときにクライアントが Initial 鍵を破棄すること。クライアントの振る舞い(サーバー側は 9001-024)。
- (§4.9.3) 1-RTT 鍵をインストールしたときにクライアントが 0-RTT 鍵を破棄すること。クライアントの振る舞い。
- (§5.1) "Other versions of TLS MUST provide a similar function"。将来の TLS バージョンに対する要件で、実装に対するものではない。
- (§5.2, §9.6) 将来の QUIC バージョン向けの新しいソルトと鍵導出ラベルの定義。バージョンの設計者向けの指針。v2 での具体化は RFC 9369 の台帳で扱う。
- (§5.6) クライアント側の 0-RTT の使用制限(求められない限りアプリケーションデータを送らない、拒否されたら送信をやめる、受信した 0-RTT を決して復号しない、1-RTT 鍵のインストール後は使わない)。クライアントの振る舞い。
- (§5.7) クライアントによる 1-RTT 処理の延期と、Finished の結合に関する助言。クライアントの振る舞い。
- (§6.6) "Any TLS cipher suite specified for use with QUIC MUST define AEAD limits"。将来の仕様に対する要件。
- (§8.1) ALPN のネゴシエーションに失敗したときにクライアントがエラー 0x0178 を使うこと。クライアントの振る舞い。
- (§8.2) quic_transport_parameters が QUIC の外で現れたときに unsupported_extension を送ること。この SDK の TLS は QUIC の外では動かない。
- (§8.3) "Clients MUST NOT send the EndOfEarlyData message"。クライアントの振る舞い。
- (§8.4) クライアントが TLS 1.3 のミドルボックス互換モードを要求することの禁止。クライアントの振る舞い。
- (§5.6, §9.2) アプリケーションプロトコルの 0-RTT の使用プロファイルとリプレイの分析、および QUIC 拡張に課される同様の義務。仕様レベルの要件(HTTP/3 のプロファイルは RFC 9114 が扱う)。
- (§9.3) ClientHello を含むデータグラムを最小サイズまでパディングすること。クライアントの振る舞い。
- (§9.4) "Future header protection variants MUST use a PRF"。将来の仕様に対する要件。
- (§10) quic_transport_parameters のコードポイントの IANA 登録。登録の手続きで、実装ではない。
