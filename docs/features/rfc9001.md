# RFC 9001 — Using TLS to Secure QUIC

EARS requirement ledger extracted from the spec text
(`tasks/specs/rfc9001.txt`, not in git). Each requirement carries the test
that demonstrates it; an unchecked box with no test line is an open gap.
Status as of 2026-10.

Legend:

- `[x]` — demonstrated by the referenced test
- `[~]` — exercised indirectly (evidence line explains how; no dedicated test)
- `[ ]` — not demonstrated by any test yet

**Coverage: 66/78 tested, 12 indirect, 0 untested.**

  - test: `tests/transport/antiamp_test.c` — `test_antiamp_budget`
  - test: `tests/transport/dosmitigate_test.c` — `test_dosmitigate`
- [x] 9001-067 (§9.5) The implementation shall apply header protection
  removal, packet number recovery, and packet protection removal together
  without timing side channels.
  - test: `tests/transport/vpn_open_test.c` — `test_vpn_tamper`
  - test: `tests/transport/vpn_open_test.c` — `test_vpn_roundtrip_lengths`
  - evidence: `vpn_open`/`vpn_open_suite`
    (`src/transport/packet/build/vpn/vpn_open.c`) run header protection
    removal (`remove_hp`/`remove_hp_suite`), packet number recovery
    (`read_pn` inside the same call), and packet protection removal
    (`vpn_aead_open`/`vpn_aead_open_suite`) as one unconditional sequence:
    the only branch before the AEAD open is `region_ok`, a check of the
    caller-supplied `length`/`pn_off` against the buffer's own size (a
    structural bound on the received bytes, independent of key material or
    Key Phase validity) -- not a data- or key-dependent early exit. HP
    removal and pn recovery therefore always run before the AEAD result is
    known, and an AEAD failure (`test_vpn_tamper`) never skips them:
    `test_vpn_tamper` asserts the unmasked byte0/pn bytes read back exactly
    as `vpn_open` left them despite the AEAD open returning 0. This
    was previously investigated together with 9001-053 below and confirmed
    as already satisfied by this existing pipeline; 9001-053's remaining
    gap is upstream of this function (see its evidence).
- [x] 9001-077 (§9.5) The server shall construct and protect packet payloads
  and packet numbers without side channels that reveal the packet number or
  its encoded size.
  - test: `tests/app/srvloop_test.c` — `test_srvloop_send_pn_fixed_four_bytes`
  - evidence: the encoded size is fixed at 4 bytes for every packet
    number, so neither the header protection mask length nor the payload
    offset depends on it; the nonce is the IV XOR the pn (protect_nonce).

## Out of scope

Client-only or operator-level requirements this server SDK does not
implement, excluded from the coverage denominator:

- (§4.1.2) Client confirmation of the handshake on HANDSHAKE_DONE receipt or
  a 1-RTT acknowledgment — client behavior.
- (§4.1.4) Continuing to respond while asynchronous TLS processing completes
  — the TLS stack runs synchronously in-process; no waiting state exists.
- (§4.2) "Clients MUST NOT offer TLS versions older than 1.3" — client
  behavior.
- (§4.3) ClientHello size management (Retry-gated buffering of partial
  ClientHellos, minimizing ticket size) — MAY-level operational guidance.
- (§4.4) Client authentication of the server identity — client behavior.
- (§4.4) Client rejection of post-handshake CertificateRequest messages —
  client behavior.
- (§4.5) "Clients SHOULD NOT reuse tickets" — client behavior.
- (§4.6.1) Client rejection of a NewSessionTicket whose max_early_data_size
  is not 0xffffffff — client behavior.
- (§4.6.2) Client stream-state reset on 0-RTT rejection and treating a 0-RTT
  acknowledgment after rejection as an error — client behavior.
- (§4.9.1) Client discarding Initial keys when first sending a Handshake
  packet — client behavior (the server side is 9001-024).
- (§4.9.3) Client discarding 0-RTT keys upon installing 1-RTT keys — client
  behavior.
- (§5.1) "Other versions of TLS MUST provide a similar function" —
  requirement on future TLS versions, not an implementation.
- (§5.2, §9.6) Defining new salts and key-derivation labels for future QUIC
  versions — guidance to version designers; the v2 instantiation is covered
  by the RFC 9369 ledger.
- (§5.6) Client-side 0-RTT usage restrictions (no application data unless
  requested, stop sending on rejection, never decrypt received 0-RTT, none
  after 1-RTT keys are installed) — client behavior.
- (§5.7) Client deferral of 1-RTT processing and Finished-coalescing advice —
  client behavior.
- (§6.6) "Any TLS cipher suite specified for use with QUIC MUST define AEAD
  limits" — requirement on future specifications.
- (§8.1) Client use of error 0x0178 when ALPN negotiation fails — client
  behavior.
- (§8.2) Sending unsupported_extension when quic_transport_parameters appears
  outside QUIC — this SDK's TLS never runs outside QUIC.
- (§8.3) "Clients MUST NOT send the EndOfEarlyData message" — client
  behavior.
- (§8.4) Client prohibition on requesting TLS 1.3 middlebox compatibility
  mode — client behavior.
- (§5.6, §9.2) Application-protocol 0-RTT usage profiles and replay
  analyses, and the matching duty on QUIC extensions — specification-level
  requirements (HTTP/3's profile belongs to RFC 9114).
- (§9.3) Padding the ClientHello's datagram to the minimum size — client
  behavior.
- (§9.4) "Future header protection variants MUST use a PRF" — requirement on
  future specifications.
- (§10) IANA registration of the quic_transport_parameters codepoint —
  registry process, not implementation.
