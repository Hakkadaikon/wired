# RFC 9204: QPACK: HTTP/3 のフィールド圧縮

仕様の本文(`tasks/specs/rfc9204.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。サーバーは `SETTINGS_QPACK_MAX_TABLE_CAPACITY 2016` と `SETTINGS_QPACK_BLOCKED_STREAMS 0` を通知します。相手の動的テーブルは保持します(エンコーダーストリームの内容を適用し、Section Acknowledgment、Stream Cancellation、Insert Count Increment をデコーダーストリームで送ります)が、ストリームをブロックすることはありません。サーバー自身のエンコーダーのテーブルは min(相手の SETTINGS_QPACK_MAX_TABLE_CAPACITY, 2016) の容量を取り、静的テーブルに一致しない `:status` に使います。確認応答を受けたエントリだけを参照するので、そのセクションもブロックしません。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)、またはこの SDK 自身のテストだけで固定(ワイヤー上の動作は第三者の実装との相互接続性の確認待ち)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 57/67、間接 9、未テスト 1。**

## 対象外

このサーバー SDK が実装しない、クライアントだけの要件や運用者レベルの要件です。カバレッジの分母には含めません。

- (§3.2.2, §4.3.1) 容量を減らすことで、追い出せないエントリを追い出さないこと。エンコーダーは容量を一度だけ設定し、減らさない。
- (§2.1.1.1) 禁止された挿入を避けるための draining index の経験則。エンコーダーの選択に関する指針で、提供していない。
- (§2.1.2) ブロックのおそれがあるストリームに対するエンコーダーの予算。SDK のエンコーダーは確認応答を受けたエントリだけを参照するので、どのセクションもブロックしない(9204-067)。
- (§2.1.3) フロー制御のクレジットが足りるまで命令を送らずにおくこと。命令はクレジットにかかわらずエンコーダーストリームの送信リングに積む。リングが満杯なら挿入はせず、そのフィールドはリテラルとして送り、後のレスポンスで挿入をやり直す。
- (§2.2.1) ブロックされたストリームのデータをフロー制御ウィンドウ内に保持し、Insert Count が増えたらブロックを解除すること。デコーダーはブロックしない(SETTINGS_QPACK_BLOCKED_STREAMS 0)。
- (§2.2.2.3) Insert Count Increment を出すタイミングとまとめ方(出すこと自体は 9204-062)。1 ステップに 1 回の増分で、まだ確認応答していないすべての挿入を扱い、それ以上の調整はしない。
- (§3.2.3) 0-RTT のクライアントが、変更または省略された SETTINGS_QPACK_MAX_TABLE_CAPACITY を QPACK_DECODER_STREAM_ERROR として扱うこと。クライアントだけの要件。
- (§4.5.4, §7.1.3) 仲介者での never-indexed リテラルの再エンコードの規則。wired はオリジンサーバーで、仲介者ではない。
- (§7.1) 動的テーブルの探り(CRIME 型)への対策。テーブルを共有するデプロイ向けの設計指針で、サーバーは相手が渡した値をインデックスに登録しない。
- (§7.2) 静的な Huffman 符号による情報漏えいの議論。参考情報。
- (§7.3) メモリ消費の調整に関する指針。運用者向けの指針(反映しているのは、容量 0 のデフォルトでデコーダーの状態を抑えている点だけ)。
