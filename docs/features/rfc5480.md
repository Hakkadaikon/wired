# RFC 5480: 楕円曲線暗号 (ECC) のサブジェクト公開鍵情報

仕様の本文(`tasks/specs/rfc5480.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。範囲は、この TLS サーバー SDK の証明書スタックが読み込むものと生成するものです。具体的には P-256 と P-384 の EC SubjectPublicKeyInfo の解析とエンコード、P-521 の解析(2026-10-10)です。2026-10 時点の状況です。

- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

## 対象外

このサーバー SDK が実装しない曲線、アルゴリズム、CA ポリシーの意味論です。カバレッジの分母から除いています。

- (§2.1.1) id-ecDH/id-ecMQV を認識したあとに、サブジェクト公開鍵を実際に ECDH または ECMQV アルゴリズムに制限すること。SDK は両方の OID を認識し、その ECParameters と keyUsage の要件を検証する(5480-004/005/011/012/020)が、証明書スタック自体には ECDH/ECMQV の鍵合意のコードパスがない。実際の鍵操作で生成し読み込むのは id-ecPublicKey(制限なしで、ECDSA で使う)だけである。
- (§2.1.1.1) secp256r1/secp384r1/secp521r1 以外の 12 個の名前付き曲線(secp192r1、sect163k1、sect163r2、secp224r1、sect233k1、sect233r1、sect283k1、sect283r1、sect409k1、sect409r1、sect571k1、sect571r1)。SDK が実装する体と点の演算は、P-256、P-384、P-521(検証だけ)のものに限られる。
- (§3) id-ecPublicKey の CA 証明書と EE 証明書で許される keyUsage の組み合わせと、keyCertSign と並ぶ keyAgreement についての SHOULD NOT。CA の発行の指針(すべて発行者に対する MAY/SHOULD)。
- (§4) 鍵長、ハッシュアルゴリズム、曲線の選び方を対応づけるセキュリティ強度の推奨。運用者や CA のポリシーの指針で、実装できるコードの動作ではない。
- (§5) PER (Packed Encoding Rules) でのエンコードの考慮事項。SDK は DER だけを使い、PER は X.509 の対象外である。
- 付録 A の ASN.1 モジュールにある、網羅のために載せた MD2、MD5、SHA-1、DSA、(EC でない)Diffie-Hellman のアルゴリズムの項目。ECC ではなく、この SDK の証明書スタックも実装していない。
