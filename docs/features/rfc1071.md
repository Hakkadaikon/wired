# RFC 1071: インターネットチェックサムの計算

仕様の本文(`tasks/specs/rfc1071.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 4/5、間接 1、未テスト 0。**

wired がこのチェックサムを自前で計算するのは AF_XDP 経路だけです(`src/transport/io/socket/net/checksum.c`。IPv4 と UDP のフレーミングで共用)。相互接続性の試験ではカーネルの UDP ソケットを使っており、チェックサムはカーネルが計算します。そのため、このアルゴリズムは単体テストで確かめていますが、相互接続性の試験では確かめていません。

## §1 はじめに

- [x] 1071-001 (§1) 実装はチェックサムの対象となる隣り合うオクテットを組にして 16 ビット整数とし、それらの整数の 1 の補数和を求めなければならない。
  - test: `tests/transport/net_test.c` — `test_checksum_rfc1071`
- [x] 1071-002 (§1) チェックサムを生成するとき、実装はチェックサムフィールドを 0 にし、対象のオクテットについて 16 ビットの 1 の補数和を求め、その和の 1 の補数をチェックサムフィールドに入れなければならない。
  - test: `tests/transport/net_test.c` — `test_ipv4_checksum`
  - test: `tests/transport/net_test.c` — `test_udp_checksum`
- [x] 1071-003 (§1) チェックサムを検査するとき、実装はチェックサムフィールドを含む同じオクテットについて 1 の補数和を求めなければならず、検査は結果のビットがすべて 1 の場合にだけ成功しなければならない。
  - test: `tests/transport/net_test.c` — `test_ipv4_checksum`
  - test: `tests/transport/net_test.c` — `test_udp_checksum`
- [x] 1071-004 (§1) 2 の補数の計算機では、実装は最上位ビットからのあふれを最下位ビットへ足し戻して(end-around carry)、1 の補数和を求めなければならない。
  - test: `tests/transport/net_test.c` — `test_checksum_rfc1071` (§3 の例の和は 0x2ddf0 になる。end-around carry を行ったときだけ 0xddf2 と、固定したチェックサム 0x220d が得られる)
- [~] 1071-005 (§1) 実装は和を求める前に、必要ならオクテット列の末尾に 0 のオクテットを 1 つ足して、長さを 2 オクテットの倍数にしなければならない。
  - evidence: `cksum_accum` は奇数長のときに余る末尾の 1 バイトを 16 ビット語の上位側として足す(`src/transport/io/socket/net/checksum.c`)。つまり [Z,0] として扱う。
    `test_checksum_rfc1071` の入力は偶数長(8 バイト)で、`test_net_datagram_build` の奇数長(13 バイト)の UDP データグラムは、それを組み立てたのと同じコードでしか検査していない。そのため、奇数長について固定した期待値はない。

## 対象外

このサーバー SDK が実装しない、クライアント専用または運用者向けの要件です。カバレッジの分母から除きます。

- (§2) 和を求める順序の交換則と結合則、バイト順に依存しないこと、並列に和を求めることを、特定の CPU の語長で計算を速める方法として述べた部分。実装技法の指針であり、SDK の API の境界から見て単純なアルゴリズムと区別できる振る舞いではない。
- (§2) 桁上げの後回し、ループ展開、データコピーとの組み合わせ、差分更新といった性能のための技法。最適化の指針であり、規範的な要件ではない。
- (§3) バイトごと、通常の順序、入れ替えた順序で和を求める数値の計算例。説明のための例にすぎない。§1/§3 にある RFC 自身の計算例は、上のテストベクターとしてすでに使っている。
- (§4) C、Motorola 68020、Cray、IBM 370 アセンブリでの実装例。ほかのアーキテクチャー向けの参照実装であり、この SDK への要件ではない。
- (Appendix / IEN 45) William Plummer の "TCP Checksum Function Design" による、チェックサムの性質(P1-P7)、積符号、CRC 方式、外部処理装置での処理の議論。採用しなかった設計の経緯と代替案であり、要件ではない。
