# RFC 9369: QUIC バージョン 2

仕様の本文(`tasks/specs/rfc9369.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。2026-10 時点の状況です。

範囲についての注記: サーバーは互換性のあるバージョンネゴシエーション(RFC 9368 §2.3)を行います。version_information で v2 を優先する v1 の Initial パケットには v2 で応答するので、§4.1 のバージョン切り替えの要件は実際の切り替えに当てはまります。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 23/29、間接 6、未テスト 0。**

## §3 QUIC バージョン 1 との違い

- [~] 9369-001 (§3) この節に挙げる違いを除き、サーバーはバージョン 2 の接続に対して QUIC バージョン 1 の仕様(RFC 9000、RFC 9001、RFC 9002)を実装しなければならない。
  - evidence: v2 の受け入れ経路は RFC 9000/9001/9002 の台帳が扱うのと同じ処理を通ります(`tests/app/srvboot_version_test.c` — `test_srvboot_accept_v2_initial` が v2 の Initial パケットを共通のコード経路で最後まで処理します)。それらのテスト群を v2 で別に流し直してはいません。

## §7 適用可能性

- [~] 9369-022 (§7) サーバーは、QUIC バージョン 1 向けに定められた ALPN のコードポイント("h3" など)がバージョン 2 の上で動くことを許さなければならない。
  - evidence: `sdrv_negotiate_alpn` は、設定した生の ID、h3、hq-interop の中から QUIC バージョンを見ずに選びます。そのどれも v1 と v2 の両方で定義されています(RFC 9369 §7)。サーバーは v2 の Initial パケットを受け入れます(`test_srvboot_accept_v2_initial`)。v2 の上で ALPN を最後までネゴシエートするテストはありません。

## 対象外

このサーバー SDK が実装しない、クライアントだけの要件と運用者レベルの要件です。カバレッジの分母から除いています。

- (§1, §6) 硬直化(ossification)の理由づけと、ミドルボックスの振る舞いについての議論。参考情報です。
- (§4) Alt-Svc による発見についての考慮事項。HTTP クライアントと運用者の関心事です。
- (§4.1) クライアント側の規則: ほかのバージョンの Retry パケットを無視すること、トークンを持つ Initial パケットでバージョンを切り替えないこと、ネゴシエートしたバージョンをロングヘッダーの Version フィールドから知ること、以降の Initial パケットをそのバージョンで送ること、ネゴシエートしたバージョンでは 0-RTT を決して送らないこと。クライアントの動作です。
- (§4.1) クライアントのバージョン切り替えを検出するために、Retry トークンに QUIC バージョンをエンコードすること。任意(MAY)で、実装していません。
- (§5) バージョンをまたいでチケットやトークンを使うことのクライアントへの禁止。クライアントの動作です。
- (§6) バージョン 2 で接続を始めるというクライアントの選択。クライアントの動作です。
- (§8) セキュリティに関する考慮事項。参考情報で、バージョン 1 に対する新しい要件はありません。
- (§9) IANA への登録(0x6b3343cf は恒久、0x709a50c4 は暫定)。登録の手続きで、実装の対象ではありません。
