# RFC 9369 — QUIC Version 2

EARS requirement ledger extracted from the spec text
(`tasks/specs/rfc9369.txt`, not in git). Each requirement carries the test
that demonstrates it; an unchecked box with no test line is an open gap.
Status as of 2026-10.

Scope note: the server performs compatible version negotiation (RFC 9368
§2.3): a v1 Initial whose version_information prefers v2 is answered in
v2, so the §4.1 switching requirements apply to real switches.

Legend:

- `[x]` — demonstrated by the referenced test
- `[~]` — exercised indirectly (evidence line explains how; no dedicated test)
- `[ ]` — not demonstrated by any test yet

**Coverage: 23/29 tested, 6 indirect, 0 untested.**

## §3 Differences with QUIC Version 1

- [~] 9369-001 (§3) Except for the differences listed in this section, the
  server shall implement the QUIC version 1 specification (RFC 9000,
  RFC 9001, RFC 9002) for version 2 connections.
  - evidence: the v2 accept path runs through the same machinery the
    RFC 9000/9001/9002 ledgers cover
    (`tests/app/srvboot_version_test.c` —
    `test_srvboot_accept_v2_initial` drives a v2 Initial end to end
    through the shared code path); no separate v2 re-run of those suites.

## §3.2 Long Header Packet Types

- [x] 9369-003 (§3.2) The implementation shall map version 2 long-header
  Type field values as Initial=0b01, 0-RTT=0b10, Handshake=0b11,
  Retry=0b00, round-tripping against the v1 mapping.
  - test: `tests/transport/v2types_test.c` — `test_v2_wire_values`
  - test: `tests/transport/v2types_test.c` — `test_roundtrip`
- [x] 9369-004 (§3.2) When parsing a long header, the server shall decode
  the type bits under the mapping selected by the packet's Version field,
  never under the other version's mapping.
  - test: `tests/app/srvboot_version_test.c` — `test_is_initial_v2_recognized`
  - test: `tests/app/srvboot_version_test.c` —
    `test_is_initial_v1_0rtt_bits_rejected`
  - test: `tests/app/srvboot_version_test.c` —
    `test_initpkt_ver_v2_byte0_type_bits`
- [x] 9369-005 (§3.2) If a logical packet type or wire type value is out of
  range, then the implementation shall reject the mapping.
  - test: `tests/transport/v2types_test.c` — `test_invalid`

## §4.1 Compatible Negotiation Requirements

- [x] 9369-014 (§4.1) If the server sends a Retry packet, then the server
  shall use the original version.
  - test: `tests/app/srvrun_pin_test.c` —
    `test_srvrun_force_retry_uses_initial_version` (a v2 Initial through
    `srvrun_serve` draws a v2 Retry whose tag verifies under the v2 key)
  - test: `tests/tls/retry_tag_v2_test.c` —
    `test_retry_tag_v2_build_matches_a4` (RFC 9369 A.4 packet rebuilt)
- [~] 9369-028 (§4.1) When the server switches to a negotiated version
  after a Retry, the server shall include the transport parameters that
  validate the Retry and the connection IDs used in the exchange.

    independently of the version (`tests/tls/server_tp_test.c` —
    `test_server_tp_retry_scid` asserts retry_source_connection_id); no
    test combines a Retry with a version switch.
- [x] 9369-016 (§4.1) The server shall send all CRYPTO frames using the

  - test: `tests/app/srvboot_version_test.c` —
    `test_srvboot_accept_v2_initial`

    `test_srvboot_v1_initial_with_vi_switches_to_v2`
  - vuln: V-0227
- [~] 9369-029 (§4.1) While the server has not yet processed the client's

- [x] 9369-017 (§4.1) Where the server accepts 0-RTT on a connection that

## §5 TLS Resumption and NEW_TOKEN Tokens

- [x] 9369-020 (§5) If a session ticket or token was issued from a QUIC
  version different from the connection's version, then the server shall
  not accept it.
  - test: `tests/tls/sdrv_test.c` — `test_sdrv_ticket_version_bound`
    (`ticket_version_ok` is strict equality)
  - test: `tests/app/srvrun_token_test.c` — `test_srvrun_newtok_binding`
    (the NEW_TOKEN MAC covers the version)
- [x] 9369-021 (§5) If the server rejects a session ticket for its
  originating version, then the server shall fall back to a full TLS
  handshake without 0-RTT.
  - test: `tests/tls/sdrv_test.c` — `test_sdrv_ticket_version_bound`
    (psk_accepted and early_data_accepted both 0)
- [~] 9369-030 (§5) When a connection used compatible version negotiation,
  the server shall treat the session tickets and tokens it issues as
  originating from the negotiated version.
  - test: `tests/app/srvloop_test.c` —
    `test_srvloop_ticket_seals_version_and_limits` (tickets record
    `sdrv_wire_version`, the negotiated version once one was picked; NEW_TOKEN
    tokens are bound to the same value in `srvrun_newtok_seal`)
  - gap: no test drives a compatibly negotiated (v1 -> v2) connection to
    ticket or token issuance.

## §7 Applicability

- [~] 9369-022 (§7) The server shall allow ALPN codepoints specified for
  QUIC version 1 (such as "h3") to operate over version 2.
  - evidence: `sdrv_negotiate_alpn` picks from the configured raw ids, h3
    and hq-interop without consulting the QUIC version, and each of those
    is defined for both v1 and v2 (RFC 9369 §7); the server accepts a v2
    Initial (`test_srvboot_accept_v2_initial`). No test negotiates an ALPN
    over v2 end to end.

## Out of scope

Client-only or operator-level requirements this server SDK does not
implement, excluded from the coverage denominator:

- (§1, §6) Ossification rationale and middlebox-behavior discussion —
  informational.
- (§4) Alt-Svc discovery considerations — HTTP client and operator
  concern.
- (§4.1) Client-side rules: ignoring Retry packets in other versions, not
  switching versions in the token-bearing Initial, learning the negotiated
  version from the long-header Version field, sending subsequent Initials
  in it, and never sending 0-RTT in the negotiated version — client
  behavior.
- (§4.1) Encoding the QUIC version in the Retry token to detect a client
  version switch — optional (MAY), not implemented.
- (§5) Client prohibition on using tickets or tokens across versions —
  client behavior.
- (§6) Client choice to initiate a connection with version 2 — client
  behavior.
- (§8) Security considerations — informational; no new requirements over
  version 1.
- (§9) IANA registrations (0x6b3343cf permanent, 0x709a50c4 provisional) —
  registry process, not implementation.
