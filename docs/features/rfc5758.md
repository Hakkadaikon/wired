# RFC 5758 — X.509 Additional Algorithms: ECDSA and SHA-2 Signature OIDs

EARS requirement ledger extracted from the spec text
(`tasks/specs/rfc5758.txt`, not in git). Each requirement carries the test
that demonstrates it; an unchecked box with no test line is an open gap.
Scope: what this TLS server SDK's certificate stack consumes/produces —
ecdsa-with-SHA256/SHA384 signature-algorithm OID recognition and matching
in certificates. Status as of 2026-10.

## Out of scope

Algorithms and CA-generation policy this server SDK does not implement,
excluded from the coverage denominator:

- 5758-001 (§2) Recognizing the bare id-sha224 OBJECT IDENTIFIER (the
  digest algorithm alone, not the composite ecdsa-with-SHA224
  signatureAlgorithm OID that 5758-007 already covers) — a certificate's
  signatureAlgorithm field only ever appears in the composite form, so no
  caller in this SDK ever needs to resolve a bare digest OID on its own;
  same non-actionable-OID shape as 5758-006's DSA judgment below.
- 5758-005 (§2) Accepting both NULL and absent parameters on a bare SHA-2
  hash AlgorithmIdentifier — the only bare hash OID this SDK reads is the
  PKCS#1 v1.5 DigestInfo, where RFC 8017 Appendix B.1's exception pins the
  parameters to NULL (`rsa_pkcs1_verify` compares against that form); no
  other hash AlgorithmIdentifier is parsed.
- 5758-006 (§3.1) Recognizing id-dsa-with-sha224/id-dsa-with-sha256 as DSA
  signature algorithms — the SDK implements only RSA-PKCS1 and ECDSA
  signature verification/generation; no DSA code path exists anywhere in
  `src/crypto/`. Recognizing the OID alone would not be actionable: there is
  no `X509_SIG_DSA` key kind or DSA verification primitive for a
  recognized OID to route to.
- (§3.1, §3.2) FIPS 186-4-conformance generation requirements ("Conforming
  CA implementations ... MUST generate ... in accordance with all the
  requirements in Sections 4.1, 4.5, and 4.6 of [FIPS186-3]") — a CA
  operational-policy statement, not a testable wire-format or parsing
  behavior of this server SDK.
- (§5) Security-considerations guidance pointing to NIST SP 800-56A/57/107
  and X9.62 for key-size selection — operator policy guidance, not
  implementable code behavior.
