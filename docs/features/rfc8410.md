# RFC 8410: インターネット X.509 公開鍵基盤における Ed25519、Ed448、X25519、X448 のためのアルゴリズム識別子

仕様の本文(`tasks/specs/rfc8410.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。範囲は、この TLS サーバー SDK の証明書スタックが読み込むものと生成するものです。具体的には Ed25519 の SubjectPublicKeyInfo のエンコード、EdDSA 署名のエンコード、自己署名証明書の構築です。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

## 付録 A 無効なエンコーディング

- [~] 8410-015 (Appendix A) 公開鍵が、必須の BIT STRING ではなく OCTET STRING としてエンコードされている場合、実装はその SubjectPublicKeyInfo を拒否しなければならない。
  - evidence: `test_spki_short_tbs` が与えるのは途切れた tbs だけである。`split_spki` は SPKI の 2 番目の要素のタグが `DER_BIT_STRING` と一致することを求めており、ほかのタグ(OCTET STRING を含む)では `derseq_next_tagged` の不一致で解析が失敗する。P-256 と Ed25519 の SPKI の解析(`x509_public_key`)は同じコードパスを通るが、Ed25519 に特化して OCTET STRING に置き換えた専用のフィクスチャはない。
- [~] 8410-016 (Appendix A) 実装は、秘密鍵を取り込むときに、Ed25519/X25519 の秘密鍵のマスクや形式の要件(たとえば X25519 の上位ビットと下位ビットのクランプ規則)が適用されることを保証しなければならない。
  - test: `tests/crypto/eckey_test.c` —
    `test_eckey_x25519_import_clamped_on_use`
  - evidence: `wired_eckey_curve25519_priv` は PKCS#8 の秘密鍵をクランプせずにそのままデコードする(テストは、取り込んだバイトがクランプ前の生の入力と等しいことを確かめている)。代わりに、使用時に `wired_x25519_base` 自身の RFC 7748 §5 decodeScalar25519 のクランプがかかる。これは要件の未実装ではなく、意図した設計(取り込み時ではなく使用時にクランプする)である。ただし、同じ取り決めの Ed25519 のシード側を固定したテストはない(確かめているのは X25519 だけ)。
- [x] 8410-017 (Appendix A) 取り込んだ曲線の秘密鍵がちょうど 32 オクテットでない場合、実装はそれを拒否しなければならない。
  - test: `tests/crypto/eckey_test.c` — `test_eckey_curve25519_bad_len`
- [x] 8410-018 (Appendix A, RFC 5958) OneAsymmetricKey をデコードするとき、実装は、publicKey がなければ version 0 を、あれば version 1 を必須としなければならない。

- [x] 8410-019 (§3, §6) 実装は、証明書のサブジェクト公開鍵を、その SubjectPublicKeyInfo のアルゴリズムが id-Ed25519 であるときに限り、Ed25519 の検証鍵として使わなければならない。
  - test: `tests/tls/certverify_test.c` — `test_certverify_spki_ed25519_alg` (同じ Ed25519 の鍵に id-X25519 のラベルを付けると検証できなくなる)

## 対象外

このサーバー SDK が実装しない曲線、アルゴリズム、鍵管理の関心事です。カバレッジの分母から除いています。

- (§3, §4, §5, §9) X25519 と X448 の鍵合意アルゴリズム識別子と、その SubjectPublicKeyInfo と keyUsage のエンコード。SDK には ECDH 型の鍵合意証明書の経路がない。`ed25519_field.c` が実装する curve25519 の体の演算は EdDSA 署名と共有するためだけのもので、独立した X25519 の KEX や SPKI の機能ではない。
- (§3, §4, §6, §9) Ed448 署名アルゴリズム識別子と、その SubjectPublicKeyInfo と署名のエンコード。SDK が実装するのは Ed25519 だけで、`src/crypto/` に Ed448/curve448 の演算はない。
- (§7) OneAsymmetricKey の任意フィールド `attributes` と `publicKey`、および公開鍵と秘密鍵の整合性の検査。エンコーダーはどちらも出力せず、デコーダー(`wired_eckey_curve25519_priv`)は version、algorithm、privateKey だけを読む。
- (§8) 人間が読めるアルゴリズム名の命名規則("ECDH"、"X25519"、"EdDSA"、"Ed25519")。実装者向けの表示やログの慣習であり、ワイヤー形式や解析の要件ではない。
- (§10) 説明用の具体例(公開鍵のサンプル、X25519 証明書、秘密鍵のダンプ)。規範ではない例であり、上で扱ったもの以上に単独でテストできる要件ではない。
- (§11) IANA のモジュール識別子の登録。レジストリ管理の関心事で、実装できるコードの動作ではない。
- OneAsymmetricKey について付録 A が述べる BER(DER ではなく)のデコードの受け入れ。SDK の ASN.1 層(`crypto/pki/encoding/asn1/`)は DER だけを実装しており、RFC 8410 自身も BER の受け入れは任意だと述べている("some acceptors will only decode DER formats")。
