# NIST SP 800-38D: ブロック暗号の利用モードに関する勧告（ガロア/カウンターモード（GCM）および GMAC）

仕様の本文(`tasks/specs/sp800-38d.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 15/23、間接 8、未テスト 0。**

## §5.1 ブロック暗号

- [~] S38D-001 (§5.1) 実装は、GCM の下位の暗号として、ブロックサイズが 128 ビットで鍵長が 128 ビット以上の承認されたブロック暗号を使わなければならない。
  - evidence: `gcm_ctx`(`src/crypto/symmetric/aead/gcm/gcm.h`)は `aes128*` を、`gcm256_ctx`(`gcm256.h`)は `aes256*` を受け取ります。どちらも 128 ビットのブロックと 128 ビットまたは 256 ビットの鍵を持つ FIPS 197 の AES で、C の型で固定されています。ベクターのテスト(`test_gcm_nist`、`test_gcm256_kat`)はまさにこれらの暗号を使いますが、サイズそのものを検証するテストはありません。
- [x] S38D-002 (§5.1) 実装は、GCM の中では下位のブロック暗号の順方向暗号関数だけを使わなければならない(逆方向は必要ない)。
  - test: `tests/crypto/gcm_test.c` — `test_gcm_nist`
  - test: `tests/crypto/gcm_test.c` — `test_gcm_open`
  - evidence: `gcm_seal`/`gcm_open`(`src/crypto/symmetric/aead/gcm/gcm_open.c`)と `gcm256_*`(`gcm_gcm256.c`)は `aes128_encrypt`/`aes256_encrypt` だけを呼び出し、復号のプリミティブは呼び出しません(この SDK には復号のプリミティブがありません。FIPS 197 の台帳の「対象外」を参照)。

## §5.2 2 つの GCM 関数

- [x] S38D-003 (§5.2.1.1) 認証付き暗号化関数は、平文 P、追加認証データ A、初期化ベクトル IV を入力として受け取らなければならない。
  - test: `tests/crypto/gcm_test.c` — `test_gcm_nist`
  - test: `tests/crypto/gcm_test.c` — `test_gcm_open`
- [~] S38D-004 (§5.2.1.1) 実装は、len(P) <= 2^39-256、len(A) <= 2^64-1、1 <= len(IV) <= 2^64-1 の範囲で、IV、平文、AAD のビット長としてそれぞれ 8 の倍数(バイト列)をサポートしなければならない。
  - evidence: `wired_span`(`common/bytes/span/span.h`)はどこでもバイト単位なので、バイト未満の長さは作れません。上限は実用上到達せず(2^39 バイトの平文に近づくテストはありません)、個別には検証していません。
- [~] S38D-005 (§5.2.1.1) 実装は、相互接続性、効率、設計の単純さを高めるため、サポートする IV を 96 ビットに限定するべきである。
  - evidence: `GCM_NONCE` = 12 バイト(`src/crypto/symmetric/aead/gcm/gcm.h`)が、IV のパラメーター型をコンパイル時にちょうど 96 ビットに固定しています。API が表せる IV の長さはほかにないので、拒否の専用テストを書いても動かす対象がありません(異なるサイズの IV をいったん受け付けてから拒否するコード経路はなく、パラメーターの C の型そのものが制約になっています)。実行時の検査ではなく、構造によって満たしています。
- [x] S38D-006 (§5.2.1.2) 認証付き暗号化関数は、P と同じビット長の暗号文 C と、認証タグ T を出力しなければならない。
  - test: `tests/crypto/gcm_test.c` — `test_gcm_nist`
- [~] S38D-007 (§5.2.1.2) タグ長 t は 128、120、112、104、96、64、32 ビットのいずれかで、鍵ごとに固定されていなければならない。実装はそれ以外のタグ長をサポートしてはならない。
  - evidence: `GCM_TAG`(`src/crypto/symmetric/aead/gcm/gcm.h`)が t = 128 を無条件に固定しています。ほかのタグ長には単に到達できない(タグ長のパラメーターがない)ので「ほかの値をサポートしてはならない」は自明に満たしますが、専用のテストでは検証していません。
- [x] S38D-008 (§5.2.2) 認証付き復号関数は、IV、C、A、T を入力として受け取り、平文 P か FAIL のどちらかを出力しなければならない。P を返すのは、T が (IV, A, C) に対する正しいタグである場合だけである。
  - test: `tests/crypto/gcm_test.c` — `test_gcm_open`
- [~] S38D-026 (§5.2.1.1) 実装は、P、A、IV のサポートするビット長の組を、鍵に依存せず実装全体で 1 つに定めるべきである。
  - evidence: `GCM_NONCE` = 12 とバイト単位の `wired_span` による P/A の長さは、`gcm_*` と `gcm256_*` で同じで、鍵に依存するパラメーターを取りません。構造によって満たしており、専用のテストはありません。
- [x] S38D-027 (§5.2.2) 実装は、認証付き復号で、認証付き暗号化の P、A、IV と同じ長さの C、A、IV をサポートしなければならない。
  - test: `tests/crypto/gcm_test.c` — `test_gcm_dispatch`

## §5.3 機密性と認証のためのプリミティブ

- [~] S38D-028 (§5.3) 実装は、ハッシュ部分鍵 H を含む GCM 関数の中間値を秘密に保たなければならず、H をほかの目的に公開してはならない。
  - evidence: H と J0 はスタック上のローカルな `gcm_st`(`src/crypto/symmetric/aead/gcm/gcm_open.c`)の中にだけあります。`gcm.h`/`gcm256.h` が公開するのは seal/open だけで、H を返すアクセサーはありません。専用のテストはありません。

## §6.2 インクリメント関数

- [x] S38D-009 (§6.2) 実装は、s ビットのインクリメント関数 inc_s(X) を、X の右端 s ビットを 2^s を法としてインクリメントし、残りの左側のビットは変えないものとして定義しなければならない。
  - test: `tests/crypto/gcm_test.c` — `test_gcm_nist`
  - evidence: `gcm_ctr_inc`(`src/crypto/symmetric/aead/gcm/gcm_impl.h`)は 16 バイトのカウンターブロックの下位 32 ビットだけをインクリメントし(inc_32)、要件に合っています。NIST のベクターで端から端まで動かしています(複数ブロックの平文では、期待する暗号文に一致させるためにカウンターのインクリメントが 2 回以上必要です)。

## §6.3 ブロックの乗算

- [x] S38D-010 (§6.3) 実装は、ビットを反転した簡約多項式 R = {11100001} || 0^120 を使って GF(2^128) 上のブロックの積 X . Y を計算しなければならない。X のビットは最上位から処理し、反復ごとに Y を 1 ビットシフトして簡約する(LSB=1 のとき R を XOR する)。
  - test: `tests/crypto/gcm_test.c` — `test_gcm_nist`
  - evidence: `gcm_gf_mul`/`gf_step`(`src/crypto/symmetric/aead/gcm/gcm_impl_head.h`)は Algorithm 1 をそのまま実装しています(`y` のビットを MSB から順に調べて、ビットごとに `z ^= v & mask` を行い、`v` を右シフトして、押し出された LSB に応じて `0xe1`(簡約定数 R の先頭バイト)を条件付きで XOR します)。

## §6.4 GHASH 関数

- [x] S38D-011 (§6.4) 実装は、各 128 ビットのブロック X_i をアキュムレーター Y に畳み込んで(Y_i = (Y_{i-1} XOR X_i) . H、Y_0 = 0^128)Y_m を返すことで、GHASH_H(X_1 || ... || X_m) を計算しなければならない。
  - test: `tests/crypto/gcm_test.c` — `test_gcm_nist`
  - evidence: `gcm_ghash_block`/`gcm_ghash_bytes`(`src/crypto/symmetric/aead/gcm/gcm_impl.h`)はこの漸化式をそのまま実装し、最後の部分ブロックを `load_block` でゼロ詰めします。

## §6.5 GCTR 関数

- [x] S38D-012 (§6.5) 実装は、ICB から inc_32 で導いたカウンターブロックの列を暗号化し、得られたキーストリームを X と XOR することで GCTR_K(ICB, X) を計算しなければならない。最後のブロックのキーストリームは最後の部分入力ブロックの長さに切り詰める。空文字列に対する GCTR は空文字列を返さなければならない。
  - test: `tests/crypto/gcm_test.c` — `test_gcm_nist`
  - test: `tests/crypto/gcm_test.c` — `test_gcm_dispatch`
  - evidence: `gcm_ctr_xor`/`ctr_chunk`(`src/crypto/symmetric/aead/gcm/gcm_impl.h`、`gcm_impl_head.h`)がこれを実装しています。`test_gcm_dispatch` は空文字列と最後の部分ブロック(長さ 0、1、15、17、255)を往復させています。

## §7.1 認証付き暗号化関数のアルゴリズム

- [x] S38D-013 (§7.1, Step 1-2) 実装は、ハッシュ部分鍵 H = CIPH_K(0^128) を計算しなければならず、96 ビットの IV に対してはプレカウンターブロック J0 を IV || 0^31 || 1 として作らなければならない。
  - test: `tests/crypto/gcm_test.c` — `test_gcm_nist`
  - evidence: `gcm_setup`(`src/crypto/symmetric/aead/gcm/gcm_ctr.c`)は `st->h = E(K, 0^128)` を計算し、`j0` をちょうど `nonce || 00 00 00 01` として組み立てます(実装しているのは 96 ビットの IV の分岐だけです。「対象外」を参照)。
- [x] S38D-014 (§7.1, Step 3) 実装は、暗号文を C = GCTR_K(inc_32(J0), P) として計算しなければならない。
  - test: `tests/crypto/gcm_test.c` — `test_gcm_nist`
  - evidence: `gcm_seal` の中で、`ctr_xor` が平文を暗号化する前に、`data_ctr` がカウンターを `inc_32(J0)` に進めます。
- [x] S38D-015 (§7.1, Step 4-6) 実装は、タグを T = MSB_t(GCTR_K(J0, GHASH_H(A || 0^v || C || 0^u || [len(A)]_64 || [len(C)]_64))) として計算しなければならない。ここで u と v は A と C をブロック境界までゼロ詰めする長さである。
  - test: `tests/crypto/gcm_test.c` — `test_gcm_nist`
  - evidence: `gcm_tag`(`src/crypto/symmetric/aead/gcm/gcm_open.c`)は、AAD、続いて暗号文(それぞれ `ghash_bytes`/`load_block` で暗にブロック単位までゼロ詰め)、最後に 128 ビットの `[len(A)]64 || [len(C)]64` ブロックを GHASH に通し、その結果を `E(K, J0)` で暗号化します。t = 128 なので MSB_128 は何も切り詰めず、仕様と完全に一致します。

## §10 適合性

- [~] S38D-024 (§10) 適合する実装は、GHASH/GCTR/GCM-AE/GCM-AD の規定の手順を、すべての入力に対して同じ出力を生む数学的に等価な任意の手順に置き換えてもよい。
  - evidence: `gf_mul` のビット反転と LSB 側へのシフトによる定式化(`src/crypto/symmetric/aead/gcm/gcm_impl_head.h`)と AES-NI の経路(`gcmx86`)は、MSB から処理する Algorithm 1 を、ソフトウェアで扱いやすい形に言い直した等価なものです。仕様自身の構成と一致することは、独立した構造上の証明ではなく、NIST のテストベクターで示しています。

## 付録 B: 認証保証

- [x] S38D-025 (App. B) サーバーは、1 つの鍵で保護する平文と AAD のブロックの総数を制限するべきであり(推奨の上限は 2^64)、鍵ごとに検証の失敗の回数を監視して制限するべきである。
  - test: `tests/tls/aeadlimit_test.c` — `test_aeadlimit`
  - evidence: RFC 9001 6.6 の機密性の上限により、AES-GCM では 2^23 パケット(2^64 ブロックよりはるかに少ない)で鍵の更新が強制されます。完全性の上限は接続ごとに復号の失敗を数えます(9001-057)。

## 対象外

このサーバー SDK が意図して実装しない要件、またはこのプリミティブではなく呼び出し側・プロトコル・運用者が担う要件です。カバレッジの分母から除いています。

- (§5.1) 一様ランダムな鍵の生成、鍵の秘密性、鍵を GCM 専用に使うこと。鍵は呼び出し側から渡されます(RFC 9001 5.1 の鍵スケジュールが、パケット保護とヘッダー保護に別々の鍵を導出します)。鍵管理はプロトコルの関心事です。
- (§3, Authority) IV の一意性が保証されない限り「配備するべきではない」こと、CMVP の検証、適用に関する告知。配備と方針の記述。
- (§5.2.1, §5.2.2) GMAC(機密の平文を持たない、認証だけの入力に限定した GCM の特殊形)。この SDK は実際の平文がある場合(QUIC のパケット保護)にしか GCM を呼び出しません。認証だけの入口は公開していません。
- (§7.1 Step 2, §7.2 Step 3, non-96-bit branch) 96 ビット以外の長さの IV について、GHASH_H(IV || 0^(s+64) || [len(IV)]_64) で J0 を導出すること。`GCM_NONCE` がノンスをちょうど 12 バイトに固定しているので(`src/crypto/symmetric/aead/gcm/gcm.h`)、到達できるのは Step 2 の 96 ビットの分岐だけです。QUIC(RFC 9001 5.3)は常に 96 ビットの AEAD ノンスを使います。
- (§8 S38D-019, §8.1 S38D-020, §8.2.1/§8.2.2 S38D-021, §8.3) IV と鍵の一意性、鍵の新規性、IV の構成の枠組み、呼び出し回数の上限。これらが縛るのは呼び出し側のプロトコル(RFC 9001 はパケットごとのノンスを接続のシークレットとパケット番号から決定論的に導出し、鍵ごとの一意性を保証します)であり、GCM のプリミティブそのものではありません。プリミティブには、再利用を追跡する「接続」やセッションの概念も、強制するべき鍵の新規性のライフサイクルもありません。呼び出しごとに生の IV と鍵の組を受け取る GCM のプリミティブには、呼び出しをまたいで再利用を検出するための状態がないので、`gcm_*` 自体に再利用の検出を組み込むには、この層にないセッションの概念を新たに作る必要があります。
- (§8.3 S38D-022) 呼び出し回数の上限のうち、96 ビット以外の IV の分岐(2^32。96 ビットの決定論的構成では無条件に 2^32)。`GCM_NONCE` がノンスをちょうど 12 バイトに固定し(`src/crypto/symmetric/aead/gcm/gcm.h`)、ほかの IV の長さはサポートしていないので(上の §7.1/§7.2 の J0 の導出の項目を参照)、この要件の「unless」節が防いでいる条件は決して成り立ちません。96 ビットの場合の上限も実際にはより厳しい RFC 9001 §6.6 の AEAD の機密性の上限(AES-GCM で 2^23)に置き換わります。`aead_needs_update`/`AEAD_LIMIT_AESGCM`(`tests/tls/aeadlimit_test.c` の `test_aeadlimit`)が、どちらの上限に達するよりずっと前に鍵の更新を起こします。
- (§8.2.2) RBG に基づく IV の構成。使っていません。RFC 9001 5.3 のノンスは決定論的です(IV とパケット番号の XOR)。
- (§9, §9.1 S38D-023, §9.2) FIPS 140-2 の暗号モジュールの検証、IV 生成ユニットのハードウェアとファームウェアの境界、電源断からの復旧。運用者・配備とハードウェアの検証の関心事であり、このソフトウェア SDK が表せる実装の振る舞いではありません。
- (Appendix A) IV の再利用がなぜ危険かを説明する本文(参考情報。§8 自身の要件を超える規範的な内容はなく、§8 の要件は S38D-019 としてすでに取り込んでいます)。
- (Appendix C) 短いタグ(32/64 ビット)の使用の指針と、そのパケット長と呼び出し回数の表。この SDK は常に 128 ビットの完全なタグ(`GCM_TAG` = 16 バイト)だけを使うので、短いタグの指針は当てはまりません。
- (Appendix D) IV の重複の監視や AAD のシーケンス番号によるリプレイ保護。アプリケーション層またはプロトコル層の関心事であり(QUIC では RFC 9000 のパケット番号空間がこれを担います)、AEAD のプリミティブの性質ではありません。
- (Appendix E) 参考文献。参照の一覧であり、要件ではありません。
