# 要件台帳の書式

[ドキュメント](../README.md) › [要件台帳](README.md) › 台帳の書式


| 項目 | 内容 |
|---|---|
| 目的 | `docs/features/` の要件台帳の書式を定める |
| 読む人 | 台帳を追加・編集するコントリビューター |
| 前提文書 | [要件台帳](README.md) |
| 関連文書 | `scripts/check_features.py`(`just features-check`。CI で実行) |

各台帳は 1 つの仕様についての EARS 形式の要件台帳で、各要件をそれを確かめる既存のテストに結び付ける。テストされていない要件を一覧で示すのが目的である。機械で確かめられる規則は `scripts/check_features.py` が強制する。


## 1. ファイルの骨組み(このとおりに書く)

```markdown
[ドキュメント](../README.md) › [機能](README.md) › RFC 9000

# RFC 9000: QUIC: UDP ベースの多重化されたセキュアなトランスポート

仕様の本文(`tasks/specs/rfc9000.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。
各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。
2026-07 時点の状況です。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み NN/MM、間接 KK、未テスト LL。**

## §16 可変長整数エンコーディング

- [x] 9000-001 (§16) サーバーは、先頭バイトの上位 2 ビットを可変長整数の長さとしてデコードしなければならない。
  - test: `tests/transport/varint_test.c` — `test_varint_decode`
- [~] 9000-002 (§16) 可変長整数をエンコードするとき、サーバーは必要以上に長いエンコーディングを使ってはならない。
  - evidence: すべてのフレームコーデックのラウンドトリップテストで動いている。最小長を確かめる専用のアサーションはない。
- [ ] 9000-003 (§16) 可変長整数が 2^62-1 を超える場合、サーバーはそのエンコーディングを拒否しなければならない。

## 対象外

このサーバー SDK が実装しない、クライアント専用または運用者向けの要件。カバレッジの分母から除く:

- (§6.2) クライアントが始めるバージョンネゴシエーションの応答の処理: クライアントの動作。
```


## 2. 規則

### 2.1 ID

- 形は `<stem>-NNN` で、数字は 3 桁である。
- 新しい台帳では仕様の順に番号を振る。その後は ID を変えない。ほかのページ([既知の制限](../security/limitations/README.md) など)や GitHub の issue が引用する。
- 項目を消したら番号は欠番として残す。新しい項目は、節の中で順序が崩れても次の空き番号を使う。
- ID は再利用も振り直しもしない(同じ ID を 2 回使うとチェッカーが拒否する)。
- 末尾の英字(`MQ18-118a`)は既存の項目から分けた項目を表す。
- RFC 9000 の台帳は仮の ID `9000-XXX` を使っていて、一意性の検査はこれを飛ばす。

| 台帳 | stem |
|---|---|
| rfc9000 | `9000` |
| fips197 | `F197` |
| fips186-4 | `F186` |
| fips180-4 | `F180` |
| fips198-1 | `F198` |
| sp800-38d | `S38D` |
| draft-ietf-webtrans-http3-15 | `WTH3` |
| draft-ietf-moq-transport-19 | `MOQT` |

### 2.2 EARS の書き方

合う型を選び、要件文は常体で書く。

| 型 | 文型 |
|---|---|
| 常時 | 「サーバーは X しなければならない。」 |
| イベント駆動 | 「T とき、サーバーは X しなければならない。」 |
| 状態駆動 | 「S 間、サーバーは X しなければならない。」 |
| 望ましくない動作 | 「C 場合、サーバーは X しなければならない。」 |
| オプション機能 | 「F の構成では、サーバーは X しなければならない。」 |

システムの名前は「サーバー」である(wired はサーバー SDK)。純粋なライブラリのプリミティブ(暗号、コーデック)には「実装」を使う。SHOULD / RECOMMENDED の規則は「するべきである」、MUST の規則は「しなければならない」で書く。

### 2.3 抽出の範囲

- サーバー側の実装に関わる規範的な MUST / MUST NOT / SHALL / SHOULD / SHOULD NOT / REQUIRED の記述すべて。
- 記述的に書かれていても仕様の中心となるアルゴリズム(KDF の導出手順、ステートマシンの遷移など)。
- 迷ったら入れる。取りすぎは許し、漏れは許さない。
- 項目は仕様の節の構成をなぞった `##` 見出しの下に、仕様の順にまとめる。

### 2.4 対象外の項目

最後の `## 対象外` の節に、チェックボックスも ID もない普通の箇条として、理由を一言添えて書く。クライアントだけの動作、運用者向けの指針、SDK が意図的に出荷しないアルゴリズムが入る。黙って落とすことも、集計に数えることもしない。

### 2.5 テストの参照

チェッカーはこの書式を厳密に強制する。

``- test: `tests/<dir>/<file>` — `<function>` ``

- ファイルパスはリポジトリに存在し、関数名はそのファイルに出てくる必要がある。grep で確かめていないテストは挙げない。本物のテストが見つからなければ、その項目は `[~]`(evidence 行付き)か `[ ]` にする。
- 挙げるテストは `tests/run.c` の `main()` から到達でき、本番の経路(`examples/` → srvrun/srvloop/sdrv/moqtrun)が呼ぶコードを動かすものに限る。本番から呼ばれないヘルパーのテストは、`[~]` の evidence にとどまる。
- 「実装は〜しなければならない」と書くライブラリやコーデックの項目も同じである。テスト、ファズハーネス、出荷していないクライアントからしか呼ばれないプリミティブは `[~]`(本番の経路がまったく動かさないなら `[ ]`)とし、evidence 行かギャップの行でそう書く。
- テストが複数あるときは `- test:` 行を繰り返す。
- ゴールデンベクターのヘッダー(`tests/*_golden.h`)とファズハーネス(`fuzz/fuzz_*.c`)も `- test:` 行に挙げられる。
- `[~]` の項目は `- test:` の代わりに `- evidence:`(自由記述)を使う。
- 相互運用性テストでしか確かめていない項目は `[~]` とし、テストケースの名前を evidence 行に書く。例: ``- evidence: interop テストケース `keyupdate`([相互運用性の検証結果](../verification/interop.md) を参照)。専用の単体テストはない。``
- `- vuln: V-nnnn, ...` の行は [脆弱性台帳](../security/vuln-ledger.md) の行のうち、項目の `- test:` 行のどれかを pinning test(その脅威への修正を固定するテスト)とするものを挙げる(この要件が対処する脅威)。最後の下位行で、手で選ばず、共有のテスト名から生成し直す。

### 2.6 テストの探し場所

`tests/{transport,crypto,tls,app,common}/<domain>_test.c` の `static void test_*` 関数である。手がかりの対応表は `docs/verification/coverage.md`(ベクターの置き場所)にある。対応表は証拠にならないので、必ず grep で確かめる。

### 2.7 集計の行

`**カバレッジ: テスト済み NN/MM、間接 KK、未テスト LL。**`

| 記号 | 意味 |
|---|---|
| MM | チェックボックス付きの項目の総数 |
| NN | `[x]` の数 |
| KK | `[~]` の数 |
| LL | `[ ]` の数 |

`## Not implemented`、`## Out of scope`、`## Experimental ...`、`## Informational ...` と、日本語の `## 未実装`、`## 対象外`、`## 実験的...`、`## 参考情報...` の見出しの下のチェックボックスは数えない。

件数は実際のチェックボックスと一致し、README の各行と合計の行も台帳と一致する必要がある。`python3 scripts/check_features.py --fix` が、この 3 つをチェックボックスから書き直す。

### 2.8 項目の文

- 各要件は 1 文で書き、ID の後ろの括弧に仕様の節を書く。
- 論評は書かない。テストされていない理由が分かっているときは、短い `- gap:` 行を書ける。
- 要件文は項目の 1 行目に 1 行で書き、下位行(`- test:` など)は 2 文字字下げする。

### 2.9 文体とラベル

- 台帳の地の文は日本語(です・ます)、要件文は常体で書く。
- `- test:`、`- evidence:`、`- gap:`、`- vuln:` のラベルと `- test:` 行の書式は、チェッカーとツールが読むので英語のままにする。
- 英語のまま残っている台帳(MoQT と WebTransport のドラフト)も、その書式のままで検査を通る。
