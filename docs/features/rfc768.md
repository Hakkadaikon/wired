# RFC 768 — User Datagram Protocol

EARS requirement ledger extracted from the spec text
(`tasks/specs/rfc768.txt`, not in git). Each requirement carries the test
that demonstrates it; an unchecked box with no test line is an open gap.
Status as of 2026-10.

Legend:

- `[x]` — demonstrated by the referenced test
- `[~]` — exercised indirectly (evidence line explains how; no dedicated test)
- `[ ]` — not demonstrated by any test yet

**Coverage: 9/9 tested, 0 indirect, 0 untested.**

These headers are built and parsed by wired itself only on the AF_XDP path
(`src/transport/io/socket/net/udp4.c`,
`src/transport/io/xdp/xdpframe/xdpframe.c`); the interop runs used kernel
UDP sockets, which fill in the UDP header themselves, so this framing is
unit-tested but not interop-proven.

## Format

- [x] 768-001 (Format) The implementation shall lay out the UDP header as
  Source Port, Destination Port, Length, and Checksum, each a 16-bit field,
  followed by the data octets.
  - test: `tests/transport/net_test.c` — `test_udp_checksum`
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_rx_golden`
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_tx_roundtrip`
- [x] 768-003 (Fields) The implementation shall set Length to the length in
  octets of the UDP header plus the data, with a minimum value of eight.
  - test: `tests/transport/net_test.c` — `test_udp_checksum`
- [x] 768-004 (Fields) The implementation shall compute Checksum as the
  16-bit one's complement of the one's complement sum of the pseudo-header
  (source address, destination address, protocol, UDP length), the UDP
  header, and the data, padded with a zero octet if the data is an odd
  number of octets.
  - test: `tests/transport/net_test.c` — `test_udp_checksum`
  - test: `tests/transport/net_test.c` — `test_net_datagram_over_link`
- [x] 768-005 (Fields) If the computed checksum is zero, then the
  implementation shall transmit it as all ones.
  - test: `tests/transport/net_test.c` —
    `test_udp_checksum_zero_result_becomes_all_ones`
- [x] 768-006 (Fields) If a received datagram's checksum field is all zero,
  then the implementation shall treat it as "no checksum generated" and
  shall not reject the datagram for its checksum.
  - test: `tests/transport/net_test.c` —
    `test_udp_checksum_zero_field_accepted_unchecked`
- [x] 768-007 (Fields) Where the server replies to a datagram, it shall
  address the reply to the received Source Port (and source address).
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_reflect`
- [x] 768-008 (Fields) When a received datagram carries a non-zero
  checksum, the implementation shall verify it over the pseudo-header, the
  UDP header and the data, and reject a mismatch.
  - test: `tests/transport/net_test.c` — `test_udp_checksum`
  - test: `tests/transport/srvxdp_test.c` —
    `test_srvxdp_rx_drops_bad_headers` (the AF_XDP receive path verifies
    by default; `wired_srvxdp_cfg.skip_udp_csum` / `--skip-udp-csum` is the
    explicit opt-out for veth's CHECKSUM_PARTIAL frames)
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_rx_udp_checksum`
- [x] 768-009 (Fields) If a received datagram's Length is below eight or
  disagrees with the length the IP header gives it, then the implementation
  shall reject the datagram.
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_rx_rejects`

## IP Interface

- [x] 768-010 (IP Interface) The implementation shall determine the source
  and destination internet addresses and the protocol of a received
  datagram from its internet header.
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_rx_golden`
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_rx_rejects`

## Out of scope

Client-only or operator-level requirements this server SDK does not
implement, excluded from the coverage denominator:

- (Fields) 768-002: inserting a value of zero for Source Port when no
  meaningful source port is available — `put_udp`
  (`src/transport/io/socket/net/udp4.c`) writes the caller-supplied `sport`
  verbatim, and every call site in this server SDK passes a fixed, meaningful
  port (e.g. 4433); the "no meaningful source port" case this requirement
  addresses does not arise for an endpoint that always has one.
- (User Interface) The receive-port creation, receive, and send operations
  described for a UDP user interface — an application/operator-facing API
  shape, not a wire-format requirement.
- (IP Interface) Passing a full internet datagram between UDP and IP as
  one possible interface — an informative design option.
- (Introduction) Applications needing ordered reliable delivery "should use"
  TCP — application guidance; QUIC provides its own reliability.
- (Protocol Application) The Internet Name Server and Trivial File Transfer
  as example UDP applications — informational, not a requirement on this
  SDK.
- (Protocol Number) UDP being assigned protocol number 17 — a registry fact
  reflected as the `IP_PROTO_UDP` constant, not a testable behavior in
  its own right.
