# RFC 768: ユーザーデータグラムプロトコル(User Datagram Protocol)

仕様の本文(`tasks/specs/rfc768.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。2026-10 時点の状況です。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 9/9、間接 0、未テスト 0。**

wired がこれらのヘッダーを自前で組み立て、解析するのは AF_XDP 経路だけです(`src/transport/io/socket/net/udp4.c`、`src/transport/io/xdp/xdpframe/xdpframe.c`)。相互接続性の試験ではカーネルの UDP ソケットを使っており、UDP ヘッダーはカーネルが埋めます。そのため、このフレーミングは単体テストで確かめていますが、相互接続性の試験では確かめていません。

## フォーマット

- [x] 768-001 (Format) 実装は UDP ヘッダーを、それぞれ 16 ビットのフィールドである Source Port、Destination Port、Length、Checksum の順に並べ、そのあとにデータのオクテットを続けなければならない。
  - test: `tests/transport/net_test.c` — `test_udp_checksum`
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_rx_golden`
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_tx_roundtrip`
- [x] 768-003 (Fields) 実装は Length を UDP ヘッダーとデータを合わせたオクテット単位の長さにしなければならず、その最小値は 8 である。
  - test: `tests/transport/net_test.c` — `test_udp_checksum`
- [x] 768-004 (Fields) 実装は擬似ヘッダー(送信元アドレス、宛先アドレス、プロトコル、UDP の長さ)、UDP ヘッダー、データ(データが奇数オクテットなら 0 のオクテットで埋める)の 1 の補数和を求め、その 16 ビットの 1 の補数を Checksum としなければならない。
  - test: `tests/transport/net_test.c` — `test_udp_checksum`
  - test: `tests/transport/net_test.c` — `test_net_datagram_over_link`
- [x] 768-005 (Fields) 計算したチェックサムが 0 の場合、実装はそれをすべて 1 のビットとして送信しなければならない。
  - test: `tests/transport/net_test.c` —
    `test_udp_checksum_zero_result_becomes_all_ones`
- [x] 768-006 (Fields) 受信したデータグラムのチェックサムフィールドがすべて 0 の場合、実装はそれを「チェックサムを生成していない」として扱わなければならず、チェックサムを理由にそのデータグラムを拒否してはならない。
  - test: `tests/transport/net_test.c` —
    `test_udp_checksum_zero_field_accepted_unchecked`
- [x] 768-007 (Fields) データグラムに応答する場合、サーバーは受信した Source Port(と送信元アドレス)を応答の宛先にしなければならない。
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_reflect`
- [x] 768-008 (Fields) 受信したデータグラムのチェックサムが 0 でないとき、実装は擬似ヘッダー、UDP ヘッダー、データについてそれを検証し、一致しなければ拒否しなければならない。
  - test: `tests/transport/net_test.c` — `test_udp_checksum`
  - test: `tests/transport/srvxdp_test.c` — `test_srvxdp_rx_drops_bad_headers` (AF_XDP の受信経路は既定で検証する。`wired_srvxdp_cfg.skip_udp_csum` / `--skip-udp-csum` は、veth の CHECKSUM_PARTIAL のフレーム向けに検証を明示的に外す設定)
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_rx_udp_checksum`
- [x] 768-009 (Fields) 受信したデータグラムの Length が 8 未満であるか、IP ヘッダーが示す長さと食い違う場合、実装はそのデータグラムを拒否しなければならない。
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_rx_rejects`

## IP インターフェース

- [x] 768-010 (IP Interface) 実装は受信したデータグラムの送信元と宛先のインターネットアドレス、およびプロトコルを、そのインターネットヘッダーから求めなければならない。
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_rx_golden`
  - test: `tests/transport/xdpframe_test.c` — `test_xdpframe_rx_rejects`

## 対象外

このサーバー SDK が実装しない、クライアント専用または運用者向けの要件です。カバレッジの分母から除きます。

- (Fields) 768-002: 意味のある送信元ポートがないときに Source Port に 0 を入れること。`put_udp`(`src/transport/io/socket/net/udp4.c`)は呼び出し側が渡した `sport` をそのまま書き込み、このサーバー SDK の呼び出し箇所はどれも固定の意味のあるポート(例: 4433)を渡す。この要件が想定する「意味のある送信元ポートがない」場合は、常にポートを持つエンドポイントでは起こらない。
- (User Interface) UDP のユーザーインターフェースとして説明されている、受信ポートの作成、受信、送信の操作。アプリケーションや運用者向けの API の形であり、ワイヤーフォーマットの要件ではない。
- (IP Interface) UDP と IP の間でインターネットデータグラム全体を渡すという、考えられるインターフェースの 1 つ。参考としての設計の選択肢。
- (Introduction) 順序どおりの信頼性のある配送が必要なアプリケーションは TCP を「使うべきである」という記述。アプリケーションへの指針であり、QUIC は独自に信頼性を提供する。
- (Protocol Application) UDP を使うアプリケーションの例としての Internet Name Server と Trivial File Transfer。参考情報で、この SDK への要件ではない。
- (Protocol Number) UDP にプロトコル番号 17 が割り当てられていること。`IP_PROTO_UDP` 定数に反映したレジストリ上の事実であり、それ自体はテストできる振る舞いではない。
