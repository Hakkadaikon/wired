# RFC 8439: IETF プロトコルのための ChaCha20 および Poly1305

仕様の本文(`tasks/specs/rfc8439.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。2026-10 時点の状況です。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

## 対象外

このサーバー SDK が実装しない、クライアントだけの要件と運用者レベルの要件です。カバレッジの分母から除いています。

- (§2.3) 128 ビットの鍵と、8/12 ラウンドの ChaCha の変種。仕様自体が対象から外しています。
- (§2.5) AES でノンスを暗号化してワンタイム鍵を生成すること。参考のための背景で、この SDK は §2.6 の ChaCha20 の方法を使います。
- (§2.6) プロトコルの 64 ビットのノンスを 96 ビットに変換すること。プロトコルレベルの話で、QUIC は常に 96 ビットのノンスを渡します。
- (§2.4) プロトコルが指定する平文のパディング。プロトコルレベルの話で、QUIC はこの層ではパディングを加えません。
- (§2.6) プロトコルの文書が完全性の鍵に 256 ビットを割り当てなければならない(MUST)という規定。プロトコル仕様に対する要件です。
- (§2.7) ChaCha/Poly1305 の暗号スイートのための PRF。仕様は何も定義していません。
- (§2.8) P_MAX/A_MAX のメッセージサイズの上限。QUIC の AEAD の入力は MTU で制限され、256 GB / 2^64-1 の上限をはるかに下回ります。
- (§2.8) 別々の AAD 入力の連結と、AAD の構造化。アプリケーションやプロトコルの関心事で、API は 1 つの AAD のスパンを受け取ります。
- (§3) 性能についての助言(状態のコピーの再利用、多倍長整数ライブラリの選び方)。参考情報です。
- (§4) ノンスの生成方法(カウンター、LFSR、暗号化したカウンター)。運用者やプロトコル向けの指針で、ノンスの一意性そのものは 8439-006 です。
