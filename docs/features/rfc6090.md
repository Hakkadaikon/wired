# RFC 6090: 基本的な楕円曲線暗号アルゴリズム

仕様の本文(`tasks/specs/rfc6090.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。範囲は、SDK が提供する P-256 の体と群の演算(`src/crypto/asymmetric/ecc/p256/`)、その ECDH での使用(`p256_ecdhe.c`)、ECDSA (KT-I) の検証での使用に絞っています。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 26/28、間接 2、未テスト 0。**

## 対象外

クライアントだけの要件や運用者レベルの要件で、このサーバー SDK が実装しないものです。カバレッジの分母から除いています。

- (§3) y1 = 0 の点の 2 倍算。P-256 では到達しない。素数位数の群には位数 2 の点がない。
- (§3.1) 同次座標での群演算の式。SDK は代わりに Jacobian 座標(§3.2)を使う。
- (§3.3.1) 判別式の検査。パラメーターの生成の話であり、SDK は固定の NIST P-256 パラメーターを埋め込んでいる。
- (§3.3.2) パラメーターの選び方の指針(弱い曲線についての SHOULD NOT)。P-256 のパラメーターセットに固定で、パラメーターのネゴシエーションはない。
- (§4.2) コンパクト表現(x だけの公開鍵)と、それにはコンパクト出力を伴わなければならないという MUST。TLS 1.3 は非圧縮の点を運び、`p256_pubkey_decode` はそれ以外の形式をすべて拒否する。
- (§10.2) 交換した ECDH 公開鍵の認証。プロトコルの関心事(TLS 1.3 の CertificateVerify)。
- (§5.3, §5.5) KT-IV 署名と、KT-IV から KT-I への変換。提供していない。使うのは ECDSA (KT-I) の形式だけ。
- (§5.4.2) ランダムに選んだ k による署名生成。SDK は k を決定的に導出する(RFC 6979。rfc6979.md を参照)。
- (§7) IKE と IEEE P1363 への相互運用のための対応付け。この SDK の外のプロトコルプロファイル。
- (§10) セキュリティに関する考慮事項にある暗号解読の背景。参考情報。
- (Appendix B) ランダムな整数の生成。決定的な RFC 6979 のノンス生成に置き換えている。
- (Appendices C–F) コンパクト表現の証明、パラメーターセットの例、表記、擬似コード。参考情報。
