# RFC 6066 — TLS Extensions: Extension Definitions

EARS requirement ledger extracted from the spec text
(`tasks/specs/rfc6066.txt`, not in git). Each requirement carries the test
that demonstrates it; an unchecked box with no test line is an open gap.
This ledger is scoped to Server Name Indication (§3) as this server SDK
handles it; the other extensions this RFC defines (max_fragment_length,
client_certificate_url, trusted_ca_keys, truncated_hmac, status_request) are
grouped under Out of scope — `src/` ships none of them (grep-verified).
Status as of 2026-10.

Legend:

- `[x]` — demonstrated by the referenced test
- `[~]` — exercised indirectly (evidence line explains how; no dedicated test)
- `[ ]` — not demonstrated by any test yet

**Coverage: 13/14 tested, 1 indirect, 0 untested.**

## §3 Server Name Indication

- [x] 6066-001 (§3) The server shall accept a ClientHello "server_name"
  extension whose extension_data is a ServerNameList of one host_name
  entry: name_type(1)=0, a 16-bit length, and the hostname bytes.
  - test: `tests/tls/sni_test.c` — `test_sni_roundtrip`
  - test: `tests/tls/sni_extract_test.c` —
    `test_sni_extract_from_clienthello`
- [x] 6066-002 (§3) If the server_name extension's name_type is not
  host_name(0), then the server shall reject the entry.
  - test: `tests/tls/sni_test.c` — `test_sni_wrong_type`
  - test: `tests/tls/sni_extract_test.c` —
    `test_sni_extract_wrong_name_type`
- [x] 6066-003 (§3) If a length field inside the server_name extension
  overruns the available bytes, then the server shall reject the
  extension rather than over-read.
  - test: `tests/tls/sni_test.c` — `test_sni_truncated`
  - test: `tests/tls/sni_extract_test.c` — `test_sni_extract_truncated`
- [x] 6066-004 (§3) The server shall locate the server_name extension
  (extension_type 0x0000) inside a ClientHello's extensions block by its
  type, independent of the other extensions present.
  - test: `tests/tls/ch_ext_test.c` — `test_ch_ext_finds_alpn_and_sni`
- [~] 6066-005 (§3) The implementation shall not emit a ServerNameList
  that contains more than one name of the same name_type.
  - evidence: the only ServerNameList builder (`append_sni` in
    `src/tls/handshake/core/tls/clienthello.c`) wraps exactly one
    `tls_sni_encode` host_name entry; on receipt
    `tls_sni_decode`/`salpn_extract_sni` read only the first entry — no
    dedicated single-entry assertion.
- [x] 6066-006 (§3) If the server understood the server_name extension but
  does not recognize the server name, the server should either abort the
  handshake with a fatal unrecognized_name(112) alert or continue the
  handshake.
  - test: `tests/tls/sni_check_test.c` — `test_sni_check_mismatch`
  - test: `tests/tls/sdrv_test.c` — `test_sdrv_sni_mismatch`,
    `test_sdrv_enforce_sni_mismatch_rejects`, `test_sdrv_enforce_sni_match_ok`,
    `test_sdrv_enforce_sni_absent_ok`
  - test: `tests/tls/server_test.c` — `test_server_sni_mismatch_rejected`,
    `test_server_sni_match_accepted`, `test_server_sni_absent_accepted`
  - `salpn_sni_check` compares the extracted SNI against the leaf
    certificate and records match/mismatch/absent on `sdrv`'s
    `sni_outcome` (`sdrv_check_sni`, wired into
    `sdrv_recv_client_hello`). `sdrv_enforce_sni` is the caller-side
    opt-in that turns a mismatch into an actual abort
    (`TLS_ALERT_UNRECOGNIZED_NAME`); `wired_server_recv_initial`
    (`src/tls/handshake/roles/server/server.c`) calls it right after a
    successful `sdrv_recv_client_hello`, so this server SDK exercises
    the abort branch. A match or absent SNI takes the continue branch.
- [x] 6066-007 (§3) Where the server uses the ClientHello's server_name to
  guide its certificate selection or security policy, the server shall
  include a server_name extension with empty extension_data in its
  (extended) server hello (EncryptedExtensions in TLS 1.3).
  - test: `tests/tls/sni_srv_test.c` — `test_snisrv_ee_server_name_echo`
  - test: `tests/tls/eebuild_test.c` — `test_eebuild_server_name_groups`
  - `sdrv_ee_flags` (`sdrv_flight_emit.c`) sets `EEBUILD_SERVER_NAME`
    when `sni_outcome` is MATCH on a full handshake.
- [x] 6066-008 (§3) Currently, the only server name supported is the DNS
  hostname type; the associated data structure is a variable-length
  vector beginning with a 16-bit length.
  - test: `tests/tls/sni_test.c` — `test_sni_roundtrip`
- [x] 6066-009 (§3) When comparing the received HostName against its own
  identities, the server shall treat DNS hostnames as case-insensitive.
  - test: `tests/crypto/san_test.c` — `test_san_case_fold`
  - evidence: SNI itself is carried opaquely (`tls_sni_encode`/
    `tls_sni_decode` do not case-fold); case-insensitive comparison
    is demonstrated at the hostname-matching layer (RFC 6125 6.4.1), the
    consumer of the extracted SNI value.
- [x] 6066-010 (§3) If a resumption request's server_name extension
  contains a name different from the one the session was established
  under, then the server shall not accept the resumption and shall proceed
  with a full handshake.
  - test: `tests/tls/sdrv_test.c` — `test_sdrv_psk_bound_to_sni`
  - every ticket (`ticket_fill`, `respond_ticket.c`) seals
    `salpn_sni_digest` of the matched name; `sdrv_psk_open_usable`
    (`sdrv_early.c`) ignores a ticket whose digest differs, so the
    handshake proceeds as a full one. A name on only one side counts as
    different. (`resume_sni_compatible` is the client-side `resume`
    store's check and stays unwired: no shipping client resumes.)
- [x] 6066-014 (§1, §3) When resuming a session, the server shall not
  include a server_name extension in its server hello.
  - test: `tests/tls/sdrv_test.c` — `test_sdrv_psk_bound_to_sni`
  - `sdrv_ee_sni_flag` (`sdrv_flight_emit.c`) sets
    `EEBUILD_SERVER_NAME` only when `psk_accepted` is 0.
- [x] 6066-015 (§3) If the ServerNameList or a HostName is empty (below
  its `<1..2^16-1>` lower bound), then the server shall treat the
  server_name extension as malformed.
  - test: `tests/tls/sni_extract_test.c` — `test_sni_extract_empty`
  - test: `tests/tls/sni_check_test.c` — `test_sni_check_malformed`
  - test: `tests/tls/sni_srv_test.c` —
    `test_snisrv_malformed_sni_decode_error`
  - `salpn_sni_check` returns `SALPN_SNI_MALFORMED` and
    `sdrv_enforce_sni` closes with decode_error (`err_crypto(50)`,
    RFC 8446 6.2) on the `wired_srvboot_accept` path.

## §9 Error Alerts / §11.1 Security Considerations for server_name

- [x] 6066-011 (§11.1) The server shall not overflow a buffer whatever
  the values of the length fields in server_name.
  - test: `fuzz/fuzz_tlsmsg.c` — `fuzz_ch_extensions`
  - test: `tests/tls/sni_test.c` — `test_sni_truncated`
  - test: `tests/tls/sni_extract_test.c` — `test_sni_extract_truncated`
- [x] 6066-013 (§9) The server shall send the unrecognized_name(112) alert
  only after it has received an extended hello from its peer.
  - test: `tests/tls/sdrv_test.c` — `test_sdrv_enforce_sni_mismatch_rejects`
  - `TLS_ALERT_UNRECOGNIZED_NAME` (112) is defined in
    `src/common/diag/error/codes.h` and set on `sdrv.last_error` by
    `sdrv_enforce_sni` on a mismatch (only ever sent post-ClientHello,
    per `wired_server_recv_initial`'s call order); see 6066-006.

## Out of scope

Extensions this RFC defines that this server SDK does not implement
(grep-verified absent from `src/`), excluded from the coverage denominator:

- (§4) Maximum Fragment Length Negotiation — no `max_fragment_length`
  extension handling exists; QUIC's own datagram/packet sizing (RFC 9000
  §14, RFC 8899) governs record sizing instead.
- (§5) Client Certificate URLs (the `client_certificate_url` extension and
  the `CertificateURL`/`CertificateStatus` handshake messages) — not
  shipped; this server SDK does not perform client-certificate
  authentication via URL dereference.
- (§6) Trusted CA Indication (`trusted_ca_keys`) — not shipped.
- (§7) Truncated HMAC (`truncated_hmac`) — not shipped; QUIC 1.3's AEAD
  suites do not use HMAC-truncation-style MACs on records.
- (§8) Certificate Status Request (OCSP stapling, `status_request`) — not
  shipped.
- (§1, §2) Finished-hash inclusion of extension-specific handshake
  messages and the CertificateURL/CertificateStatus message types — no
  such message is shipped.
- (§3) Sender-side rules: the RECOMMENDATION that clients send
  server_name, the ASCII/no-trailing-dot/no-IP-literal HostName encoding,
  and reusing the same name on resumption and at the application layer —
  client behavior; the server may treat names as opaque.
- (§3) Future NameTypes beginning with a 16-bit length — a rule for
  future specifications.
- (§11.1) An application server that relies on the TLS server_name and
  an application-layer name being equal must compare them — application
  obligation; the SDK exposes no SNI to the application.
- (§9) certificate_unobtainable(111), bad_certificate_status_response(113)
  and bad_certificate_hash_value(114) — alerts of the unshipped §5/§8.
- (§10.1) pkipath MIME type encoding rules — belong to unshipped §5.
- (§11.2–§11.6) Security considerations for the five out-of-scope
  extensions above — inapplicable once the extensions themselves are not
  implemented.
