# RFC 9114: HTTP/3

仕様の本文(`tasks/specs/rfc9114.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 81/97、間接 15、未テスト 1。**

`src/app/http3/core/h3/` にある HTTP/3 の規則を判定する部品のいくつか(フレームの順序、擬似ヘッダーの組、Content-Length、SETTINGS の検査、プッシュ ID と GOAWAY の状態、制御ストリームの状態)には単体テストがありますが、サーバーの経路から呼ぶ箇所がありません。こうした未配線の部品のテストは、サーバーの動作の証拠としては挙げていません。以下の項目には、サーバーが実際にどの経路を通るかを書いています。

## 対象外

このサーバー SDK が実装しない、クライアントだけの要件や運用者レベルの要件です。カバレッジの分母には含めません。

- (§3.1) HTTP/3 エンドポイントの発見と Alt-Svc による通知。運用者・デプロイの関心事。
- (§3.1) URI のオリジンに対するサーバー証明書の検証。クライアントの動作。
- (§3.1) QUIC が失敗したときの、TCP ベースの HTTP へのフォールバック。クライアントの動作。
- (§3.1.2) サーバーが "https" 以外のスキームを処理する意思を持つことの確認。クライアントの動作。
- (§3.2) SNI など、対象ホストを示す情報の送信。クライアントの動作。
- (§3.3) 接続を新しいオリジンに再利用するときの証明書の再検証と、authority ごとの接続数の制限。クライアントの動作。
- (§3.3) 421 (Misdirected Request) による通知。オリジンの選択に関する任意のレスポンスで、アプリケーションのハンドラーに任せる。
- (§4.1) 1 つのストリームで 1 つのリクエストを送ること、送信後にリクエストストリームを閉じること、完全なレスポンスを保持すること。クライアントの動作。
- (§4.1) プッシュされたレスポンスの中の PUSH_PROMISE をエラーとして扱うこと。クライアントの動作で、サーバーはプッシュストリームを受け取らない。
- (§4.1.1) すでに処理中のリクエストを、キャンセルせずにステータスコードで応答すること。アプリケーションのハンドラーが選ぶ。
- (§4.1.1) H3_REQUEST_CANCELLED でリクエストをキャンセルし、H3_REQUEST_REJECTED を使わないこと、およびキャンセルされたリクエストの再試行の規則。クライアントの動作。
- (§4.1.2) 不正な形式のメッセージを転送しないこと。仲介者の動作で、wired はオリジンサーバー。
- (§4.1.2) 不正な形式のレスポンスを拒否すること。クライアントの動作。
- (§4.2, §4.3.1) 接続固有のフィールドの除去、HTTP/1.1 から変換するときの :authority の省略、HTTP/1.1 へ変換するときの Host の作成。仲介者の動作。
- (§4.3.1) リクエストを生成するときに Host より :authority を優先すること。クライアントの動作。
