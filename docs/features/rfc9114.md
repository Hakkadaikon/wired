# RFC 9114 — HTTP/3

EARS requirement ledger extracted from the spec text
(`tasks/specs/rfc9114.txt`, not in git). Each requirement carries the test
that demonstrates it; an unchecked box with no test line is an open gap.
Status as of 2026-10.

Legend:

- `[x]` — demonstrated by the referenced test
- `[~]` — exercised indirectly (evidence line explains how; no dedicated test)
- `[ ]` — not demonstrated by any test yet

**Coverage: 62/97 tested, 22 indirect, 13 untested.**

Several HTTP/3 rule classifiers under `src/app/http3/core/h3/` (frame
order, pseudo-header set, Content-Length, SETTINGS checks, push-ID and
GOAWAY state, control-stream state) have unit tests but no caller in the
server path. A test of such an unwired part is not cited as evidence for
what the server does; the items below say which path the server really
takes.

## Out of scope

Client-only or operator-level requirements this server SDK does not
implement, excluded from the coverage denominator:

- (§3.1) HTTP/3 endpoint discovery and Alt-Svc advertisement — operator /
  deployment concern.
- (§3.1) Verifying the server certificate against the URI's origin —
  client behavior.
- (§3.1) Falling back to TCP-based HTTP when QUIC fails — client behavior.
- (§3.1.2) Ensuring the server is willing to serve non-"https" schemes —
  client behavior.
- (§3.2) Sending SNI or another target-host indication — client behavior.
- (§3.3) Revalidating certificates when reusing a connection for a new
  origin, and limiting connections per authority — client behavior.
- (§3.3) Signalling 421 (Misdirected Request) — optional origin-selection
  response left to the application handler.
- (§4.1) Sending one request per stream, closing the request stream after
  sending, keeping complete responses — client behavior.
- (§4.1) Treating PUSH_PROMISE inside a pushed response as an error —
  client behavior; the server receives no push streams.
- (§4.1.1) Answering with a status code rather than cancelling a request
  already being processed — application handler choice.
- (§4.1.1) Cancelling requests with H3_REQUEST_CANCELLED, not using
  H3_REQUEST_REJECTED, and the retry rules for cancelled requests — client
  behavior.
- (§4.1.2) Not forwarding malformed messages — intermediary behavior; wired
  is an origin server.
- (§4.1.2) Rejecting malformed responses — client behavior.
- (§4.2, §4.3.1) Removing connection-specific fields, omitting :authority
  when translating HTTP/1.1, and creating Host when converting to HTTP/1.1
  — intermediary behavior.
- (§4.3.1) Preferring :authority over Host when generating requests —
  client behavior.
- (§4.4) CONNECT proxy tunneling to a TCP server (H3_CONNECT_ERROR,
  FIN/RST mapping, target-port restrictions) and the client's half-close
  advice — wired is an origin server; CONNECT is honored only as Extended
  CONNECT (RFC 9220 / WebTransport).
- (§4.6, §6.2.2, §7.2.3, §7.2.5) Server-push sending obligations
  (sequential push IDs, identical repeated promises, promise-before-
  reference ordering, push-ID reuse, single use in a push stream header,
  aborting or cancelling a promised push) — server push is not shipped.
- (§4.6) Consuming pushed responses (buffering push streams, sending
  CANCEL_PUSH, cacheability, authority validation of promises, storing in a
  cache) — client behavior.
- (§5.1) Opening a new connection near the idle timeout and gateway
  pre-warming — client / gateway behavior.
- (§5.2) Not initiating requests or promising pushes after a peer GOAWAY —
  the server initiates no requests and ships no push.
- (§5.2) Choosing the push ID in a client-sent GOAWAY — client behavior.
- (§5.4) Assuming requests may have been processed when a connection
  terminates without GOAWAY — client behavior.
- (§6.1) Treating server-initiated bidirectional streams as
  H3_STREAM_CREATION_ERROR — client behavior.
- (§6.2.2) Push stream header checks (duplicate push ID as H3_ID_ERROR,
  not aborting before the header) — client behavior.
- (§6.2.3) Reset codes for a sent reserved-type stream — the SDK sends no
  reserved-type streams.
- (§7.2.3) Not sending CANCEL_PUSH for a received push stream — client
  behavior.
- (§7.2.4.2) Storing server settings, complying with them when attempting
  0-RTT, and checking an accepting server's SETTINGS — client behavior.
- (§7.2.5) Checks on received PUSH_PROMISE frames (push ID beyond the
  advertised maximum, mismatched duplicate promises, PUSH_PROMISE on the
  control stream) — client behavior.
- (§7.2.6) Treating a GOAWAY with a wrong identifier type or on the wrong
  stream as an error — client behavior (the server-side ID-type rule is
  9114-036).
- (§9) Defining an extension setting's default so that omission disables
  it — rule for extension authors.
- (§10.4) Preventing tenants from pushing for others — server push is not
  shipped; multi-tenant hosting is operator policy.
- (§10.5) Limiting push IDs issued — client behavior.
- (§10.2, §10.5.2, §10.7, §10.10, §10.11) Cross-protocol attack notes,
  CONNECT proxy load, padding and traffic analysis, migration-aware
  logging, and privacy considerations — informational / operator guidance.
- (§11) IANA registrations and registry policies — process requirements
  for specification authors.
- (Appendix A) HTTP/2 transition guidance — informative.
