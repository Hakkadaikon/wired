# RFC 6125: サービス識別子の表現と検証

仕様の本文(`tasks/specs/rfc6125.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。この台帳の範囲は、このサーバー SDK が提供する SAN・ホスト名照合の API(`x509_san_matches`。RFC 5280 §4.2.1.6 の dNSName エントリだけ)です。この API は呼び出し側が呼ぶものです([セキュリティ](../security/README.md)を参照)。証明書発行の指針(§4。CA 向け)と、アプリケーションの入力からの参照識別子の構築(§6.1–§6.3。呼び出し側の、DNS-ID 以外の識別子のポリシー)は、提供している照合処理の振る舞いがかかわる範囲でだけ扱います。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 11/14、間接 3、未テスト 0。**

## §6.2.1 参照識別子のリストの構築

- [~] 6125-013 (§6.2.1) 実装は、提示された識別子の中の Common Name 以外の相対識別名(RDN)を確かめてはならない。
  - evidence: subject をたどる処理(`src/crypto/pki/encoding/x509/san_x509.c` の `atv_cn_value`)は id-at-commonName 属性に対してだけ値を返すので、ほかの RDN が比べられることはありません。値がホスト名に等しい CN 以外の RDN を提示するテストはありません。

## §6.3 照合の準備

- [x] 6125-002 (§6.3) 提示された識別子のどれかが参照識別子のどれかに一致すれば、検索は成功する。
  - test: `tests/crypto/san_test.c` — `test_exact_match`
  - test: `tests/crypto/san_test.c` — `test_wildcard_match`
  - vuln: V-0592, V-0632
- [x] 6125-003 (§6.3) 一致を見つけないまま参照識別子のリストを使い切った場合、検索は失敗する。
  - test: `tests/crypto/san_test.c` — `test_no_match`
  - test: `tests/crypto/san_test.c` — `test_no_san`
  - vuln: V-0579

## §6.4.1 従来のドメイン名のチェック

- [x] 6125-004 (§6.4.1) 実装は、ドメイン名のラベルを大文字と小文字を区別しない ASCII 比較で比べて、DNS ドメイン名の部分を照合しなければならない。
  - test: `tests/crypto/san_test.c` — `test_san_case_fold`
  - vuln: V-0530, V-0547, V-0561
- [x] 6125-005 (§6.4.1) 名前が一致するとみなすには、各ラベルが順に一致しなければならない(§6.4.3 のワイルドカードの規則に従う)。
  - test: `tests/crypto/san_test.c` — `test_no_match`
  - vuln: V-0579

## §6.4.2 国際化ドメイン名のチェック

- [x] 6125-006 (§6.4.2) DNS ドメイン名の部分が国際化ドメイン名であるとき、実装はチェックの前に U-label をすべて A-label に変換しなければならない。
  - test: `tests/tls/idna_test.c` — `test_idna_ulabel_to_alabel`,
    `test_idna_rejects`
  - test: `tests/tls/client_test.c` — `test_client_init_host_alabel`
  - `salpn_idna_to_ascii`(`src/tls/ext/salpn/idna.c`)は、ASCII でない各ラベルを Punycode でエンコードします(`salpn_punycode_encode`、RFC 3492 6.3。ベクターは RFC 3492 7.1 の (L)/(M) を Python のコーデックで導出し直したもの)。`client_init` はサーバー名をその形のまま SNI と SAN の照合の両方に使い、空の名前や変換できない名前を拒否します。そのため、クライアントのホスト名チェックが無効になることはありません。IDNA2008 のマッピングと妥当性の手順(NFC、大文字と小文字の畳み込み)は、呼び出し側の担当のままです。
- [~] 6125-014 (§6.4.2) 実装は、A-label を大文字と小文字を区別しない ASCII として、ラベルごとに比べなければならない。
  - evidence: A-label はただの ASCII なので、従来の名前(6125-004、`test_san_case_fold`)と同じ `ascii_dns_eq` の経路を通ります。`xn--` の名前を使うテストはありません。

## §6.4.3 ワイルドカード証明書のチェック

- [~] 6125-007 (§6.4.3 rule 1) 実装は、ワイルドカード文字が左端以外のラベルを構成している提示された識別子を、一致とするべきではない。
  - evidence: `is_wildcard`(`src/crypto/pki/encoding/x509/san.c`)は、左端のラベルの中でだけ `*` を探します。それより後ろのラベルの `*` は文字どおりに比べるので、`bar.*.example.net` は構造上一致しません。そうしたエントリを提示するテストはありません(`test_wildcard_no_nested` が確かめるのは、規則 2 の入れ子のホストです)。
- [x] 6125-008 (§6.4.3 rule 2) 提示された識別子の左端のラベルがワイルドカード文字だけからなる場合、実装は参照識別子の左端のラベルとだけ比べるべきである。
  - test: `tests/crypto/san_test.c` — `test_wildcard_match`
  - test: `tests/crypto/san_test.c` — `test_wildcard_no_nested`
  - vuln: V-0627, V-0632
- [x] 6125-009 (§6.4.3 rule 3) 実装は、ワイルドカード文字がラベルの唯一の文字ではない提示された識別子(例: `baz*.example.net`)を、一致としてもよい。
  - test: `tests/crypto/san_test.c` — `test_san_fragment_wildcard_match`
  - test: `tests/crypto/san_test.c` —
    `test_san_fragment_wildcard_no_match`
  - vuln: V-0525, V-0564, V-0628, V-0633
- [x] 6125-015 (§6.4.3 rule 3, §7.2) 実装は、ワイルドカード文字が国際化ドメイン名の A-label または U-label の中に埋め込まれている提示された識別子を、一致とするべきではない。
  - test: `tests/crypto/san_test.c` — `test_san_alabel_wildcard_no_match`
  - note: dNSName は IA5String なので、提示される DNS-ID は A-label しか持ちません。いずれにせよ、`is_wildcard` は `xn--` プレフィックスを持つ左端のラベルを拒否します。
  - vuln: V-0629

## 対象外

呼び出し側の識別子構築のポリシー、DNS 以外の識別子の型、CA 向けの発行の指針で、このサーバー SDK がコードとして実装しないものです(照合の API は、すでに決まったホスト名を証明書の dNSName SAN と照らすだけです)。カバレッジの分母から外しています。

- (§4) サーバーのアイデンティティの表現(証明書が含めるべき(SHOULD)識別子についての CA・発行者向けの規則。§4.1 規則 7 の「提示された識別子にワイルドカードを含めない」と §7.4 の単一の CN-ID を含む): 証明書の発行者向けの指針で、検証側のコードではありません。ワイルドカードの検証側は上の §6.4.3 です。
- (§5) サーバー証明書の要求: サービス運用者向けの CSR 作成の指針で、SDK のコードではありません。
- (§6.1) 概要、クライアントの検証手順の大筋: 説明のための枠組みで、その下の番号つきの小節が言い直しています。
- (§6.2) 参照識別子のリストの構築: 呼び出し側・アプリケーションのポリシーで決めることです(どのホスト名と照らすかを、URI、アカウントの設定、ユーザーの入力から導く)。SDK の `x509_san_matches` はすでに決まったホスト名を引数に取り、参照識別子を自分では構築しません。
- (§6.3、CN-ID とピン留めの側面) 「CN 以外の RDN について参照識別子を構築してはならない(MUST NOT)」と、証明書のピン留めへのフォールバック(§6.6.2、§6.6.4): ピン留めと参照識別子のポリシーは呼び出し側の責任です。照合処理が提供するのは、単一のホスト名を照合するプリミティブだけです。
- (§6.5, §6.5.1, §6.5.2) SRV-ID と URI-ID の照合(アプリケーションサービスタイプの部分): SDK が照合するのは DNS-ID 形式の dNSName SAN エントリだけです。SRV-ID と URI-ID は取り出しも比較もしません。
- (§6.6) 結果(一致あり、ピン留めした証明書、一致なし、フォールバック): 全体としての受け入れ・拒否の判断と人に向けたフォールバックの振る舞いは、`docs/security/protocols.md` の 「呼び出し側の責任」の注記のとおり、`x509_san_matches` を呼ぶ側の担当です。
- (§7.1) ピン留めした証明書: ピン留めのポリシーは呼び出し側・アプリケーションの関心事です。
- (§7.3) 国際化ドメイン名(セキュリティの議論): 説明のための記述です。変換の規則そのものは 6125-006 です。
- (付録 A、付録 B) ほかのプロトコルの RFC からのサンプル文と先行事例の抜粋: 規範ではありません。
- (§7.4) 複数の識別子: 証明書発行の実務(複数の DNS-ID を埋め込むか、SNI に頼るか)についての議論で、検証側のコードではありません。
