# RFC 9110: HTTPセマンティクス

仕様の本文(`tasks/specs/rfc9110.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。
RFC 9110 は多くの内容をまとめた仕様です。この台帳は、wired の HTTP/3 オリジンサーバーが表に出す部分(メソッド、ステータスコード、サーバーループのレベルでのフィールドの扱い)を扱い、残りは「対象外」にまとめています。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 42/43、間接 1、未テスト 0。**

## 対象外

この HTTP/3 サーバー SDK が実装しない、上位レイヤー、クライアント専用、仲介者、運用者向けの要件で、カバレッジの分母から外しています。

- (§1–§3) 導入、適合性の説明、用語、「サーバーは接続ごとにユーザーエージェントが 1 つだと仮定してはならない」: 定義か、アプリケーションの関心事です。
- (§4) URI スキームの定義、正規化と同等性、URI の生成、https の証明書検証: URI の生成とリソースの命名はアプリケーションの役割です。証明書検証はクライアントの動作です(サーバー側の TLS は TLS/PKI の台帳で扱います)。
- (§5.1–§5.3) 認識しないフィールドの転送とフィールド行の順序の保持: プロキシの動作です。
- (§5.5–§5.6) 新しいフィールド定義でのフィールド値の規則、リスト構文、空白の生成、quoted-string、コメント、HTTP-date のパース: フィールド値の生成とパースはアプリケーションが行います。SDK は日付、リスト、quoted-string の文法をパースしません。
- (§6.2) メッセージのバージョン選択: HTTP/3 はバージョンを運びません(暗黙に 3.0 です。RFC 9114 §4.3.2)。
- (§6.5, §6.6.2) トレーラーフィールドと Trailer フィールドの生成: SDK はトレーラーを生成しません。
- (§6.6.1) 受信時の Date の付加: 受信側のキャッシュとクライアントの動作です。
- (§7.2) Host の生成: ユーザーエージェントの動作です。
- (§7.3, §7.5–§7.7) キャッシュとプロキシへのルーティング、レスポンスの対応付け、Connection、Max-Forwards、Via、メッセージの変換: 仲介者の動作です。この SDK はオリジンサーバーだけを扱います。
- (§7.8, §15.2.2, §15.5.22) Upgrade、101、426: HTTP/3 には Upgrade がありません(RFC 9114 §4.5)。
- (§8.3.3, §8.4, §8.5, §8.7, §8.8) マルチパートのボディ、Content-Encoding、Content-Language、Content-Location、バリデーターのフィールド(Last-Modified、ETag): アプリケーションのハンドラーが受け持つ表現メタデータです。SDK はコンテンツコーディングを適用しません。
- (§8.6) ユーザーエージェントと転送する仲介者向けの Content-Length の規則: クライアントと仲介者の動作です。
- (§9.2) safe と idempotent のメソッドの性質と再試行の規則: クライアント、プロキシ、アプリケーション向けの意味上の指針です。
- (§9.3.1, §9.3.2, §9.3.5) GET/HEAD/DELETE のリクエストのコンテンツに頼ること: アプリケーションが決めることです。
- (§9.3.3–§9.3.5) POST、PUT、DELETE のステータスの選択: アプリケーションのハンドラーが選びます。
- (§9.3.6) CONNECT プロキシでのトンネルの転送とポートの制限: CONNECT のプロキシは提供していません(Extended CONNECT のみ)。
- (§9.3.7) OPTIONS のレスポンスのフィールド: アプリケーションが選びます。
- (§9.3.8) TRACE: 認識はしますが 405 で応答し、内容を反射することはありません。
- (§10.1.1) クライアント側の Expect の規則、プロキシによる 100-continue の転送、HTTP/1.0 の扱い: クライアント、プロキシ、HTTP/1.x の動作です。
- (§10.1.2–§10.1.5, §10.2.2–§10.2.4) From、Referer、TE の接続オプション、User-Agent、Location、Retry-After、Server の各フィールド: ユーザーエージェントかアプリケーションが生成し、消費します。SDK は Server フィールドを送りません。
- (§11) HTTP 認証と、401/407 のチャレンジのフィールド: アプリケーションの関心事です。
- (§12) コンテンツネゴシエーション、Accept-*、Vary: アプリケーションの関心事です。
- (§13) 条件付きリクエストと前提条件の評価: 提供していません。SDK は前提条件を評価せず、バリデーターも生成しません。フィールドはアプリケーションのハンドラーが参照します。
- (§14) 範囲リクエスト、Content-Range、206、416: 提供していません。
- (§15) クライアントによるステータスクラスと無効なコードの扱い、1xx のパースと転送: クライアントとプロキシの動作です。
- (§15.3–§15.5、ほかのコード) ステータスごとのフィールドとコンテンツ(205、リダイレクトの Location、304 のフィールドの組、401 のチャレンジ、Retry-After、プロキシからの 421): アプリケーションが選ぶか、クライアントとプロキシの動作です。
- (§15.6.6) 505: HTTP/3 には HTTP レベルでのバージョンネゴシエーションがありません。
- (§16) 拡張のレジストリと、新しいメソッド、コード、フィールド、スキームについての考慮事項: IANA と仕様の著者向けの指針です。
- (§17–§18) セキュリティと IANA に関する考慮事項: 参考の指針で、直接テストできるサーバーの動作はありません。
