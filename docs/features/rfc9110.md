# RFC 9110 — HTTP Semantics

EARS requirement ledger extracted from the spec text
(`tasks/specs/rfc9110.txt`, not in git). Each requirement carries the test
that demonstrates it; an unchecked box with no test line is an open gap.
RFC 9110 is an omnibus spec; this ledger covers the slice a wired HTTP/3
origin server surfaces (methods, status codes, field handling at the
server-loop level) — the rest is grouped under Out of scope.
Status as of 2026-10.

Legend:

- `[x]` — demonstrated by the referenced test
- `[~]` — exercised indirectly (evidence line explains how; no dedicated test)
- `[ ]` — not demonstrated by any test yet

**Coverage: 42/43 tested, 1 indirect, 0 untested.**

## §5 Fields

- [x] 9110-001 (§5.1) The server shall match received field names
  case-insensitively.
  - test: `tests/app/h3reqdrive_check_test.c` —
    `test_h3reqcheck_uppercase_name_rejected`
  - evidence: HTTP/3 carries names in lowercase (RFC 9114 §4.2): a name
    with an uppercase letter is rejected as malformed, so the exact
    lowercase compare (`h3reqdrive_line_name_is`) sees every name the
    server accepts.
- [x] 9110-002 (§5.1) When a request carries a header field the server does
  not recognize, the server shall ignore it and process the rest of the
  message.
  - test: `tests/app/h3reqdrive_test.c` — `test_reqdrive_curl_get`
- [x] 9110-032 (§5.3) The server shall not apply a request to the target
  resource until it has received the entire request header section.
  - test: `tests/app/srvloop_test.c` —
    `test_srvloop_fin_truncated_headers_marks_incomplete`
  - test: `tests/app/srvloop_test.c` —
    `test_srvloop_connect_drives_without_fin`
- [x] 9110-033 (§5.3) The server shall not send more than one field line
  with the same name in a response unless the field is list-based or
  Set-Cookie.
  - test: `tests/app/srvrun_test.c` — `test_srvrun_http_duplicate_field_is_500`
  - test: `tests/app/srvrun_test.c` — `test_srvrun_http_two_set_cookie_fields`
  - evidence: the SDK's own Date / Content-Length are skipped when the
    application set them (`srvrun_hdrs_sdk`), so they never double up.
- [x] 9110-003 (§5.4) If a received field line, value, or field section is

  - test: `tests/app/srvrun_test.c` — `test_srvrun_full_window_headers_get_431`

- [x] 9110-004 (§5.4) While a field value fits within the server's limits,

  - test: `tests/app/h3reqdrive_test.c` — `test_reqdrive_long_value_header`
- [x] 9110-034 (§5.5) When evaluating a received field value, the server

  - test: `tests/app/h3reqdrive_check_test.c` —

## Out of scope

Upper-layer, client-only, intermediary, or operator requirements this
HTTP/3 server SDK does not implement, excluded from the coverage
denominator:

- (§1–§3) Introduction, conformance prose, terminology, and "a server must
  not assume one user agent per connection" — definitional or application
  concerns.
- (§4) URI scheme definitions, normalization and equivalence, generating
  URIs, and https certificate verification — URI generation and resource
  naming are the application's; certificate verification is client
  behavior (the server's TLS side is covered by the TLS/PKI ledgers).
- (§5.1–§5.3) Forwarding unrecognized fields and preserving field-line
  order — proxy behavior.
- (§5.5–§5.6) Field-value rules for new field definitions, list syntax,
  whitespace generation, quoted strings, comments, and HTTP-date parsing —
  field values are generated and parsed by the application; the SDK
  parses no date, list, or quoted-string grammar.
- (§6.2) Message version selection — HTTP/3 carries no version (it is
  implicitly 3.0, RFC 9114 §4.3.2).
- (§6.5, §6.6.2) Generating trailer fields and the Trailer field — the SDK
  generates no trailers.
- (§6.6.1) Appending Date on receipt — recipient caches / clients.
- (§7.2) Generating Host — user agent behavior.
- (§7.3, §7.5–§7.7) Routing to caches and proxies, response correlation,
  Connection, Max-Forwards, Via, and message transformation —
  intermediary behavior; this SDK is an origin server only.
- (§7.8, §15.2.2, §15.5.22) Upgrade, 101, and 426 — HTTP/3 has no Upgrade
  (RFC 9114 §4.5).
- (§8.3.3, §8.4, §8.5, §8.7, §8.8) Multipart bodies, Content-Encoding,
  Content-Language, Content-Location, and validator fields
  (Last-Modified, ETag) — representation metadata owned by the
  application handler; the SDK applies no content coding.
- (§8.6) Content-Length rules for user agents and for forwarding
  intermediaries — client / intermediary behavior.
- (§9.2) Safe/idempotent method properties and retry rules — semantic
  guidance for clients, proxies and the application.
- (§9.3.1, §9.3.2, §9.3.5) Relying on content in GET/HEAD/DELETE requests —
  an application decision.
- (§9.3.3–§9.3.5) Status choices for POST, PUT, and DELETE — the
  application handler chooses them.
- (§9.3.6) Tunnel forwarding and port restrictions for CONNECT proxies —
  CONNECT proxying is not shipped (Extended CONNECT only).
- (§9.3.7) OPTIONS response fields — the application's choice.
- (§9.3.8) TRACE — recognized but answered 405, never reflected.
- (§10.1.1) Client Expect rules, proxy forwarding of 100-continue, and
  HTTP/1.0 handling — client / proxy / HTTP/1.x behavior.
- (§10.1.2–§10.1.5, §10.2.2–§10.2.4) From, Referer, TE connection option,
  User-Agent, Location, Retry-After, and Server fields — generated and
  consumed by the user agent or the application; the SDK sends no Server
  field.
- (§11) HTTP authentication, 401/407 challenge fields — application
  concern.
- (§12) Content negotiation, Accept-*, and Vary — application concern.
- (§13) Conditional requests and precondition evaluation — not shipped:
  the SDK evaluates no preconditions and generates no validators; the
  application handler sees the fields.
- (§14) Range requests, Content-Range, 206 and 416 — not shipped.
- (§15) Client handling of status classes and invalid codes, 1xx parsing
  and forwarding — client / proxy behavior.
- (§15.3–§15.5, other codes) Status-specific fields and content (205,
  redirect Location, 304 field set, 401 challenge, Retry-After, 421 from
  proxies) — chosen by the application, or client / proxy behavior.
- (§15.6.6) 505 — HTTP/3 has no HTTP-level version negotiation.
- (§16) Extension registries and considerations for new methods, codes,
  fields, and schemes — IANA/author guidance.
- (§17–§18) Security and IANA considerations — informational guidance with
  no directly testable server behavior.
