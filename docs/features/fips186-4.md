# FIPS 186-4 — Digital Signature Standard (DSS)

EARS requirement ledger extracted from the spec text
(`tasks/specs/fips186-4.txt`, not in git), scoped to ECDSA over the
P-256/P-384 prime-field curves as the SDK ships them: P-256 sign
(`src/crypto/asymmetric/ecc/p256sign/sign.c`, deterministic per-message
secret via RFC 6979) and verify
(`src/crypto/asymmetric/ecc/p256/ecdsa_verify.c`), and P-384 verify only
(`src/crypto/asymmetric/ecc/p384/ecdsa_verify.c` — the SDK never signs with
P-384), and P-521 verify only (`src/crypto/asymmetric/ecc/p521/`, added
2026-10-10 for certificate chains), plus the §5.5 constraints on the
RSASSA-PKCS1-v1_5/PSS verifiers in `src/crypto/asymmetric/rsa/`. RSA key
generation, plain DSA, ECDSA key-pair generation, and curves other than
P-256/P-384/P-521 are not shipped (confirmed by grepping
`src/crypto/asymmetric/`: `rsa/` holds PKCS#1/PSS verify only, no keygen or
DSA anywhere). Each requirement carries the test that demonstrates it; an
unchecked box with no test line is an open gap. Status as of 2026-10.

Legend:

- `[x]` — demonstrated by the referenced test
- `[~]` — exercised indirectly (evidence line explains how; no dedicated test)
- `[ ]` — not demonstrated by any test yet

**Coverage: 20/25 tested, 4 indirect, 1 untested.**

## §5.5 PKCS #1 (RSA signature verification)

- [x] F186-025 (§5.1, §5.5(b)) If an RSA signature is presented with a
  digest that is not from an approved hash function (SHA-256, SHA-384 or
  SHA-512), then the implementation shall reject it.
  - test: `tests/crypto/rsa_verify_test.c` — `test_rsa_pkcs1_sizes`
  - test: `tests/crypto/rsa_pss_test.c` — `test_rsa_pss_sizes`
- [~] F186-026 (§5.5(e)) Where RSASSA-PSS is verified, the implementation
  shall accept only a salt length sLen with 0 <= sLen <= hLen.
  - evidence: `rsa_pss_verify` (`src/crypto/asymmetric/rsa/pss.c`) fixes
    sLen = 32 = hLen for SHA-256; `tests/crypto/rsa_pss_test.c` —
    `test_rsa_pss_valid` and the Wycheproof sLen-32 files verify it, but no
    test presents a longer salt.
- [x] F186-027 (§5.5(f)) When verifying an RSASSA-PKCS1-v1_5 signature,
  the implementation shall take the hash only from the rightmost bytes of
  EM with no other information following it (here by comparing the whole
  re-encoded EM).
  - test: `tests/crypto/rsa_verify_test.c` — `test_rsa_pkcs1_tampered_sig`
  - test: `tests/crypto/wyc_rsa_pkcs1_test.c` — `test_wyc_rsa_pkcs1`

## §6.2 Private/Public Keys

- [~] F186-006 (§6.2) The implementation shall treat an ECDSA key pair as
  usable only for ECDSA digital signature generation and verification, not
  for any other purpose (e.g. key establishment).
  - evidence: the P-256/P-384 sign and verify entry points take raw
    scalar/point byte arrays and are called only from the TLS
    CertificateVerify path (`src/tls/`); no shared code path reuses an
    ECDSA key for key agreement. No dedicated unit test asserts the
    restriction, since it is an API-shape property rather than a runtime
    check.
F186-007 (§6.2.1, Appendix B.4, ECDSA private-key generation) — moved to
"Out of scope"; see below.

## §6.3 Secret Number Generation

- [x] F186-008 (§6.3) The implementation shall generate a new per-message
  secret number k prior to each signature generation, distinct from any
  other signature's k value derived from a different message.
  - test: `tests/crypto/rfc6979_test.c` — `test_rfc6979_sample_k`
  - test: `tests/crypto/p256sign_test.c` — `test_p256sign_ps_roundtrip`
- [x] F186-009 (§6.3, App. C.1) The implementation shall compute k^-1 mod
  n (and s^-1 mod n in verification), satisfying 1 = (k^-1 * k) mod n, by
  the Appendix C.1 algorithm or an equivalent one.
  - test: `tests/crypto/p256sign_test.c` — `test_p256sign_known_vector`
  - test: `tests/crypto/p256_field_test.c` — `test_p256_field_mont_inv_n`
  - test: `tests/crypto/p384_field_test.c` — `test_p384_field_mont_inv_n`
- [~] F186-010 (§6.3) The per-message secret number k and its uses shall be
  protected from unauthorized disclosure; k must not be reused across
  distinct messages under the same key.
  - evidence: k is derived deterministically per-message from
    (private key, message hash) via RFC 6979 HMAC_DRBG
    (`p256sign_k`, see the [RFC 6979 ledger](rfc6979.md)), which by
    construction yields a different k for a different hash input; no
    test directly demonstrates non-disclosure since k is never persisted
    or exposed by the API.

## §6.4 ECDSA Digital Signature Generation and Verification

- [x] F186-011 (§6.4) The implementation shall generate an ECDSA signature
  (r, s) using the domain parameters, the private key, the per-message
  secret number k, and an approved hash function (SHA-256 for P-256).
  - test: `tests/crypto/p256sign_test.c` — `test_p256sign_known_vector`
- [x] F186-012 (§6.4) The implementation shall verify an ECDSA signature
  using the same domain parameters and hash function that were used
  during signature generation.
  - test: `tests/crypto/ecdsa_verify_test.c` — `test_ecdsa_valid`
  - test: `tests/crypto/ecdsa_p384_verify_test.c` — `test_ecdsa_p384_valid`
- [x] F186-013 (§6.4) When the hash function's output is longer than the
  bit length of n, the implementation shall use only the left-most n bits
  of the hash output in the signature/verification calculation.
  - test: `tests/crypto/ecdsa_p521_verify_test.c` —
    `test_ecdsa_p521_digest_truncation` (a 528-bit digest whose low 7
    bits are cut off verifies; the cut is not byte-aligned for P-521)
  - test: `tests/crypto/bssl_ecdsa_test.c` — `test_bssl_ecdsa` (the
    71-byte-digest P-521 case of BoringSSL's ecdsa_verify_tests.txt)
  - test: `tests/crypto/wyc_ecdsa_test.c` — `test_wyc_ecdsa`
    (`ecdsa_secp384r1_sha512_test.json`: SHA-512 cut to 384 bits)
- [x] F186-014 (§6.4, referencing ANS X9.62) The implementation shall reject
  a signature verification whose flipped/tampered hash no longer matches
  the signed message.
  - test: `tests/crypto/ecdsa_verify_test.c` — `test_ecdsa_bad_hash`
  - test: `tests/crypto/ecdsa_p384_verify_test.c` — `test_ecdsa_p384_bad_hash`
- [x] F186-015 (§6.4, referencing ANS X9.62) The implementation shall reject
  a signature verification whose (r, s) has been tampered with.
  - test: `tests/crypto/ecdsa_verify_test.c` — `test_ecdsa_bad_sig`

## Out of scope

Client-only or operator-level requirements this server SDK does not
implement, excluded from the coverage denominator:

- (§4, Appendix A, Appendix C.3-C.10) DSA domain parameter generation and
  validation (finite-field cryptography), primality testing (Miller-Rabin,
  Lucas, Shawe-Taylor), and the DSA signature/verification algorithm
  itself — the SDK ships no DSA.
- (§5.1-§5.3, §5.5(a)(c)(d), Appendix B.3, Appendix C.9-C.10) RSA key
  pair criteria, generation (provable and probable primes), key secrecy,
  nlen choices for signing, single-scheme key use, two-prime moduli and
  RBG use — the SDK's `rsa/` directory contains PKCS#1 v1.5 and PSS
  signature *verification* only; it never generates or holds an RSA
  private key, and key usage is checked at the certificate layer.
- (§5.4) ANS X9.31 signatures — not shipped.
- (§6.1.1, §6.1.2) ECDSA domain parameter *generation* (as opposed to using
  a fixed NIST curve) and domain parameter management/registration — the
  SDK hard-codes the P-256/P-384 domain parameters from Appendix D rather
  than generating or negotiating its own.
- (§6.2.1 F186-007, Appendix B.4) ECDSA key pair *generation*, including
  generating d uniformly in [1, n-1] and computing Q = dG (both the
  extra-random-bits and testing-candidates methods) — the SDK loads
  existing key pairs from certificates/PEM; it does not mint new ECDSA
  keys. Confirmed by grep: no keygen routine exists under
  `src/crypto/asymmetric/ecc/`.
- (§6.2.2) Key pair management over a cryptoperiod — operator/PKI
  lifecycle concern, not implemented by a cryptographic primitive.
- (§6.5 F186-021, §3.1) Assurance that the intended signatory possesses a
  valid private key and domain parameters prior to signing — an
  operator/provisioning concern (how a private key reaches the signing
  process); not a property the signing primitive itself can enforce or a
  unit test can demonstrate, since by the time `p256sign_sign` is
  called the key is already a fixed byte array with no provenance to
  inspect.
- (§6.5 F186-022, §3.3) Assurance of the claimed signatory's identity,
  domain-parameter validity, public-key validity, and private-key
  possession at signing time, prior to accepting a verification as valid —
  a certificate-chain/PKI concern layered above the raw ECDSA verify
  primitive (see `docs/features/rfc5280.md` for the certificate-path
  side); the raw verify function here covers only the mathematical check
  (F186-012, F186-016..F186-019), which is the totality of what a
  standalone verify primitive can express.
- (Appendix B.5.1, B.5.2) The two RBG-based per-message secret number
  methods — not used; the SDK's deterministic RFC 6979 construction
  (`docs/features/rfc6979.md`) is tracked as the open gap F186-029.
- (§6.3) Protection of pre-computed k and k^-1 — k is never pre-computed.
- (§5.1, §6.1.1) CA guidance on choosing n or nlen relative to
  subscribers — CA/operator guidance.
- (Appendix D.1.2.1, D.1.2.2, D.1.3, D.2.1, D.2.2, D.3-D.10) Binary-field
  curves (B-xxx), Koblitz curves (K-xxx), P-192, P-224, their
  fast-reduction algorithms, normal bases and pseudo-random curve
  generation/verification — curves and fields the SDK does not implement
  (only P-256, P-384 and verify-only P-521 are shipped).
- (Appendix E) Proof that v = r in the DSA — mathematical justification
  for DSA, out of scope with DSA itself.
- (Appendix F) Calculating the required number of Miller-Rabin rounds —
  supports DSA/RSA prime generation, out of scope with those.
- (Appendix G) References — informative.
- (§1-§3, §4.4, general) Introduction, glossary, general key-management
  guidance (SP 800-57 cross-references), and the overall
  setup/generation/verification workflow figures — informative process
  description layered above the specific algorithm requirements already
  captured under §6.
