# FIPS 186-4: デジタル署名標準（DSS）

仕様の本文(`tasks/specs/fips186-4.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。対象は、SDK が提供する形の P-256/P-384 素体曲線上の ECDSA に絞っています。P-256 の署名(`src/crypto/asymmetric/ecc/p256sign/sign.c`。メッセージごとの秘密数は RFC 6979 で決定的に導出)と検証(`src/crypto/asymmetric/ecc/p256/ecdsa_verify.c`)、P-384 の検証のみ(`src/crypto/asymmetric/ecc/p384/ecdsa_verify.c`。SDK は P-384 で署名しません)、P-521 の検証のみ(`src/crypto/asymmetric/ecc/p521/`。証明書チェーンのために 2026-10-10 に追加)、それに `src/crypto/asymmetric/rsa/` の RSASSA-PKCS1-v1_5/PSS 検証器に対する §5.5 の制約です。RSA の鍵生成、素の DSA、ECDSA の鍵ペアの生成、P-256/P-384/P-521 以外の曲線は提供していません(`src/crypto/asymmetric/` を grep して確認しました。`rsa/` にあるのは PKCS#1/PSS の検証だけで、鍵生成や DSA はどこにもありません)。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 20/24、間接 4、未テスト 0。**

## 対象外

このサーバー SDK が実装しない、クライアント専用または運用者側の要件です。カバレッジの分母から除いています。

- (§6.3, §6.4, App. B.5 F186-029) 承認された RBG から付録 B.5.1/B.5.2 の方法で k を生成すること。意図して従っていないので、満たした要件ではなく既知の逸脱です。`p256sign_sign` は RFC 6979 の決定的 ECDSA で k を導出します。これは FIPS 186-4 では承認されておらず、FIPS 186-5 §6.3.2 では承認されています。この選択により、署名者は署名時に健全な RBG に頼らずに済みます。k は [1, n-1] の範囲に収まり(`tests/crypto/rfc6979_test.c` の `test_rfc6979_k_in_range_boundaries`)、RFC 6979 A.2.5 のベクターに一致します(`test_rfc6979_sample_k`)。SDK は FIPS 186-4 の認証(validation)を受けたとは主張しません。認証を必要とする配備では、運用者または認証の側が判断します。[既知の制限: 暗号プリミティブ](../security/limitations/crypto.md#3-暗号プリミティブ)に記録しています。

- (§4, Appendix A, Appendix C.3-C.10) DSA のドメインパラメーターの生成と妥当性確認(有限体暗号)、素数判定(Miller-Rabin、Lucas、Shawe-Taylor)、DSA の署名と検証のアルゴリズムそのもの。SDK は DSA を提供していません。
- (§5.1-§5.3, §5.5(a)(c)(d), Appendix B.3, Appendix C.9-C.10) RSA の鍵ペアの基準、生成(証明可能素数と確率的素数)、鍵の秘密性、署名に使う nlen の選択、1 つの方式だけでの鍵の使用、2 素数の法、RBG の使用。SDK の `rsa/` ディレクトリにあるのは PKCS#1 v1.5 と PSS の署名の*検証*だけです。RSA の秘密鍵を生成することも保持することもなく、鍵の用途は証明書の層で検査します。
- (§5.4) ANS X9.31 の署名。提供していません。
- (§6.1.1, §6.1.2) ECDSA のドメインパラメーターの*生成*(固定の NIST 曲線を使うのとは別のもの)と、ドメインパラメーターの管理と登録。SDK は、独自に生成したり交渉したりせず、付録 D の P-256/P-384 のドメインパラメーターを埋め込んでいます。
- (§6.2.1 F186-007, Appendix B.4) ECDSA の鍵ペアの*生成*。d を [1, n-1] から一様に生成し Q = dG を計算すること(余分なランダムビットを使う方法と候補を検査する方法の両方)を含みます。SDK は既存の鍵ペアを証明書や PEM から読み込むだけで、新しい ECDSA の鍵は作りません。grep で確認しました。`src/crypto/asymmetric/ecc/` の下に鍵生成のルーチンはありません。
- (§6.2.2) 暗号期間にわたる鍵ペアの管理。運用者や PKI のライフサイクルの関心事であり、暗号プリミティブが実装するものではありません。
- (§6.5 F186-021, §3.1) 署名の前に、意図された署名者が有効な秘密鍵とドメインパラメーターを持っていることの保証。運用者やプロビジョニングの関心事(秘密鍵がどうやって署名のプロセスに届くか)です。`p256sign_sign` が呼び出される時点で鍵はすでに由来を調べようのない固定のバイト配列なので、署名のプリミティブ自体が強制できる性質でも、単体テストで示せる性質でもありません。
- (§6.5 F186-022, §3.3) 検証を有効として受け入れる前の、署名者と称する者の身元、ドメインパラメーターの妥当性、公開鍵の妥当性、署名時に秘密鍵を持っていたことの保証。生の ECDSA 検証プリミティブの上の層にある、証明書チェーンや PKI の関心事です(証明書パスの側は `docs/features/rfc5280.md` を参照)。ここでの生の検証関数が扱うのは数学的な検査(F186-012、F186-016..F186-019)だけで、単独の検証プリミティブが表せるのはそれがすべてです。
