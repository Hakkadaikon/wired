# RFC 9218: HTTP の拡張可能な優先順位付けスキーム

仕様の本文(`tasks/specs/rfc9218.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。この台帳は HTTP/3 上のサーバー側を扱います。対象は優先度パラメーター(urgency / incremental)、Priority リクエストヘッダーフィールド、HTTP/3 の PRIORITY_UPDATE フレームです。HTTP/2 だけの動作、クライアントの動作、仲介者の動作は「対象外」にまとめています。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 18/22、間接 4、未テスト 0。**

## §4 優先度パラメーター

- [x] 9218-001 (§4) urgency または incremental の優先度パラメーターを含まない HTTP リクエストを受信したとき、サーバーはそれらのデフォルト値が指定されたものとして振る舞うべきである。
  - test: `tests/app/priority_test.c` — `test_priority_init_defaults`
  - test: `tests/app/h3reqdrive_test.c` — `test_reqdrive_priority_header`
- [x] 9218-002 (§4) サーバーは、優先度パラメーターの集合を、キーと値の組からなる Structured Fields の Dictionary として解析しなければならない。
  - test: `tests/app/priupdate_test.c` — `test_priupdate_sfv_dictionary_types` (`sfield_dict_next` による RFC 8941 4.2.2: アイテム、内部リスト、パラメーター、重複)
  - test: `tests/app/priupdate_test.c` —
    `test_priupdate_sfv_parse_failure_defaults`
  - test: `tests/app/h3reqdrive_test.c` — `test_reqdrive_priority_header`
- [x] 9218-003 (§4) 優先度パラメーターが未知のもの、範囲外の値を持つもの、想定外の型の値を持つもののいずれかである場合、サーバーはそのパラメーターを無視しなければならない。
  - test: `tests/app/priupdate_test.c` — `test_priupdate_sfv_dictionary_types` (`u=10`、`u=1.5`、`u=-1`、`u="1"`、`u=?1`、`i=1` は無視し、未知のキーは読み飛ばす)

## §4.1 緊急度

- [x] 9218-004 (§4.1) サーバーは、urgency (u) パラメーターを 0 以上 7 以下の Integer として受け入れ、デフォルト値を 3 としなければならない。
  - test: `tests/app/priupdate_test.c` — `test_priupdate_sfv_parse`
  - test: `tests/app/srvloop_priupdate_test.c` —
    `test_srvloop_priupdate_bad_value_defaults`
- [x] 9218-005 (§4.1) サーバーは、urgency の値が小さいほど優先度が高いものとして扱わなければならない。
  - test: `tests/app/h3prio_test.c` — `test_h3prio_order_by_urgency`

## §4.2 増分

- [x] 9218-006 (§4.2) サーバーは、incremental (i) パラメーターを Boolean として受け入れ、デフォルト値を false としなければならない。
  - test: `tests/app/priupdate_test.c` — `test_priupdate_sfv_parse`

## §5 Priority HTTP ヘッダーフィールド

- [x] 9218-007 (§5) リクエストが Priority ヘッダーフィールドを含むとき、サーバーはその優先度パラメーターを、そのリクエストの最初の優先度シグナルとして扱わなければならない。
  - test: `tests/app/h3reqdrive_test.c` — `test_reqdrive_priority_header`

## §7 PRIORITY_UPDATE フレーム

- [x] 9218-008 (§7) PRIORITY_UPDATE フレームの Priority Field Value で優先度パラメーターが省略されているとき、サーバーはそのパラメーターのデフォルト値を使わなければならない(このフレームはパラメーターの完全な集合を運ぶ)。

  - test: `tests/app/srvloop_priupdate_test.c` —

  - test: `tests/app/srvloop_priupdate_test.c` —

- [x] 9218-011 (§7.2) サーバーは、HTTP/3 の PRIORITY_UPDATE フレーム(タイプ 0xF0700(リクエスト)または 0xF0701(プッシュ)、Prioritized Element ID、Priority Field Value)を解析しなければならない。
  - test: `tests/app/priupdate_test.c` — `test_priupdate_roundtrip`
- [x] 9218-012 (§7.2) PRIORITY_UPDATE フレームが途切れている場合、または別のフレームタイプを持つ場合、サーバーはそれをデコードしてはならない。

## §10 サーバーのスケジューリング

- [x] 9218-017 (§10) サーバーは、可能な場合は urgency の高いレスポンスを urgency の低いレスポンスより先に送るべきである。
  - test: `tests/app/h3prio_test.c` — `test_h3prio_order_by_urgency`
  - test: `tests/app/srvloop_priupdate_test.c` — `test_srvloop_priority_of_open_stream` (スケジューラーが読む優先度)
  - evidence: `srvrun_pump_resp_round` (srvrun.c) は `resp[]` を巡るラウンドロビンの各周回で、スライスを送る前に `h3prio_order` で順序を並べ替える。
- [~] 9218-018 (§10) 同じ urgency の incremental なレスポンスが送信中である間、サーバーはそれらの間で帯域を分け合うべきである。
  - evidence: `srvrun_pump_resp_round` のラウンドロビンの周回は順序にかかわらず、使用中の `resp[]` スロットそれぞれからちょうど 1 スライスずつ送る(`srvrun_pump_round_gated` のドキュメント)。urgency による並べ替えが変えるのは周回の中でどのスロットが先に来るかであり、各スロットが周回ごとに得るスライス数ではないので、同じ urgency の incremental なレスポンスは周回を均等に分け合い続ける。
- [x] 9218-019 (§10) サーバーは、同じ urgency の incremental でないレスポンスを、ストリーム ID の昇順で処理するべきである。
  - test: `tests/app/h3prio_test.c` —
    `test_h3prio_order_non_incremental_stream_id_order`
- [~] 9218-020 (§10) 1 つの urgency レベルで incremental なレスポンスとそうでないレスポンスが混在するスケジューリングでは、サーバーは飢餓状態を避けるべきである。
  - evidence: ラウンドロビンの周回(9218-018 の evidence)は、`h3prio_order` が決める巡回順とは関係なく、使用中のスロットを周回ごとに 1 回ずつ巡る。そのため、incremental かどうかや urgency にかかわらず、ほかのスロットがあることでどのスロットも 2 周回以上飛ばされることはない。
- [~] 9218-021 (§10.1, §11) サーバーは、トンネルとして働くストリームにいくらかの帯域を割り当て、CONNECT ストリームのフレームもほかのストリームと同じ指針でスケジューリングするべきである。
  - evidence: 通常の CONNECT トンネル(connect.c の `h3_connect_req_ok` で検査する)は普通のリクエストストリーム上で動き、`srvrun_pump_resp_round` が urgency でスケジューリングするのと同じ `resp[]` テーブルを通じて応答する。この SDK にはトンネル用の別の帯域割り当て経路がないので、トンネルだけが割り当てから漏れることはない。一方、Extended CONNECT (WebTransport、RFC 9220) は `wtsend[]` 上で動く。RFC 9218 はこれに対する urgency シグナルを定めていない(`srvrun_pump_wt_round` のドキュメントを参照)ため、この要件の対象外である。

## 対象外

クライアントだけの要件、HTTP/2 だけの要件、仲介者の要件、運用者レベルの要件で、この HTTP/3 サーバー SDK が実装しないものです。カバレッジの分母から除いています。

- (§2.1) SETTINGS_NO_RFC7540_PRIORITIES と HTTP/2 の優先度シグナルの扱い。HTTP/2 だけのもので、wired は HTTP/3 を提供する。
- (§2.1.1) サーバーの SETTINGS が届くまで両方の種類のシグナルを送ること。クライアントの動作。
- (§4.1) メインリソースのデフォルトの urgency を選ぶことと、urgency 7 をバックグラウンドの処理のために取っておくこと。クライアントの動作。
- (§4.3) 新しい優先度パラメーターを定義するための指針。仕様の著者向け。
- (§5) Priority レスポンスヘッダーフィールドを生成し、そのキャッシュ可能性を制御すること。オリジンのアプリケーションや運用者の選択で、SDK のコードではない。
- (§7.1) HTTP/2 の PRIORITY_UPDATE フレームとそのストリーム状態の規則。HTTP/2 だけのもの。
- (§7.2) PRIORITY_UPDATE をクライアントの制御ストリームだけで送ることと、それを受信したクライアントの H3_FRAME_UNEXPECTED。クライアントの動作。
- (§8) クライアント主導とサーバー主導の優先度パラメーターのマージ。転送する仲介者の動作。
- (§9) クライアントが始めるリクエストのローカルなスケジューリング。クライアントの動作。
- (§10) サーバープッシュのスケジューリングと PUSH_PROMISE の Priority。サーバープッシュは提供していない。
- (§10.1, §13.1–§13.3) バックエンド接続のブロッキング、接続の合体での公平性、HTTP/1.x のバックエンド、意図的な不公平。仲介者や CDN の配備の関心事。
- (§12) トランスポートの再送とプローブのスケジューリングでストリームの優先度を考慮すること。必須ではないトランスポート層の考慮事項。
