# RFC 9312: QUIC トランスポートプロトコルの管理可能性

仕様の本文(`tasks/specs/rfc9312.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。RFC 9312 は Informational です。QUIC エンドポイントへの規範的な要件を集めたものではなく、ネットワーク運用者とミドルボックス・NAT・ファイアウォールの実装者に向けて、QUIC トラフィックをどう観測し、管理し、判断するかを示した指針です。この文書はネットワーク内の観測者の視点から「主に QUIC のワイヤイメージの暗号化されていない部分を検討する」と自らの位置づけを明記しています。その大半(トラフィック識別のヒューリスティック、NAT・ファイアウォールの状態のタイムアウト、DDoS の緩和、ECMP・QoS のルーティング、ICMP の扱い、ネットワーク運用者向けのパス MTU の指針)は、このサーバー SDK が実装しないネットワーク側の振る舞いを述べています。この RFC には BCP 14 のキーワードがないので、小文字の "must"/"should"/"recommended" を含む文と、§2.6 と §3.8.2 のエンドポイント向けの指針を要件の単位にしています。つまり、接続 ID によるサーバーのマッピングの露出と、レイテンシースピンビットのシグナリングへのサーバーの参加です。それ以外はすべて、節のまとまりごとに「対象外」にまとめています。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

## §2.6 接続 ID とリバインディング

- [x] 9312-005 (§2.6) サーバーが接続 ID にルーティング情報(サーバーのマッピング)を埋め込む構成では、サーバーはそのマッピングを選ばれた主体にだけ明かし、それ以外の観測者には接続 ID がランダムに見えるようにするべきである。
  - test: `tests/app/srvrun_test.c` — `test_srvrun_open_slot_xdp_embeds_core_id` (実際に使う受け入れ経路が発行する SCID は、鍵がなければコア ID を復元できない)
  - test: `tests/transport/xdpbpf_test.c` — `test_xdpbpf_prog_unmasks_routing_byte` (リファレンスのインタープリターで実行した BPF のステアリングプログラムが、ランダムな鍵のもとで 0..63 のすべてのコアへショートヘッダー・ロングヘッダーとも振り分ける), `test_xdpbpf_routing_byte_hides_core` (1 つのコア向けの CID で、先頭バイトが 100 種類を超える)
  - evidence: `srvrun_issue_cid` は `ncid_route_encode` でコア ID をマスクします。cid[0] = コア ID と cid[1..4] の鍵つき混合値の XOR で、鍵は `wired_srvxdpbpf_open` でプロセスごとに引く 192 ビットの値です。この鍵は BPF プログラムにだけ埋め込みます。これは難読化(乗算と xorshift による混合。BPF 側にはブロック暗号がありません)であり、QUIC-LB の AES による暗号化ではありません。多数の CID を観測して鍵を復元する攻撃は否定できていません。

## §3.8.2 パッシブな RTT 測定へのスピンビットの使用

- [x] 9312-001 (§3.8.2) サーバーがスピンビットのシグナリングに参加する構成では、サーバーは送信するスピンビットを、受信したピアのパケットのうちパケット番号が最大のもので観測したスピンビットの値に設定しなければならない(クライアントのように反転させるのではなく、そのまま返す)。
  - test: `tests/app/srvloop_test.c` — `test_srvloop_spin_reflects_highest_pn` (`srvloop_note_app_rx` がビットを記録し、`send_onertt_seal` が `spin_outgoing_ex` を送る)
- [~] 9312-002 (§3.8.2) サーバーは、スピンビットをショートヘッダーでだけ見せ、ロングヘッダーのパケットには含めないようにしなければならない。
  - evidence: ロングヘッダーを組み立てる処理は、形式上スピンビットを持ちません(RFC 9000 §17.2)。スピンビットを設定するのは、ショートヘッダーを組み立てる処理(`spin_outgoing`)だけです。
- [~] 9312-004 (§3.8.2) スピンへの参加が既定で有効になっている場合でも、サーバーは接続の少なくとも 8 分の 1 で、スピンビットへの参加をランダムに無効にしなければならない(そのまま返す・反転させる規則の代わりに、固定のビットかランダムに設定したビットを使う)。
  - evidence: `wired_server_init` は接続ごとに `spin_disabled` を引きます(16 分の 1。RFC 9000 §17.4 自身の MUST の値です)。クライアント自身の 16 分の 1 の抽選と合わせると 31/256 ≈ 12.1% になり(`tests/transport/spin_test.c` —
    `test_spin_disabled_combined_rate_matches_rfc9000_math`)、RFC 9312 が言い換えた「少なくとも 8 分の 1」をわずかに下回ります。
- [x] 9312-006 (§3.8.2) ある接続でスピンビットのシグナリングに参加しない間、サーバーはその接続の期間中は固定のスピン値を使うか、パケットごとにビットをランダムに設定しなければならない。
  - test: `tests/app/srvloop_test.c` — `test_srvloop_spin_reflects_highest_pn` (無効にした接続は、何を受け取っても spin 0 を送る)

## 対象外

ネットワーク運用者と経路上の観測者に向けた指針で、このサーバー SDK が実装もテストもしないものです。カバレッジの分母から外しています。

- (§1 はじめに) 文書の範囲をネットワーク管理の指針と位置づける記述と、暗号化されたトランスポート全般の管理可能性についての RFC 9065 への参照: 実装できる要件ではありません。
- (§2, §2.1–§2.8 QUIC ワイヤイメージの特徴) ワイヤイメージの中で観測できるヘッダーフィールド(バージョン、接続 ID、固定ビット、ヘッダーの種類、長さ、トークン、パケット番号、鍵フェーズ)、結合されたパケット、ポートの使い方の説明: RFC 9000 と RFC 9001 の台帳ですでに扱っているワイヤ形式の説明です。この文書が新しく加えるエンドポイントの要件はありません。
- (§3.1, §3.1.1, §3.1.2 QUIC トラフィックの識別) 経路上の観測者が QUIC トラフィック、ネゴシエートされたバージョン、無効な(ゴミの)最初のパケットを見分けるのに使いうるヒューリスティック: 観測者側の振る舞いで、サーバーの振る舞いではありません。
- (§3.2 接続の確認) 経路上の観測者がハンドシェイクの完了をどう検出するかの説明: 観測者側の推測で、サーバーの振る舞いではありません。
- (§3.3 確認応答トラフィックの区別) QUIC の暗号化されたペイロードに対して ACK だけのパケットを見分けるヒューリスティックがなぜ失敗するかの議論: 観測者側の限界で、サーバーの振る舞いではありません。
- (§3.4, §3.4.1 Server Name Indication) 経路上の観測者が暗号化されていない ClientHello から SNI を取り出すための指針(Initial シークレットの手作業での導出や CRYPTO フレームの再構成を含む): 観測者・ミドルボックスのコードで、サーバーエンドポイントの振る舞いではありません。サーバー自身の TLS・SNI の扱いは RFC 8446 と RFC 9001 の台帳で扱っています。
- (§3.5 フローの関連付け、§3.6 フローの終了、§3.7 フローの対称性の測定) 経路上の装置が接続 ID やトラフィックの対称性を使ってフローの状態を関連付けたり終了したりできるか(できないか)の議論: 観測者・ミドルボックスの振る舞いです。
- (§3.8.2) スピンビットのエッジからのパッシブな RTT の標本化、エッジを除外するヒューリスティック、上流と下流の部分ごとの RTT: 経路上の観測者による測定です。
- (§3.5) 「エンドポイントが意図してアドレスを変えるときは、接続 ID を変えなければならない」: サーバーはマイグレーションしません。この規則は RFC 9000 の台帳(§9.5)で扱っています。
- (§3.8, §3.8.1 往復時間の測定、初期 RTT の測定) パッシブなネットワーク観測者がフライトのタイミングからハンドシェイクの RTT をどう推測するかの議論: 観測者側の測定手法で、サーバーの振る舞いではありません。
- (§4.1 パッシブなネットワーク性能の測定とトラブルシューティング) パッシブに観測できる性能指標についてのネットワーク運用者向けの指針: 運用者側の話です。
- (§4.2 QUIC トラフィックのステートフルな扱い) 推奨される NAT・ファイアウォールの状態のタイムアウト値と、ステートフルなミドルボックスが接続 ID をフローのキーに使うことへの警告: ミドルボックス・NAT の設定の指針で、サーバーの振る舞いではありません。
- (§4.3 ルーティングの安定性を保つためのアドレスの書き換え) 接続 ID に基づくミドルボックスのアドレス書き換えがなぜ有害かの議論: ミドルボックス向けの指針です。
- (§4.4 サーバーとロードバランサーの協調) サーバープールの中で接続 ID の割り当てをロードバランサーと調整するための指針: 配置のトポロジーの指針で、単一のエンドポイントの振る舞いではありません。
- (§4.5 フィルタリングの振る舞い) いったん通してからフィルタするファイアウォールのパターンを避ける指針: ミドルボックス・ファイアウォールの設定の指針です。
- (§4.6 UDP のブロック、スロットリング、NAT バインディング) ネットワークが UDP・QUIC のトラフィックをどう絞り、どう遮断するべきかと、リフレクションを招きやすい NAT の送信元ポートのバインディングについての指針: ネットワーク運用者向けの指針です。
- (§4.7 DDoS の検出と緩和) ネットワーク内の DDoS 分類・緩和システム向けの指針(ネットワークの視点から Retry パケットを SYN cookie に相当するものとして使うことを含む): サーバー自身の Retry の生成は RFC 9000 の台帳で扱っています。この節の内容は、ネットワーク側の緩和の基盤についての話です。
- (§4.8 QoS の扱いと ECMP ルーティング) ネットワークの QoS・ECMP の扱いはパケット単位ではなくフロー単位で適用するべきだという指針: ネットワーク運用者・ルーター向けの指針です。
- (§4.9 ICMP メッセージの扱い、§4.10 パス MTU の誘導) ルーターが ICMP PTB メッセージを転送することと、ネットワーク運用者がパス MTU の上限を課すことについての指針: ネットワーク基盤向けの指針です。サーバー自身の DPLPMTUD の振る舞いは RFC 8899 の台帳で扱っています。
- (§6 セキュリティに関する考慮事項) ネットワークノードがバージョンの選択に影響を与えようとしないこと: 経路上のノード向けの指針です。残りは、ネットワーク内での QUIC の観測にかかわるセキュリティ上のトレードオフについての一般的な議論で、実装できるエンドポイントの要件ではありません。
