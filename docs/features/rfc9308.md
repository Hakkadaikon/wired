# RFC 9308 — Applicability of the QUIC Transport Protocol

EARS requirement ledger extracted from the spec text
(`tasks/specs/rfc9308.txt`, not in git). RFC 9308 is Informational: it is
guidance for application developers deciding how to use QUIC, not a set of
normative requirements on a QUIC transport implementation. Most of its
content — fallback strategy, stream-mapping advice, packetization/latency
trade-offs, port selection, versioning rollout strategy — is advice for an
application built on top of a QUIC SDK. This ledger keeps the sentences
that describe what a QUIC implementation or server endpoint should do
(0-RTT replay safety, idle timeout, stream properties and prioritization,
connection IDs, tokens, DSCP, version selection); as the RFC has no BCP 14
keywords, lowercase "must"/"should"/"recommended" sentences are the units.
Everything else is grouped under Out of scope by section family. Status as
of 2026-10.

Legend:

- `[x]` — demonstrated by the referenced test
- `[~]` — exercised indirectly (evidence line explains how; no dedicated test)
- `[ ]` — not demonstrated by any test yet

**Coverage: 6/10 tested, 2 indirect, 2 untested.**

## §3 0-RTT

- [x] 9308-001 (§3, §3.1) The server shall treat 0-RTT application data as
  possibly replayed and shall accept 0-RTT only under replay protection.
  - test: `tests/tls/sdrv_test.c` — `test_sdrv_early_data_replay_rejected`
  - test: `tests/transport/zerortt_seen_test.c` —
    `test_seen_replay_is_not_first_use`

## §3.2 Session Resumption versus Keep-Alive

- [ ] 9308-003 (§3.2, §10) The server shall compute the effective
  connection idle timeout as the minimum of the client's and server's
  advertised idle timeout values.
  - gap: `idledrive_effective` implements the minimum (unit-tested in
    `tests/transport/idlenego_test.c`), but no `src/` caller uses it; the
    server loop idles out at its own advertised 30 s
    (`WIRED_SRVRUN_IDLE_MS`).

## §9 Connection Migration

- [~] 9308-007 (§9) The server should use a non-zero-length connection ID.
  - evidence: `srvrun_issue_cid` generates a server connection ID of the
    configured `scid_len` (8 bytes in the examples and test fixtures); no
    check rejects a zero length and no test asserts it.

## §10 Connection Termination

- [ ] 9308-008 (§10) The server should let the application configure its
  maximum idle timeout and read the computed minimum for a connection.
  - gap: max_idle_timeout is the fixed `TP_MAX_IDLE_TIMEOUT` /
    `WIRED_SRVRUN_IDLE_MS`; `stp_limits` exposes no idle field and no API
    returns the negotiated minimum.

## §12 Quality of Service (QoS) and DSCP

- [~] 9308-011 (§12) The server should mark all packets belonging to one
  connection with a single DSCP.
  - evidence: the TOS / traffic-class byte is set once per socket
    (`wired_udp_ect0_enable`, ECT(0) with DSCP 0), so every packet of
    every connection carries the same DSCP; no test asserts the DSCP bits.

## Out of scope

Application- and operator-facing guidance this server SDK does not
implement or test, excluded from the coverage denominator:

- (§2, §17) Falling back from QUIC to TCP/TLS when UDP is blocked, and
  keeping the fallback's security properties — an application-layer
  decision outside the transport SDK.
- (§3) An application choosing to use 0-RTT and defining a replay-safety
  profile for its data (HTTP: RFC 8470) — application protocol design.
- (§3.1) "Once a server accepts 0-RTT data, there is no means of
  selectively discarding data" — a description of QUIC, not a
  requirement; protocols above may reject individual actions.
- (§3.2) Keep-alive policy: which side keeps the connection alive, the
  30-second NAT guidance, and using keep-alives only when continued
  communication is likely — the text calls this application specific;
  the application mapping decides.
- (§4, §4.1, §4.3–§4.5) Mapping application data to streams, using
  separate connections for different network treatment, assuming
  in-order reliable delivery, avoiding flow-control deadlocks for
  interdependent data, and stream-limit commitments — design guidance for
  protocols built on QUIC streams (e.g. HTTP/3).
- (§4.2) Retransmitting lost data before new data — restates the RFC 9000
  §13.3 recommendation, tracked in the RFC 9000 ledger.
- (§5) Frame bundling delay and application-controlled padding — optional
  interfaces ("can"), advisory for latency tuning.
- (§6) QUIC's error-signaling surface (CONNECTION_CLOSE, STOP_SENDING,
  RESET_STREAM) and the recommendation to signal detected errors —
  covered by the RFC 9000 ledger.
- (§7) Alternative ACK-frequency strategies — descriptive pointer to an
  extension draft.
- (§8, §8.1) UDP port registration, ALPN token registration, alternate
  endpoint discovery, and clients avoiding reflection-prone source ports
  — deployment and client concerns.
- (§9) Using a new connection ID when a client intentionally migrates,
  path validation, and the preferred-address mechanism — client behavior
  or covered by the RFC 9000 ledger.
- (§10) Termination modes and transport keep-alive mechanisms — covered by
  the RFC 9000 ledger.
- (§11, §11.1, §11.2) Connection ID routing through load balancers and
  migration-timing mitigations — operator / deployment-topology concerns.
- (§11.3) Redirecting connections with Retry across a server pool —
  operator deployment concern.
- (§12) Choosing the DSCP of the highest-priority multiplexed flow, and
  minimizing parallel connections to one server — the server marks no
  per-flow DSCP; client and application deployment guidance.
- (§13) Not using experimental versions long-term — registry / operator
  guidance.
- (§14) The three-stage rollout for a new QUIC version across a server
  fleet — deployment-process guidance (see the RFC 9368 ledger).
- (§15) When applications should prefer the datagram extension — covered
  by the RFC 9221 ledger where implemented.
- (§16) UDP port registration for applications — IANA / application
  guidance.
