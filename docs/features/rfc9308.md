# RFC 9308: QUIC トランスポートプロトコルの適用性

仕様の本文(`tasks/specs/rfc9308.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。RFC 9308 は Informational で、QUIC の使い方を決めるアプリケーション開発者向けの指針です。QUIC トランスポートの実装に対する規範的な要件の集まりではありません。内容の大半(フォールバックの戦略、ストリームへの対応付けの助言、パケット化とレイテンシーのトレードオフ、ポートの選択、バージョンの展開戦略)は、QUIC SDK の上に作るアプリケーションへの助言です。この台帳には、QUIC の実装やサーバーのエンドポイントがするべきことを述べた文(0-RTT のリプレイに対する安全性、アイドルタイムアウト、ストリームの性質と優先順位付け、接続 ID、トークン、DSCP、バージョンの選択)を残しています。この RFC には BCP 14 のキーワードがないため、小文字の "must"/"should"/"recommended" を含む文を単位にしています。それ以外はすべて、節のまとまりごとに「対象外」にまとめています。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。2026-10 時点の状況です。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 9/10、間接 1、未テスト 0。**

## §12 サービス品質(QoS)と DSCP

- [~] 9308-011 (§12) サーバーは 1 つの接続に属するすべてのパケットに同じ 1 つの DSCP を付けるべきである。
  - evidence: TOS / traffic class のバイトはソケットごとに一度だけ設定する(`wired_udp_ect0_enable`、DSCP 0 の ECT(0))。そのため、どの接続のどのパケットも同じ DSCP を持つ。DSCP のビットを確かめるテストはない。

## 対象外

このサーバー SDK が実装もテストもしない、アプリケーションと運用者向けの指針です。カバレッジの分母には含めません。

- (§2, §17) UDP がブロックされたときに QUIC から TCP/TLS へフォールバックすることと、フォールバック先のセキュリティ上の性質を保つこと。トランスポートの SDK の外にある、アプリケーション層の判断。
- (§3) アプリケーションが 0-RTT を使うと決め、自分のデータについてリプレイに対する安全性のプロファイルを定めること(HTTP では RFC 8470)。アプリケーションプロトコルの設計。
- (§3.1) "Once a server accepts 0-RTT data, there is no means of selectively discarding data"。QUIC の説明であって要件ではない。上位のプロトコルは個々の操作を拒否してもよい。
- (§3.2) キープアライブの方針。どちらの側が接続を維持するか、NAT についての 30 秒の指針、通信が続きそうなときだけキープアライブを使うこと。本文はこれをアプリケーション固有と呼んでおり、アプリケーションマッピング(QUIC 上のアプリケーションプロトコルの定義)が決める。
- (§4, §4.1, §4.3–§4.5) アプリケーションデータのストリームへの対応付け、ネットワーク上の扱いを変えるために接続を分けること、順序どおりの信頼性のある配送を前提にすること、互いに依存するデータでフロー制御のデッドロックを避けること、ストリーム数の上限の約束。QUIC のストリームの上に作るプロトコル(例: HTTP/3)向けの設計の指針。
- (§4.2) 新しいデータより先に失われたデータを再送すること。RFC 9000 §13.3 の推奨の再掲で、RFC 9000 の台帳で追っている。
- (§5) フレームをまとめるための遅延と、アプリケーションが制御するパディング。任意のインターフェース("can")で、レイテンシー調整のための助言。
- (§6) QUIC のエラー通知の手段(CONNECTION_CLOSE、STOP_SENDING、RESET_STREAM)と、検出したエラーを通知するようにという推奨。RFC 9000 の台帳で扱う。
- (§7) ACK の頻度についての別の戦略。拡張の draft を指す説明。
- (§8, §8.1) UDP ポートの登録、ALPN トークンの登録、代替エンドポイントの発見、クライアントがリフレクションに使われやすい送信元ポートを避けること。デプロイとクライアントの関心事。
- (§9) クライアントが意図して移行するときに新しい接続 ID を使うこと、パス検証、preferred address の仕組み。クライアントの振る舞いか、RFC 9000 の台帳で扱うもの。
- (§10) 終了の方式と、トランスポートのキープアライブの仕組み。RFC 9000 の台帳で扱う。
- (§11, §11.1, §11.2) ロードバランサーを通した接続 ID によるルーティングと、移行のタイミングに関する軽減策。運用者とデプロイの構成の関心事。
- (§11.3) サーバープールの中で Retry によって接続をリダイレクトすること。運用者のデプロイの関心事。
- (§12) 多重化したフローのうち最も優先度の高いものの DSCP を選ぶことと、1 つのサーバーへの並列の接続を最小にすること。サーバーはフローごとの DSCP を付けない。クライアントとアプリケーションのデプロイの指針。
- (§13) 実験的なバージョンを長期にわたって使わないこと。レジストリと運用者への指針。
- (§14) サーバー群全体に新しい QUIC のバージョンを展開する 3 段階の手順。デプロイの手順の指針(RFC 9368 の台帳を参照)。
- (§15) アプリケーションがデータグラム拡張を選ぶべき場合。実装している範囲は RFC 9221 の台帳で扱う。
- (§16) アプリケーションのための UDP ポートの登録。IANA とアプリケーションへの指針。
