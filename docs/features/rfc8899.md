# RFC 8899 — Packetization Layer Path MTU Discovery for Datagram Transports

EARS requirement ledger extracted from the spec text
(`tasks/specs/rfc8899.txt`, not in git). Each requirement carries the test
that demonstrates it; an unchecked box with no test line is an open gap.
This ledger covers the generic DPLPMTUD machinery a QUIC server carries —
the probe/ack/ceiling search around `pmtu` — as RFC 9000 §14.3 applies
it; the TCP- and SCTP-specific material is grouped under Out of scope.
Two drivers run the shared `pmtu` core: the HTTP/3 server loop
(`srvrun_pmtu.c`) and the transport-level `connrunner` (`pmtudrive.c`);
tests of either are cited.
Status as of 2026-10.

Legend:

- `[x]` — demonstrated by the referenced test
- `[~]` — exercised indirectly (evidence line explains how; no dedicated test)
- `[ ]` — not demonstrated by any test yet

**Coverage: 27/34 tested, 7 indirect, 0 untested.**

- [x] 8899-003 (§3.3) When feedback indicates a probe packet was received

  - test: `tests/transport/pmtu_test.c` — `test_pmtu_grow`
  - test: `tests/app/srvrun_test.c` — `test_srvrun_pmtu_ack_raises_validated`

- [x] 8899-005 (§3.4) The server should use probe packets that do not

  - test: `tests/transport/pmtudrive_test.c` —
    `test_pmtudrive_build_probe_ping_plus_padding`
  - test: `tests/transport/pmtudrive_test.c` —
    `test_pmtudrive_probe_frame_is_ping_plus_padding_only`
- [x] 8899-006 (§3.7, §8) While probe transmission is not controlled by the
  congestion controller, the server shall keep the interval between probe
  packets at least one RTT.
  - test: `tests/transport/pmtudrive_test.c` —
    `test_pmtudrive_next_probe_blocked_within_min_interval`
  - test: `tests/transport/pmtudrive_test.c` —
    `test_pmtudrive_next_probe_allowed_after_min_interval`
  - evidence: `next_probe_size`/`gate_min_interval`
    (`src/transport/conn/loop/connrunner/pmtudrive.c`) hold back a found
    probe candidate until `RTT_INITIAL_US` (RFC 9002's kInitialRtt, the
    connrunner's only available RTT floor — see the `ponytail:` note in
    `send.c` that no live RTT sample is wired into this loop yet) has
    elapsed since `pmtu_last_probe_sent_at`, a timestamp that survives
    ack/loss resolution unlike `pmtu`'s own `probe_sent_at`. The server
    loop (`srvrun_pmtu.c`) keeps one probe outstanding and sends the next
    only after its ACK or PROBE_TIMER, so its interval is at least one RTT
    as well.
- [~] 8899-007 (§3.7) The server shall not treat loss of a probe packet as
  an indication of congestion nor trigger a congestion control reaction.
  - evidence: `connrunner_track_loss_ex`
    (`src/transport/conn/loop/connrunner/send.c`) is the one loss-detection
    function the probe path (`connrunner_pmtu_reconcile`,
    `src/transport/conn/loop/connrunner/connrunner.c`) and the ordinary
    retransmission path share; neither call site invokes a congestion
    window reaction (`cc_on_loss`, `src/transport/recovery/congestion/
    cc/cc.c`) — that call exists only in the unrelated
    `src/app/http3/server/srvrun/srvrun.c` send-session ack/loss feed, which
    the pmtu probe's `sentmeta`-based tracking never enters. In the server
    loop the probe is tracked only by `pmtu_probe_pn`, outside the
    send-session log the congestion controller reads, and its timeout calls
    `pmtu_on_loss` alone (`srvrun_pmtu_reap_lost`). No
    dedicated test: proving a negative (no cwnd reaction) would need an
    integration harness wiring srvrun to a probe loss, disproportionate to
    the property's directness in the source.
- [~] 8899-008 (§3.7) When the PLPMTU or MPS is updated, the server shall
  not increase the congestion window measured in bytes.
  - test: `tests/transport/pmtu_test.c` —
    `test_pmtu_ack_does_not_grow_cc_cwnd`
  - evidence: `cc`'s cwnd formulas (`grow`/`grow_cubic`/`bbr_set_cwnd`
    in `src/transport/recovery/congestion/cc/cc.c`) read only the fixed
    `MAX_DATAGRAM` constant (`cc.h`), which does not include `pmtu.h`
    — there is no wiring through which a PLPMTU/MPS change could reach cwnd,
    so the property holds by construction rather than by an active check;
    the referenced test pins an independently-held `cc`'s `cwnd` as
    unchanged across a `pmtu_on_ack` that raises validated/MPS, as a
    regression guard against that independence being wired together later.
- [~] 8899-009 (§3.8) The server shall not apply flow control to probe
  packets that carry no user data.
  - evidence: `connrunner_pmtu_build_probe`
    (`src/transport/conn/loop/connrunner/pmtudrive.c`) builds the probe's
    plaintext directly as PING + PADDING bytes and calls no flow-control
    primitive (`flow_send_record`, `flow_credit_consume`, etc.,
    `src/transport/stream/flow/flow/`); those primitives are reached only
    from STREAM/CRYPTO data paths the probe never enters, so flow control
    structurally cannot apply to a probe. No dedicated test: the absence of
    a call is already evident from reading the probe-building function.
- [x] 8899-010 (§3.5) The server should utilize information about the
  maximum packet size the sender's local link can transmit when choosing
  the search ceiling.
  - test: `tests/transport/udp_test.c` — `test_udp_path_mtu_loopback`
  - test: `tests/transport/pmtu_test.c` — `test_pmtu_set_max_caps_search`
  - evidence: `srvrun_pmtu_start` (each new connection and each new path)
    reads the kernel path MTU toward the peer (`wired_udp_path_mtu`: route
    MTU of a throwaway connected socket, minus IP/UDP headers) into
    `pmtu_set_max`. The ceiling stays bounded by `PMTU_MAX` (1452), the
    SDK's 1500-byte datagram buffers: jumbo links are not probed above it.

- [x] 8899-015 (§4.3) When the current PLPMTU is detected as no longer

  - test: `tests/transport/pmtu_test.c` —
    `test_pmtu_black_hole_lowers_validated`
  - test: `tests/transport/pmtu_test.c` —
    `test_pmtu_state_event_table`
- [x] 8899-033 (§4.3) The server shall detect that the path no longer
  supports the current PLPMTU, by successive loss of PLPMTU-sized probes
  or by excessive loss of packets of that size.
  - test: `tests/app/srvrun_test.c` —
    `test_srvrun_pmtu_full_size_losses_black_hole`
  - test: `tests/app/srvrun_test.c` —
    `test_srvrun_pmtu_full_size_ack_not_black_hole`
  - test: `tests/transport/pmtu_test.c` — `test_pmtu_big_losses_black_hole`
  - test: `tests/transport/pmtu_test.c` —
    `test_pmtu_black_hole_lowers_validated`
  - evidence: the server's loss pass counts lost data packets too large for
    a BASE_PLPMTU packet that were sent after the newest such packet acked
    (`srvrun_pmtu_big_lost`/`srvrun_pmtu_note_ack`); MAX_PROBES of them drop
    the PLPMTU to BASE, shrink every send session's slice size, and split
    requeued slices to it (`wired_sendsess_take`). A probe at the validated
    size lost MAX_PROBES times is a black hole too (`pmtu_on_loss`).

## §5.3 Search to Increase the PLPMTU

- [x] 8899-028 (§5.3.1) The server shall select probe candidates above the
  validated PLPMTU and no larger than the ceiling learned from losses.
  - test: `tests/transport/pmtu_test.c` — `test_pmtu_grow`
  - test: `tests/transport/pmtu_test.c` —
    `test_pmtu_loss_retries_until_max_probes`
- [~] 8899-029 (§5.3.2) The server should select probe sizes that maximize
  the gain in PLPMTU from each search step.
  - evidence: the search uses fixed 64-byte steps (`PMTU_STEP`);
    `test_pmtu_grow` asserts the first step, but no test evaluates
    step-size optimality.
- [x] 8899-030 (§5.3.3, §8) The server shall make its decision to
  increase the PLPMTU resilient to inconsistent path information, such as
  probe loss for reasons other than packet size.
  - test: `tests/app/srvrun_test.c` — `test_srvrun_pmtu_lost_probe_retried`
  - test: `tests/app/srvrun_test.c` —
    `test_srvrun_pmtu_raise_timer_resumes_search`
  - evidence: one lost probe is retried rather than capping the search
    (8899-020), and a cap is lifted again by the PMTU_RAISE_TIMER.
- [x] 8899-034 (§3) When the path changes, the server should re-validate
  the PLPMTU instead of keeping the size confirmed on the old path.
  - test: `tests/app/srvrun_test.c` — `test_srvrun_path_move_resets_pmtu`
  - evidence: `srvrun_path_move` calls `srvrun_pmtu_path_reset`, which
    restarts the search at BASE_PLPMTU (and the slice size at the base MPS)
    whenever the send path moves to another local/remote address pair.

## §8 Security Considerations

- [~] 8899-031 (§8) The server shall confirm probe reception by a method
  protected from off-path packet injection.
  - evidence: probe acknowledgments arrive in AEAD-protected ACK frames
    bound to the connection, which an off-path attacker cannot forge; no
    dedicated forgery test.

## Out of scope

TCP/SCTP-specific methods, PTB processing (which §4.6.1 permits omitting),
and requirements on layers this SDK does not ship, excluded from the
coverage denominator:

- (§3.6, §4.6, §6.1.6, §8) Validation and use of ICMP PTB messages — wired
  ignores PTB messages entirely, the simple-implementation option §4.6.1
  explicitly permits; nothing is derived from PTB_SIZE.
- (§1.3, §2) Requirements quoted from other documents (BCP 145, DCCP,
  RFC 4821 link MTU enforcement) — informative restatements, not
  requirements of this document.
- (§3.7) Adapting a packet-count congestion window to the real packet
  size — the congestion window here is kept in bytes.
- (§5) Performing DPLPMTUD at only one layer — guidance to upper layers
  and applications running over QUIC.
- (§3.9) Sharing the discovered PLPMTU through the IP-layer cache with
  other PL instances — cross-flow caching is not shipped.
- (§4.4) Segmenting or resegmenting data blocks larger than the MPS —
  QUIC streams already segment, and QUIC datagrams cannot be fragmented
  (RFC 9221).
- (§5.2) A below-base fallback out of the ERROR phase (MIN_PLPMTU below
  BASE_PLPMTU, endpoint fragmentation) — QUIC requires 1200-byte UDP
  payload support (RFC 9000 §14); the ERROR phase itself only halts
  sending, tracked in `rfc9000.md` §14.
- (§5.2) The DISABLED state and re-entry after loss of connectivity — a
  QUIC connection that loses connectivity closes; discovery does not
  outlive it.
- (§6.1) Application-implemented DPLPMTUD over UDP or UDP-Lite — wired's
  packetization layer is QUIC, not a bare-UDP application.
- (§6.2) DPLPMTUD for SCTP, SCTP/UDP, and SCTP/DTLS — SCTP is not shipped.
- (§1.2, RFC 4821 material) PLPMTUD for TCP — TCP is not shipped.
