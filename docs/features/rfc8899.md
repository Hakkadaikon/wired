# RFC 8899: データグラムトランスポートのためのパケット化レイヤーパスMTU探索(PLPMTUD)

仕様の本文(`tasks/specs/rfc8899.txt`。git には含まない)から抽出した EARS 形式の要件台帳です。各要件には、それを確かめるテストを付けています。チェックがなくテスト行もない項目は、未解決のギャップです。
この台帳は、RFC 9000 §14.3 が適用するかたちで QUIC サーバーが持つ汎用の DPLPMTUD の仕組み(`pmtu` を中心とするプローブ、ACK、上限の探索)を扱います。TCP と SCTP に固有の内容は「対象外」にまとめています。
HTTP/3 のサーバーループ(`srvrun_pmtu.c`)が共有の `pmtu` コアを動かします。`pmtu` コア単体のテストはサーバーループのテストか evidence 行と並べて挙げています。
2026-10 時点の状況です。

凡例:

- `[x]`: 挙げたテストで確認済み
- `[~]`: 間接的に確認(専用のテストはなく、evidence 行で確かめ方を説明)
- `[ ]`: まだどのテストでも確認していない

**カバレッジ: テスト済み 26/34、間接 8、未テスト 0。**

- [~] 8899-007 (§3.7) サーバーは、プローブパケットの喪失を輻輳の兆候として扱ってはならず、輻輳制御の反応を引き起こしてはならない。

- [~] 8899-008 (§3.7) PLPMTU または MPS が更新されたとき、サーバーはバイト単位で測る輻輳ウィンドウを増やしてはならない。
  - test: `tests/transport/pmtu_test.c` —
    `test_pmtu_ack_does_not_grow_cc_cwnd`
  - evidence: `cc` の cwnd の計算式(`src/transport/recovery/congestion/cc/cc.c` の `grow`/`grow_cubic`/`bbr_set_cwnd`)は固定の定数 `MAX_DATAGRAM`(`cc.h`)だけを読み、`cc.h` は `pmtu.h` を include しません。PLPMTU や MPS の変化が cwnd に届く経路がないので、この性質は能動的な検査ではなく構造によって成り立ちます。挙げたテストは、独立に保持した `cc` の `cwnd` が、validated と MPS を上げる `pmtu_on_ack` の前後で変わらないことを固定し、あとでこの独立性を崩す配線が入ったときのリグレッションを検出します。
- [~] 8899-009 (§3.8) サーバーは、ユーザーデータを運ばないプローブパケットにフロー制御を適用してはならない。
  - evidence: `srvrun_pmtu_probe_payload`(`srvrun_pmtu.c`)はプローブの平文を PING と PADDING のバイト列として直接組み立て、`srvrun_seal_pmtu_probe` は接続やストリームのクレジットに触れずにそれを暗号化します。クレジットを消費するのは STREAM データの経路だけなので、構造上フロー制御はプローブに適用されません。専用のテストはありません。呼び出しがないことは、プローブを組み立てる関数を読めば分かるためです。
- [x] 8899-010 (§3.5) サーバーは、探索の上限を選ぶときに、送信側のローカルリンクが送れる最大パケットサイズの情報を利用するべきである。
  - test: `tests/transport/udp_test.c` — `test_udp_path_mtu_loopback`
  - test: `tests/transport/pmtu_test.c` — `test_pmtu_set_max_caps_search`
  - evidence: `srvrun_pmtu_start`(新しい接続と新しいパスのたびに呼ぶ)は、ピアへのカーネルのパス MTU(`wired_udp_path_mtu`: 使い捨ての接続済みソケットの経路 MTU から IP/UDP ヘッダーを引いた値)を `pmtu_set_max` に読み込みます。上限は `PMTU_MAX`(1452)、つまり SDK の 1500 バイトのデータグラムバッファーで抑えられたままで、ジャンボフレームのリンクでもこれを超えてはプローブしません。

## §8 セキュリティに関する考慮事項

- [~] 8899-031 (§8) サーバーは、オフパスからのパケット注入に対して保護された方法で、プローブの受信を確かめなければならない。
  - evidence: プローブの確認応答は接続に結び付いた AEAD 保護の ACK フレームで届き、オフパスの攻撃者は偽造できません。偽造を試す専用のテストはありません。

## 対象外

TCP と SCTP に固有の方式、PTB の処理(§4.6.1 が省略を認めている)、この SDK が提供しないレイヤーへの要件は、カバレッジの分母から外しています。

- (§3.6, §4.6, §6.1.6, §8) ICMP PTB メッセージの検証と利用: wired は PTB メッセージをすべて無視します。これは §4.6.1 が明示的に認める簡易実装の選択肢で、PTB_SIZE からは何も導きません。
- (§1.3, §2) ほかの文書(BCP 145、DCCP、RFC 4821 のリンク MTU の強制)から引用した要件: 参考としての言い直しで、この文書の要件ではありません。
- (§3.7) パケット数で数える輻輳ウィンドウを実際のパケットサイズに合わせること: ここでの輻輳ウィンドウはバイト単位で保持しています。
- (§5) DPLPMTUD を 1 つのレイヤーだけで行うこと: QUIC の上で動く上位レイヤーとアプリケーションへの指針です。
- (§3.9) 見つけた PLPMTU を IP 層のキャッシュでほかの PL インスタンスと共有すること: フローをまたぐキャッシュは提供していません。
- (§4.4) MPS より大きいデータブロックのセグメント化と再セグメント化: QUIC のストリームはすでにセグメント化し、QUIC のデータグラムはフラグメント化できません(RFC 9221)。
- (§5.2) ERROR フェーズから基本サイズより下へのフォールバック(BASE_PLPMTU より小さい MIN_PLPMTU、エンドポイントによるフラグメンテーション): QUIC は 1200 バイトの UDP ペイロードへの対応を必須としています(RFC 9000 §14)。ERROR フェーズ自体は送信を止めるだけで、`rfc9000.md` の §14 で追跡しています。
- (§5.2) DISABLED 状態と、接続性を失ったあとの再突入: 接続性を失った QUIC の接続は閉じ、探索がそれより長く続くことはありません。
- (§6.1) UDP または UDP-Lite の上でアプリケーションが実装する DPLPMTUD: wired のパケット化レイヤーは QUIC で、素の UDP のアプリケーションではありません。
- (§6.2) SCTP、SCTP/UDP、SCTP/DTLS 向けの DPLPMTUD: SCTP は提供していません。
- (§1.2、RFC 4821 の内容) TCP 向けの PLPMTUD: TCP は提供していません。
