## 1. 対象

Track 切り替えは、購読者が 1 つのストリームの別版(高画質と低画質の映像など)の間を移る仕組みである。moqtail 互換の SWITCH_FROM(0x24)と SSTS(sender-side track switching: 0x41、Setup Option 0x09)の拡張は、`wired_moqt_hub.switch_track` と `ssts_algs` / `ssts_alg_n` で有効にしたときだけ動き、draft-22 のセッションでだけ使える。どれも draft-22 には含まれない。

| 語 | 意味 |
|---|---|
| SWITCH_FROM | 購読者が求める切り替え。古い Track A から新しい Track B へ、境界の Group G で移る |
| Hard | B の Group G がハブに届いた時点で A を終えるモード |
| Soft | A が最後の Group を先に終えるのを待つモード |
| SSTS | ハブが切り替えセットについて、購読者の接続で測った値をもとに Group ごとに切り替える仕組み |
| 切り替えセット | 別版の Track の集まり |
| ティア | 品質の段階 |
| ペーシングセット | その Group によってティアの変更を決めるセット 1 つ |
| busy shed | トランスポートが拒み続けたストリームを lossy relay がリセットすること([2.13](#213-busy-shed-はネットワークが混んでいなくても品質を下げることがある)) |
| reliable stall | データが残っているのに `WIRED_MOQTREL_STALL_MS` の間データを受け取らなかった購読者を、信頼リングが外すこと |

ほかの用語は [MoQT の Track 切り替え](../../features/moqt-track-switching.md) と [既知の制限: MoQT](moqt.md#1-用語) で定義している。

## 2. 制限

### 2.1 ループバックでしかテストしていない

影響: moqtail やほかの第三者の相手と組み合わせて使う人。

コーデックは moqtail-rs の単体テストのバイト列に固定し、ハブの動作はプロセス内でテストしている。moqtail やほかの第三者の相手と動かしたことはない。

参照: [draft-moq-transport-22.md](../../features/draft-moq-transport-22.md) MQ22-X13

### 2.2 背圧はペーシングセットの Group ごとと 100 ミリ秒の tick ごとにだけ測る

影響: `wired_moqt_tick` をまれにしか呼ばないアプリケーション。

ティアはセッションのペーシングセット(背圧を測る有効なセットのうちスロットが最も小さいもの)の Group ごとと、100 ミリ秒ごとの `wired_moqt_tick` で動く。moqtail と同じである。tick はサーバーのループが `wired_moqt_tick` を呼ぶ頻度でしか回らない。

参照: `moqtssts_run.c` の先頭のコメント

### 2.3 背圧が混雑として数えるもの

影響: 切り替えセットの Track とチャットや音声を混ぜたセッション。

| 入力 | 数え方 |
|---|---|
| 深さ | 購読者へ開いているストリームの数。ストリームを開いてから、ハブがパブリッシャーの FIN を中継するまで数える(購読者の確認応答までではない) |
| リセット | ハブ自身がそのセッションのストリームをリセットした回数。チャットや音声を含め、そのセッションのどのストリームでも数える(moqtail が接続のどのストリームでも数えるため) |

数えるリセットは busy shed、DELIVERY_TIMEOUT、reliable stall である。これらを数えるのは、セッションが背圧を測るセットを持っている間だけで、moqtail 自身の破棄タイムアウトが起こすリセットの代わりになる。

参照: `moqtssts_run.c` の先頭のコメント

### 2.4 既定のアルゴリズムの見積もりは輻輳ウィンドウに従う

影響: 品質をすぐに上げたい購読者。

予算は `ssts_cap_kbps` と、購読者の接続の配送レートの見積もりのうち、厳しいほうである。見積もりは BBR のボトルネック帯域で、BBR でなければ cwnd を平滑化 RTT で割った値である。探査はしない。

下位のメンバーだけを受け取る購読者は接続をアプリケーション律速に保つので、見積もりはゆっくりとしか上がらず、ウィンドウが大きくなるまで割り当てが低いままのことがある。最初の RTT の標本が取れるまでは見積もりが不明で、上限だけが効く。

参照: `wired_server_wt_est_kbps`

### 2.5 PUBLISH_OK / REQUEST_OK の中の SWITCHING_SET_ASSIGNMENT には対応しない

影響: そこにこれを入れる moqtail のクライアント。

moqtail はこれらのメッセージで受け付けるが、ハブが受け付けるのは SUBSCRIBE と、購読の REQUEST_UPDATE の中だけである。それ以外の場所では許されたパラメーターではない(復号時の違反になる)。

参照: `MOQCTL_PARAM_RULES`

### 2.6 フィルと FETCH は SSTS で絞らない

影響: 履歴も求めるメンバー。

Group の途中で(SUBSCRIBE か REQUEST_UPDATE で)参加したメンバーには、その Track の最大の Group をすぐに決定済みにする(記録済みの決定が優先する)。そのため信頼リングがその Group を再送する。フィルと FETCH はセットの決定にかかわらずすべての Group を返す。

参照: `moqtss_on_subscribe`

### 2.7 切り替えの促し、GOP の延長、遅延の予算はない

影響: なし。

これらは「Art of the Switch」の講演で出たアイデアで、moqtail のコードにもないので対象外である。

### 2.8 1 つの購読で SWITCH_FROM と SSTS は組み合わせられない

影響: 両方を試すクライアント。

切り替えセットのメンバーを指定した SWITCH_FROM は INVALID_SWITCH(0x32)で断る。使えるのはセット(送信側)か明示的な切り替え(受信側)のどちらか一方である。

参照: `moqtswitch.c`

### 2.9 FILL_PARAMETERS 付きの SWITCH_FROM は断る

影響: 新しい Track の履歴を求めるクライアント。

INVALID_SWITCH(0x32)を返す。切り替え先の購読は境界の Group G から始まり、履歴のフィルは受け取らない。

参照: `test_moqtrun_switch_fill_refused`

### 2.10 Hard モードは Group G が購読者ではなくハブに届いた時点で切る

影響: 混雑した接続での Hard の切り替え。

新しい Track の Largest Group が G 以上になった時点(ストリームでもデータグラムでも)で、古い購読を終える。ハブが新しい Group G のストリームを購読者へまだ開けないとき(ストリームのクレジットがない、または滞留がある)は、送信中の古い Group を先にリセットするので、明示的な欠落ができる。新しい Group G はそのあと遅れて開いたストリームで届き、最初の Object を失うことがある。

参照: `moqtswitch.c`

### 2.11 一時停止した購読はスロットを持ち続ける

影響: 購読者やリクエストの容量に近いハブ。

Publish Done(フラグ 0x80)がないと、切り替え元の購読は元に戻せるように残る(FORWARD 0、リクエストストリームは開いたまま)。購読者が取り消すかセッションが閉じるまで、購読者のスロットとリクエストストリームを持ち続ける。

参照: `moqtsw_suspend`

### 2.12 切り替えセットに入れるのはリクエストストリームの購読だけ

影響: 制御ストリームで購読するクライアントと、ハブ自身の Track を購読するクライアント。

制御ストリームの SUBSCRIBE(パブリッシャーが戻ったときに通知なしでつなぎ直すもの)や、ハブ自身の Track への SUBSCRIBE に付いた SWITCHING_SET_ASSIGNMENT は、UNSUPPORTED_EXTENSION(0x33)で断る。draft-22 のリクエストストリームの購読はパブリッシャーがいなくなると PUBLISH_DONE で終わるので、セットへの所属が Track より長く残ることはない。

参照: `test_moqtrun_ssts_ctrl_subscribe_refused`

### 2.13 busy shed はネットワークが混んでいなくても品質を下げることがある

影響: 切り替えセットの中のビットレートの高い Track。

lossy relay は `WIRED_MOQTRUN_RESET_AFTER_BUSY`(8)回拒まれたあとに購読者のストリームをリセットする。この閾値は 20 ミリ秒の音声に合わせたもので、こうしたリセットはすべて背圧に入る。ブラウザーでの実行では、ループバック上の約 3 Mbps の 1080p の画面共有が 3 回中 2 回これに当たり、上限を設けていないのに Auto が下位のメンバーへ移った。

切り替えセットのメンバーの捨てた Group は、途中で開き直さない。どのセットにも入っていない Track(音声)は開き直す。

参照: `moqtrun_relay_shed_one`

### 2.14 フェイルオーバーの待機中の切り替え

影響: パブリッシャーが切れた、切り替え中の購読やセットのメンバーの購読([フェイルオーバー](moqt.md#22-フェイルオーバーで待つのは最大-15-秒))。

- SWITCH_FROM の古い側は待たずにすぐ終わるので、つなぎ直しで両側に同じ Group が流れることはない。
- 待っている新しい側は、その間に古い側が終わっていれば、つなぎ直したときに境界から解放される。
- つなぎ直した切り替えセットのメンバーはセットを離れ、REQUEST_UPDATE で再び割り当てられるまですべての Group を受け取る。
- この割り当てはつなぎ直しのあとに送る必要がある。購読がまだ待っている間に送ったものは更新の失敗として断り、その購読は終わる。

参照: `moqtrun_rp_wait`、`moqtrun_reattach_one_sub`

### 2.15 5 Group より遅れたメンバーは決定をやり直す

影響: かなり遅れた Group を配送するメンバー。

決定はセットごとに、最新の Group から 5 を引いた所まで保持する(moqtail の窓)。それより古い Group を配送したメンバーには新しく決定するので、遅れた Group が両方のメンバーから届くことがある。

参照: `test_moqtrun_ssts_lag_outside_window`

### 2.16 パブリッシャーをまたぐ切り替えは、再接続をはさむと境界を失うことがある

影響: パブリッシャーをまたぐ切り替え、再接続、フィルターの更新が重なる場合。

切り替え先の Track のパブリッシャー(別のセッション)が生きている間に古い Track のパブリッシャーが再接続すると、古い購読がつなぎ直される前に、新しい購読が境界から解放される。そのあと新しい購読で LOCATION_FILTER を更新しても G に切り詰められないので、いくつかの Group が両方の Track から購読者に届くことがある。

参照: `moqtsw_old_alive`

### 2.17 新しい Group が切るのは、古いストリームのうち最新のものだけ

影響: `newest_group_only` を設定したハブ(既定ではオフ。moqt_chat の例は設定している)の lossy な経路の購読者。

lossy relay は購読ごとにストリームを 1 本だけ覚えている。新しい Group が開くと、そのストリームと、パブリッシャーがまだ送っている古い Group のストリームをリセットする。パブリッシャーがすでに終えた古い Group の別の Subgroup は、最後まで流す。これらのリセットは背圧に入らない。ストリームに未送信のバイトがあったかを、ハブが判断できないためである。

参照: `moqtrun_sub_note_open`

### 2.18 別版の Track は Group の番号をそろえる必要がある

影響: 別版の Track のパブリッシャー。

境界の規則は、別版の Track 間で Group ID がそろっていることを前提にしている。ハブはこれを確認しない。

### 2.19 Soft の打ち切りは固定

影響: 次のキーフレームが遠い Track への Soft の切り替え。

ハブは切り替えのあと、実時間で `WIRED_MOQTSW_SOFT_WAIT_MS`(4000 ミリ秒、moqt_chat のキーフレームの Group 2 つ分)待つ。打ち切るのは、古い購読の G より前の部分が何も残っていないときだけである。あとから届いた古い購読の Group は捨てる。

参照: `WIRED_MOQTSW_SOFT_WAIT_MS`
