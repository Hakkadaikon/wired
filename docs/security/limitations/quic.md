## 1. 送信と損失回復

### 1.1 ハンドシェイク中の送信中バイト数は概算

影響: ハンドシェイク中の輻輳制御。

Initial パケットと Handshake パケットはパケットごとの ACK の記録を持たないので、そのバイトは鍵を破棄するまで送信中(in flight)として数える(多めに数える)。増幅攻撃対策の上限で送るのを控えた、再送されたデータグラムは少なめに数えることがある。

参照: `srvrun_boot_inflight`(shortcut)

### 1.2 RFC 9002 の任意の経験則は実装していない

影響: まれな損失のパターンでの回復の動き。

次の MAY の項目は実装していない。

- ほかの時点での min_rtt の再設定(5.2。持続的輻輳のときの SHOULD のリセットは実装済み)
- 接続をまたいだ RTT の再利用
- 鍵がそろう前のパケットの損失判定の緩和
- RFC 7661 のウィンドウ更新
- CE の印のプローブ

持続的輻輳(7.6.2)は控えめに宣言する。前の ACK フレームの ACK と重なる損失期間や、ACK 範囲が 32 項目のリストを埋めたステップに照らして確かめる損失期間では宣言しない。BBR のもとでは、持続的輻輳のときの cwnd(輻輳ウィンドウ)は BBR のモデルに任せる。

参照: `srvrun_loss_unbroken`(ponytail)、[rfc9002.md](../../features/rfc9002.md) の対象外

## 2. ストリームとビット

### 2.1 とても古いストリーム ID は使用済みとして扱う

影響: なし。

受信の計上では、使用済みのストリーム ID を窓で覚えている。窓の上限より小さい ID はすでに数え終えたものとして扱う。

参照: `srvloop_rxacct_entry`(shortcut)

### 2.2 grease ビットの選び方は撹拌で、PRF ではない

影響: なし。

相手が QUIC Bit のグリースを許しているとき(RFC 9287)、サーバーは接続ごとの秘密値とパケット番号を掛け算で撹拌した値をもとに、このビットを 0 にする。観測者が原理的には解析できる方法である。

参照: `send_onertt_clear_bit`(shortcut)

## 3. パスと接続 ID

### 3.1 パス検証の制限

影響: アドレスが変わるクライアント(Wi-Fi からモバイル回線へなど)と、アドレス詐称への耐性。

QUIC サーバーは新しいクライアントのアドレスを、PATH_CHALLENGE を送り対応する PATH_RESPONSE を待って確認する。同時に追跡する PATH_CHALLENGE は 2 つ(新しいパスと離れたパス)で、ほかに最後に検証したパスを覚える。

| 状況 | 動作 |
|---|---|
| 新しいパスからのプローブ | 使っていない相手の接続 ID があれば応答する(RFC 9000 8.2.2、9.5) |
| 検証のスロットが空いていない | 検証を始めない。応答はプローブを運んだデータグラムの 3 倍以内に収め、そのパスは使わない |
| プローブに応答した | 予備の相手の接続 ID をそのパスに結び付ける |
| パスを追跡しない | 同じ手順でその ID を RETIRE_CONNECTION_ID で使用済みにする。今のパスの 3 倍の上限でそのフレームを送れないときは、確認応答されるまで再送する |
| PATH_CHALLENGE を 8 個(この実装の容量)より多く含むデータグラム | PROTOCOL_VIOLATION で接続を閉じる |

RFC 9000 9.5 はパスごとに新しい ID を求めているので、応答したプローブ 1 つにつき予備の ID を 1 つ使う。8 個を超える場合の扱いは、RFC 9000 21.9(度を超えた非生産的な活動を接続エラーとして扱える)と 8.2.1(送信側は 1 つのパケットに複数をまとめるべきではない (SHOULD NOT))による。

パスの検証を仕掛け直すとき(2 回目の移動でそのパスを離れたときなど)は新しいチャレンジを始めるので、前のチャレンジへの遅れた応答は一致しない。そのパスは次のチャレンジで検証する。本物の新しいパケットをパス外から複製したものも、そのパスの検証がタイムアウトしてサーバーが元に戻るまでは、送信パスを動かす(RFC 9000 9.3.3 はこの防御を不完全なものとしている)。

増幅攻撃対策の上限(受け取った量の 3 倍までしか送らない)は、そのパスのチャレンジのスロットで数える。スロットを持たないパスには最新のデータグラムの 3 倍を許すので、それより前のバイトは計上しない。

参照: `srvrun_path_*`、`srvrun_amp.c`、`pathsel`

### 3.2 相手の接続 ID

影響: 古い ID が使用済みにならないまま 3 回より多く移動するクライアント。

サーバーはクライアントの接続 ID を 4 つ保持する(active_connection_id_limit 4 を広告)。予備の ID が残っていないと、相手が新しい ID を発行するまで古い ID を使い続ける。

サーバーが使用済みにした ID について NEW_CONNECTION_ID が重ねて届いた場合の扱いは次のとおりである。

| シーケンス番号 | 動作 |
|---|---|
| Retire Prior To より 64 を超えて大きい | その ID を再び保持する |
| Retire Prior To - 64 より小さい | 再び使用済みにし、RETIRE_CONNECTION_ID をもう一度送る |

参照: `peercid_bit`(ponytail)、`peercid_past_bit`(shortcut)

### 3.3 接続テーブルは固定

影響: ビルド時の上限より多くの接続が必要なサーバー。

| ビルド | `WIRED_CONNTABLE_CAP` |
|---|---|
| 通常のビルド | 4(`scripts/just/flags.sh`。`CONNTABLE_CAP=<n> just ninja` で上書き) |
| interop のイメージ | 64 |
| ヘッダー自身の既定値 | 64 |

検索は、スロットが持つすべての接続 ID を対象にしたオープンアドレス法のハッシュである。索引は挿入、鍵の更新、接続 ID の変更のたびに作り直す(パケットごとではなく、接続のイベントごと)。

ハッシュはプロセスごとのランダムなシードで鍵付けしているので、クライアントが衝突する Initial の DCID を前もって計算することはできない。PRF ではないので、(タイミングなどから)衝突を知った者は、それらを固めて送れる。

最悪の場合、1 回の検索で最大 3 * cap 個のバケットをたどり(接続 ID の比較は最大 9 * cap 回で、以前の線形走査の約 3 倍)、作り直しは O(cap^2) である。

参照: `conntable.h` の先頭のコメント(ponytail)

## 4. ECN、ソケット、IP

### 4.1 ECN の印は UDP ソケットでの ECT(0) だけ

影響: ECN(IP ヘッダーに付ける明示的輻輳通知の印)に頼るネットワーク。

AF_XDP(カーネルを迂回するドライバー)は印を付けず、ECT(1) は送らない。ECN の検証に失敗した接続は Not-ECT で送り、GSO でのまとめ送りは続ける。

参照: `srvrun_ecn_unmarked`

### 4.2 ソケットオプションにカーネル側の代替経路がない

影響: `udp.h` のソケット用ヘルパーを直接呼ぶアプリケーション。

`IP_TOS`/`IP_RECVTOS` と、`IP_MTU_DISCOVER` 系の PMTU プローブのオプションのヘルパーは、setsockopt のエラーを返すだけで代わりの手段はない。`wired_server_run` はこれらをできる範囲で呼び、失敗しても bind する。

そのため、これらを拒むカーネルでは、ECN の印の付与や読み取りがないまま、あるいはカーネルの PMTU の停止がないまま、サーバーが動く。

参照: `udp.h` の `wired_udp_ect0_enable` とその仲間(ponytail)、`srvrun_listen`

### 4.3 PTB (ICMP) は無視する

影響: プローブした値より MTU が小さいパス。

DPLPMTUD(プローブを送って使える最大のパケットサイズを探すこと)はプローブだけに基づく(RFC 8899 4.6.1 の選択肢)。最初の窓は 1200 バイト固定の最大データグラムを使う。フロー間での PLPMTU の共有も、ERROR/DISABLED の段階もない。

参照: [rfc8899.md](../../features/rfc8899.md)、[rfc9000.md](../../features/rfc9000.md)、[rfc9002.md](../../features/rfc9002.md) の対象外

### 4.4 IPv4/UDP/IP の細部

影響: まれな IP トラフィック。

- wired はフラグメント化せず、IP オプションも送らない。DF は常に立てる。RFC 9000 §14 はフラグメント化が必要な QUIC のパスを除外している。
- AF_XDP の経路では、受け取ったフラグメントとオプション付きのデータグラム(IHL > 5)を捨てる。BPF のフィルターがそれらをカーネルへ渡し、カーネルが組み立て直した結果やオプションを処理した結果は、読まれないポート予約用のソケットに届く。この動作は意図したものである。
- カーネルの UDP ドライバーはどちらも通常どおり受け取る。
- ToS は使わない。AF_XDP の経路では TTL を 64 に固定し、UDP の送信元ポートが 0 の場合は扱わない。
- `veth` では `--skip-udp-csum` が必要である(CHECKSUM_PARTIAL のフレームのため)。

参照: [rfc791.md](../../features/rfc791.md)、[rfc768.md](../../features/rfc768.md) の対象外

## 5. 0-RTT とトークンの記録

### 5.1 0-RTT のリプレイ検出用リング

影響: 再開が多い中で 0-RTT を受け付ける運用。

- `ZERORTT_SEEN_CAP` は 4096 個の指紋を保持する。
- 項目を追い出すのは、そのリプレイが鮮度の確認(`ZERORTT_SEEN_LIVE_SECS`、21 秒)を通れなくなってからである。
- リングが有効な項目で埋まっている間は新しい 0-RTT の試みを断り、クライアントは 1-RTT に戻る(RFC 8446 8.2)。
- fork したワーカーはリングを共有するが、別々のサーバープロセスや再起動をまたいでは共有しない(永続化しない)。

そのため、`ticket_key` のシードをサーバー間で共有すると、0-RTT のチケットはサーバーごとに 1 回リプレイできる。シードを共有するサーバーで `early_data` を有効にすると、この状態になる。

参照: `zerortt_seen.h`(ponytail)

### 5.2 使用済みの NEW_TOKEN の記録は 4096 個まで

影響: トークンの有効期間内に多くの NEW_TOKEN のトークンを提示されるサーバー。

- 同じ 4096 項目のリングが受け付けたトークンをそれぞれ記録する。
- 項目を追い出すのは `NEWTOKEN_MAX_AGE_SECS`(7 日)より古くなってから、つまり記録したトークンが期限切れになってからである。
- リングが有効な項目で埋まっている間はそれ以上のトークンを断り、クライアントは検証なしで進む。このとき効くのは増幅攻撃対策の上限か、`force_retry` のもとでの Retry である(RFC 9000 8.1.3)。
- fork したワーカーは 1 つのリングを共有するので、4096 はワーカーごとではなくサーバーごとの数である。
- 記録は別々に起動したサーバーの間では共有せず、再起動をまたいでも残らない。

そのため、`wired_srvkeys_set_token_key` でトークンのシードを共有すると、トークンはサーバーごと、再起動ごとに 1 回再利用できる。

参照: `srvrun_newtok_ok`、`zerortt_seen_check_live`

## 6. 低レベルの入口

次の 2 項目は低レベルの入口の制限である。`wired_server_run` が組み立てるサーバー(guide が使うもの)は connio も `appdata_recv` も動かさないので、これらを直接呼ぶ場合にだけ関係する。

### 6.1 `connio` は送信を常に ACK 誘発として印を付ける

影響: connio の利用者だけ。

このフラグは 1 に固定なので、ACK 誘発でないフレームだけを送っても、そう分類されない。

参照: `connio.c`

### 6.2 `appdata_recv` はパケット番号の履歴を持たない

影響: この単発の入口の利用者だけ。

largest_pn には 0 を渡す。パケット番号の完全な復元は srvloop の経路が行う。

参照: `app_recv.c`(ponytail)

## 7. 相互運用性

### 7.1 接続の移行の相互運用性

影響: 移動するクライアント。

[相互運用性の検証結果](../../verification/interop.md) は `connectionmigration` を部分的な対応として記録している。ngtcp2 との組み合わせでは通り、quic-go のクライアントはパスの変更を一度も起こさない。

quic-go のクライアントは `ecn` と `v2` のテストケースに対応していない。どちらも ngtcp2 との組み合わせでは通る(`v2` は picoquic とも通る)。
