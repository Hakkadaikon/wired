## 1. 判定とテストの有無

<a id="what-a-ledger-row-is"></a><a id="台帳の行とは"></a>

| 判定 | テスト | 周りのコードが変わったとき |
|---|---|---|
| `fixed`、`already-safe` | たいていある。構造上の理由による少数の行は、テストの代わりに根拠の列にコードが攻撃されえない理由を書く | テストがある行は、テストが動き続けるので安全なまま |
| `n/a` | ない | 機能がないことを理由にした行は、その機能を入れないあいだだけ安全 |

`n/a` の行の一部は wired のコードへの攻撃ではなく、RFC の設計上の注記や運用者の懸念を記録する情報の行である。

## 2. 機能を追加するとき

<a id="why-this-list-matters-when-you-add-a-feature"></a><a id="機能を追加するときにこの一覧が重要な理由"></a>

3 章の表の機能を追加すると、そのグループのすべての行がふたたび現実のリスクになる。そのときは各行を読み直して新しい判定を決め、それを固定するテストを書く(再トリアージ)。

表の行の大半は `n/a` である。次の 3 行は、台帳が wired に実際にあるコードと結び付けているので `already-safe` である。

| 行 | 結び付けたコード | テスト |
|---|---|---|
| V-0223 | ECN のカウントの検査 | ある。欠けている部分(自分で CE を付けるプローブ)にはない |
| V-0547 | 大文字小文字を区別しない名前照合 | ある。欠けている部分(RFC 4518 の文字列正規化)にはない |
| V-0711 | RSA 署名の検証 | ない。wired は RSA で復号しないので、RSA 復号へのタイミング攻撃には狙えるコードパスがない(構造上の理由) |

ECN の行の補足は次のとおりである。

- wired は自分で CE を付けるプローブができない。ECN ビットをソケット全体に設定し(`IP_TOS`)、送信するパケットごとには設定しない(`cmsg`)からである。
- RFC 9000 13.4.2.1 のカウントの下限では、ピアが報告するカウントが、新しく確認応答されたパケットの数以上に増えているかを検査する。CE の報告を落とすピアはこの検査に失敗し、wired は ECN を無効にして損失検出に頼る。CE を通常の印に付け替えるピアはこの検査を通る。それを見つけるには、自分で CE を付けるプローブが要る。

## 3. 機能ごとの行

「追加したら再トリアージ」は、いまは攻撃が成り立たず、機能を追加したら行を再トリアージすることを示す。それ以外のセルは、その欠落がデプロイにとって何を意味するかを示す。MoQT の行のフックは、アプリケーションが購読を 1 件ずつ承認する仕組みで、ガイドの [購読者の認可](https://hakkadaikon.github.io/wired/guide/ja/moqt/authorize/) にある。

| ない機能 | 台帳の行 | デプロイへの影響 |
|---|---|---|
| Encrypted Client Hello(ECH、draft-ietf-tls-esni) | V-0238, V-0240 | 追加したら再トリアージ |
| CertificateVerify での ECDSA P-521(対応: P-256、RSA-PSS、Ed25519) | V-0247 | ピアは CertificateVerify に `ecdsa_secp521r1_sha512` で署名できない。P-521 で署名された証明書チェーンは検証できる(2026-10-10 から) |
| 有限体 DHE のグループ(X25519 / P-256 の ECDHE のみ) | V-0270 | 追加したら再トリアージ |
| RSA-PSK / RSA 鍵輸送(RSA は検証専用) | V-0271, V-0274, V-0660, V-0696, V-0711, V-0739, V-0741 | 追加したら再トリアージ |
| CBC モードの暗号スイート(AES-GCM と ChaCha20-Poly1305 のみ) | V-0285, V-0759 | 追加したら再トリアージ |
| certificate_compression 拡張(RFC 8879) | V-0299 | 追加したら再トリアージ |
| 外部 PSK(サーバーが封印した再開用チケットのみ) | V-0300 | チケットによる再開のみ。Selfie 型の反射には攻撃面がない([脅威モデル](threat-model.md) の 3.1) |
| 失効確認: CRL、OCSP、OCSP stapling、AIA / CRL-DP の取得 | V-0324, V-0528, V-0531, V-0557, V-0560, V-0573, V-0620, V-0621 | 失効は運用者の関心事(短命な証明書、帯域外でのローテーション)。クライアント認証を有効にしていると、失効したクライアント証明書も有効期限まで受け入れるので、短命なクライアント証明書を発行するか、その CA をトラストストアから外す |
| TLS 1.2 以前: extended_master_secret、middlebox compatibility mode、SSLv2 CLIENT-HELLO | V-0347, V-0360, V-0366 | wired は TLS 1.3 だけを、QUIC の中でだけ話す |
| クライアント側の、パラメーターを変えて再試行するループ | V-0351 | 追加したら再トリアージ |
| ECN の自分で CE を付けるプローブ(ソケット全体の IP_TOS のみ、送信ごとの cmsg なし) | V-0223 | CE の報告を抑えるピアは、RFC 9000 13.4.2.1 のカウントの下限で引き続き検出できる |
| DSA | V-0576, V-0655, V-0677, V-0687 | 追加したら再トリアージ |
| Curve448 / Ed448 / Ed25519ctx-ph のコンテキストパラメーター | V-0718, V-0729, V-0730, V-0732, V-0734, V-0766 | 追加したら再トリアージ |
| Init/Update/Finish(ストリーミング)の署名 API(単一バッファーのみ) | V-0736, V-0737 | 追加したら再トリアージ |
| 秘密鍵の生成(鍵は生のシードやスカラーとして渡す) | V-0747 | 追加したら再トリアージ |
| PKCS#7 / CMS のパース | V-0526 | 追加したら再トリアージ |
| 名前制約での RFC 4518 DN 文字列正規化(directoryName 以外の形式はバイト列の完全一致) | V-0547 | 追加したら再トリアージ |
| Signed Certificate Timestamps / Certificate Transparency | V-0549 | 追加したら再トリアージ |
| SAN / 名前制約での rfc822Name(メール)GeneralName | V-0556 | 追加したら再トリアージ |
| 複合 / 複数アルゴリズムの署名(draft PKIX CompositeSignature) | V-0568 | 追加したら再トリアージ |
| HTTP/1.1 のバックエンド接続(プロキシの役割なし) | V-0435 | 追加したら再トリアージ |
| HTTP/3 サーバープッシュ(PUSH_PROMISE) | V-0446 | 追加したら再トリアージ |
| QPACK の仲介者の役割(接続ごとに動的テーブル 1 つ、転送なし) | V-0468 | 追加したら再トリアージ |
| クライアント側での WebTransport セッションの開始 | V-0510 | 追加したら再トリアージ |
| MoQT の認可トークン方式(CAT / Privacy Pass)。トークンはデコードして authorize フックに渡す | V-0794 | 認可はリレーが wired_moqt_hub.authorize_subscribe で判断する |

この表は 25 のグループに台帳の 51 行を挙げる(2026-11-07)。台帳のほかの行は `fixed` か `already-safe`、または機能の欠落によらない理由(情報の行や設計レベルの行など)による `n/a` である。
